## 2. 必须修正的交付判断

### 2.1 [交付前必补] “机制等价版”缺少源码依据

**结论：第 79–81 行不能把容器回测直接归入最终 worker-owned 补丁的验收。**

依据：第 72 行说容器仍使用 `.staging.20261010`；第 79 行另有官方 rc7 上的终版 diff；第 80 行将二者称为“机制等价”。上一版现场说明描述的是 coroutine 创建、关闭 mmap 的方案，而 U6 又专门证明了这种所有权安排的风险。现有摘要不足以确定容器是否已经迁移到 worker-owned，更不足以确认写侧对齐 staging、短写检查已经同时进入容器。

另外，U6 是独立 `cancel_demo2.py`；U7 是 allocator/smaps 探针；U8 是独立回环。它们即使运行在同一容器，也不等于执行了容器的 `FSL2Adapter`。

最小补充材料：实际 import 路径、现场基线 commit（无法取得则明确标记）、**准备交付的完整 diff**，以及一张对应表：每项实验实际调用哪个函数、运行的是哪个版本。核对实际读写 helper、`_execute_store`、`_execute_load` 即可，不需要重新扫描整个仓库。

建议替换第 78–81 行中的验收表述：

### 2.2 [交付前必补] U8 绕开了需要验证的读路径

**结论：U8 可以证明“该探针的一次字节回环成功”，不能写“最终读写字节正确性封闭”。**

依据：U8 使用 `os.read(fd, n)` 返回 bytes；最终方案则需要读入 worker 的对齐 staging，再经 coroutine 拷入真实 ACL 目标。U8 没有覆盖后一段，也未证明最终 helper 的 `fdopen/readinto` 在现场正常。

公开 rc7 的 [_read_with_odirect](https://github.com/LMCache/LMCache/blob/05a013b29da78cf2321b9b46ec5039dde2fb0bb0/lmcache/v1/distributed/l2_adapters/fs_l2_adapter.py#L536-L573) 使用 `os.open(..., O_RDONLY | O_DIRECT)`、`os.fdopen(fd, 'rb', buffering=0)` 和 `_readinto_full`。Python 明确允许 `FileIO` 包装已有 fd，并规定关闭时是否同时关闭 fd；没有“与 O_DIRECT 固有不兼容”的接口限制。当前 `EBADF` 的具体原因**未核实**，应查看探针的打开模式、fd 所有权、关闭顺序和 traceback，不能猜定某一种原因。[Python FileIO 文档](https://docs.python.org/3.10/library/io.html#io.FileIO)

`os.read` 的契约是返回最多 n 字节的 bytes，没有承诺其内部缓冲满足指定 DIO 地址对齐。打开时携带 O_DIRECT、调用成功，也不自动证明没有发生文件系统允许的 buffered fallback。因此不要把探针的替代读法直接写进正式补丁。[Python os.read 文档](https://docs.python.org/3.10/library/os.html#os.read)、[Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

最小补测：让已知 9,437,184 字节模式经过**最终 store → 最终 load → 真实 ACL 目标**，逐字节核对目标内容；必须实际调用候选 helper，不另写一条旁路。若实际 helper 同样报 EBADF，先修清楚 fd 的使用问题，再验收。无需增加新的哈希流程。

### 2.3 [交付前必补] 对齐“部署前提”不能全部降为非阻塞项

**结论：保留 O_DIRECT 的交付，需要确认实际缓冲地址、传输长度、文件偏移都满足部署要求；statx 是优先方法，不是唯一方法。**

依据：第 88 行把对齐检查称为部署前提，却整体置于“不阻塞交付”。两者矛盾。`align=0` 只说明记录中的指针对某个模数取余为零；本轮运算可确认该指针 `%4096 == 0`，不能由此推出目标文件的全部 DIO 约束均满足。

对目标缓存文件查询 `STATX_DIOALIGN` 时，先检查返回的 `stx_mask` 是否提供该字段，再读取有效值：`stx_dio_mem_align` 约束用户缓冲地址，`stx_dio_offset_align` 约束偏移和传输长度。字段缺失不能当作“无约束”；支持标志存在但值为零的情况，也不能直接取模或解释成可放心直读。[Linux statx(2)](https://man7.org/linux/man-pages/man2/statx.2.html)

记录候选实际 staging 的地址 A、要求 M、偏移 O、长度 N、偏移/长度要求 D，验证 `A % M == 0`、`O % D == 0`、`N % D == 0`。`lcm(...) % M == 0` 只解释候选分配策略为何适用，不能替代对本次实际调用参数的检查。写临时文件和读最终文件均须满足约束；若位于不同挂载，应分别核实。

若现场内核不支持该查询，记录这一事实，并以该内核、文件系统、设备的已知约束及对齐缓冲验证提供替代依据。无法建立前提时，可以交付明确采用 buffered 的临时规避配置，但不能认证“保留 DIO 的补丁已验收”。这不要求为了本次修复实现一个通用文件系统探测框架。[Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)

## 3. 必须收窄的根因与实验结论

### 3.1 U9 增强了缓存复用证据，尚不能量化“只重算 256 tokens”

**结论：保留“命中变化与目标块删除相符”，删除“其余 32 key 全部零重算”和“仅重算 256 tokens 已闭环”。**

依据：公开 rc7 的 `engine_driven_transfer.commit_store()` 在 store 成功后，以 `len(_resolve_single_group_obj_keys(key)) * chunk_size` 生成 `Stored ... tokens`。它没有读取 vLLM 实际计算 token 数。写回 256 tokens 可以与只补算一个块相符，但也可能仅反映选择性存储范围。[公开 commit_store 源码](https://github.com/LMCache/LMCache/blob/05a013b29da78cf2321b9b46ec5039dde2fb0bb0/lmcache/v1/multiprocess/modules/engine_driven_transfer.py#L403-L442)

公开 `query_prefetch_status()` 的数量是 bitmap 中保留的 key 数；连续可用前缀需另外计算。公开实现还区分 PREFIX 与 SPARSE 等策略。因此 `32/36` 不能独立给出模型实际少算多少 tokens。[公开 Prefetch 计数源码](https://github.com/LMCache/LMCache/blob/05a013b29da78cf2321b9b46ec5039dde2fb0bb0/lmcache/v1/distributed/storage_manager.py#L692-L738)

需要补充被删 key 对应的 **chunk 序号/起止 token、4 个 rank 的完整对应关系、实际 trim policy**。若删除的是最后一块，32 个前缀 key 保留与普通前缀复用一致；若删除中间块，必须说明缺口后的 key 如何被保留并真正供模型使用。不要从总命中数推断连续前缀长度。现场 fork 是否改变这些语义，**未核实**。

精确“少算多少”只有在需要保留该结论时才补：同一请求的实际 prompt token 数、外部缓存实际消费范围、实际执行的 prefill token 数，并说明最后一 token/不满块尾部等是否仍需计算。否则降级措辞即可，无需为一个不必要的量化承诺扩大实验。

建议替换 U9 结论：

> 删除当前请求的一组 4-rank 文件后，报告的保留 key 数由 36 降至 32，并出现 Stored 256 tokens，文件数随后恢复。结果与缺失块触发补存的预期一致，增强了 L2 缓存参与本次请求的证据；具体重算量、其他块是否完全免算，尚未核实。

### 3.2 映射属性可以确认到报告层面，具体内核拒绝链仍有边界

**结论：ACL host 映射兼容性应继续作为主定位；第 28 行的绝对排除和完整内核因果链应改写。**

依据：U7 报告了实际指针所属 VMA 的 `io/pf`。这些符号分别对应 memory mapped I/O area 与 pure PFN range，支持特殊映射性质；结合之前稳定保活、相同大小的普通 mmap/ACL 对照，解释力明显高于最初单看 EFAULT 的判断。[Linux 内核 proc 文档](https://kernel.org/doc/html/v5.13/filesystems/proc.html)

但目前没有目标内核的准确版本、故障系统调用对应的拒绝点记录。新探针还需与实际服务 allocator 来源对应，才可把该映射属性直接归给每次出错的原目标。无需为推进局部兼容修复强制取得内核调用栈，但不能一边写“具体分支未取”，另一边写该分支已经定案。

“与文件系统无关”也过强：普通缓冲在同挂载成功，可排除“该挂载完全不能执行本次 I/O”这一解释；不能排除文件系统对对齐、fallback 和 DIO 路径的影响。“UAF 不是 E4 同步保活探针的必要解释”不等于所有异步补丁不存在 UAF，U6 恰好展示了另一条生命周期风险。

建议替换第 28 行：

> 在已报告的 Ascend/ext4 环境中，稳定保活且页对齐的 ACL host 缓冲直达 I/O 失败、普通 host staging 成功，新增 VmFlags 的 io/pf 证据进一步支持 ACL host 映射与该 I/O 路径不兼容的定位。具体内核拒绝分支尚未核实；本结论不排除独立异步补丁的生命周期风险，也不外推为所有对齐及文件系统条件均无关。

### 3.3 U6 没有补齐早期首请求挂死的具体因果链

**结论：可以保留“早期读补丁引入回归”的行为 A/B 判断；不能继续把两条代码风险都写成现场已触发的挂死机制。**

依据：`finally` 中 `continue` 可以丢弃待传播异常，这有语言语义依据；但“吞取消”不自动推出“等待方永久阻塞”，还取决于循环、完成通知、controller 等待条件。[Python finally 语义](https://docs.python.org/3.10/reference/compound_stmts.html#finally)

`unpin()` 触发 free 则取决于当时 pin/ref 值及 allocator 行为，文档第 89 行承认这些仍未取证。U6 检验的是 **coroutine 提前关闭 staging 与 worker 继续使用之间的竞态**，与这两条现场因果链不是同一个实验。

建议替换第 29 行和第 90 行括号：

> 既有 A/B 结果支持早期 pin/unpin 读补丁与首请求在 120 秒窗口内未完成存在回归关联；finally 中的 continue 抑制取消、unpin 条件释放属于源码风险，是否在该现场触发仍未核实。U6 单独证明了 coroutine-owner staging 的取消竞态；它没有验证原挂死的取消入口和释放时序。

## 4. 三处应直接改掉的文字或实现说明

### 4.1 映射区间是 8 TiB，且不是物理内存容量

**结论：第 12、48 行“1TB 共享段”改为“跨度 8 TiB 的共享虚拟映射区间”。**

依据：`0x180000000000 - 0x100000000000 = 0x80000000000 = 8,796,093,022,208` 字节，即 8 TiB。本轮已核算；指针 `0x12c080c00000` 位于此区间且 `%4096 == 0`。VMA 的地址跨度不等于实际分配或驻留了 8 TiB 物理内存。探针本次申请的仍是 9,437,184 字节。

### 4.2 `cast('B')` 不能随 staging ownership 一起从 coroutine 删除

**结论：第 21 行改为分别说明两种 view 的职责。**

依据：staging 的 view 由 worker 管理；实际目标的 `<B` view 仍属于 coroutine 的 copy-back 路径。`dst_bytes[:] = payload` 只是最后一行，前面仍须在目标 reservation 有效时取得可写、连续的目标 view，执行 `cast('B')`、长度校验并在使用后释放。worker 不得持有原目标；完整读取且 coroutine 未取消时才 copy-back，完成后才置命中位。

建议替换文字：

> worker 负责其 staging view 的释放和 mmap 关闭；coroutine 负责真实目标 view 的 cast('B')、完整 copy-back 和 view 释放。两者分别管理自己的视图，staging 所有权迁移不取消目标格式处理。

### 4.3 交付路线明确为 LMCache 主库 PR

**结论：按用户最新明确要求，本次修复提交 LMCache 主库；撤回此前要求改为 Ascend 侧优先的审查意见。**

依据：用户已将交付目标明确为主库，覆盖此前“尽可能只改我们自己的”的路线偏好。因此原文“主库 PR 主要”的方向正确，无需另行设计 Ascend 插件或构建补丁作为本次交付物。主库修改仍应限定在 FS L2 的相关读写路径，以通用的缓冲所有权、对齐、完整读写和失败处理实现修复，避免引入不必要的 Ascend 专用依赖。

| 可选：精确重算量 | 仅在保留“只算 256、其他零重算”时补实际计算量及被删块序号 | 若不补，使用本审查给出的 U9 限定表述即可。 |
| 可后补：故障深层机制 | 实际内核拒绝点、原挂死取消入口及 pin/ref/free 时序 | 不阻塞采用正确 staging 方案，但须保留“未核实”。 |

B 组只覆盖本次修改直接影响的路径，无需全套模型/文件系统矩阵：

| 检查 | 最小动作 | 判定 |
|---|---|---|
| 正常完整读写 | 已知 9 MiB 数据通过最终 store/load，拷入真实 ACL 目标 | 返回长度完整，目标字节一致，命中位在 copy-back 成功后置位，无 view 关闭错误。 |
| 短写失败 | 在最终写 helper 注入一次返回少于请求长度；使用独立实验 key | 抛出失败、不 rename 为正式文件、不报告完整存储成功；已有有效文件不被截断。不要直接截断正式路径。 |
| 短读失败 | 使用独立截断缓存文件调用最终 load | 不把部分数据拷回、不置命中位；其余 key 和正常批次完成处理仍有效。 |
| 取消与收尾 | 在最终 worker 开始 I/O 后阻塞它，取消等待任务，再放行 worker | 取消按既有协议传播，目标无晚写；worker 用完才释放 staging，任务和 reservation 最终进入正确终态。若 close 复用取消路径，同场核对关闭收尾。 |
| 首请求与 buffered | 在最终版本做一次 L1 空、L2 有的首请求及一次 buffered 对照 | 首请求在既定超时内完成、读写内容正确、相关命中日志对应同一请求；buffered 分支正常。已有两轮旧版本结果可保留，无需机械重跑多轮。 |

这里的“终态”不能通过伪造成功通知实现；失败、取消与命中须保持既有 controller 协议。测试可以复用现有工具，不要求新增测试框架。若能提供已在**同一最终实现**执行的对应记录，直接复用，无需重复实验。

## 6. 可直接采用的当前定稿文字

**结论：当前可以对外发布以下限定结论；最终补丁验收状态另列。**

> 在现场报告的 Ascend 910B、vllm-ascend 0.23.0、Qwen3-8B、TP=4、chunk=256、engine_driven、APC 关闭及 ext4 配置下，实验支持 ACL host 缓冲与当前 O_DIRECT 路径存在兼容性问题；新增 VmFlags 的 io/pf 记录进一步支持特殊映射解释，具体内核拒绝分支尚未核实。普通 host staging 的容器实现已有写入恢复和冷启动 L2 命中完成记录，缺失块对照与缓存参与请求的预期一致；实际重算 token 数尚未核实。最终方案采用 worker 自持有的对齐 staging、完整读写检查和受 reservation 保护的 copy-back；该终版与现场回测实现的一致性、真实读回及取消/短读/短写验收仍待补齐。修复以提交 LMCache 主库 PR 为交付目标，最终补丁与验证应对应主库实际目标基线。
