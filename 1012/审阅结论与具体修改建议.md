## 2. 定位还不全面的具体位置

### 2.1 非对齐写成功，不能推出“ext4 不强制对齐”

**结论：E1a 支持这个挂载上存在可成功的请求 direct I/O 的写法；E1b 只能说明两次非对齐调用被接受。**

依据：Linux 文档允许非对齐请求失败，也可能退回 buffered。没有应用侧降级 warning，只能排除那个应用分支，不能排除内核/文件系统内部 fallback。`stat -f` 的 block=4096 也不等于目标文件 DIO 的完整内存、长度和 offset 对齐契约。[Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)。

应补：E1b 实际 syscall 参数、最终指针余数、fd 的 O_DIRECT 标志；优先读取目标文件的 `statx(STATX_DIOALIGN)`。如果只是要修复正常读写，可暂不定位内核 fallback；但“真 O_DIRECT/绕过 page cache”的结论必须暂缓。

### 2.2 E4 确认的是候选责任层，VM 标志还缺证据

**结论：不需要为了选择 staging 而先改内核；但要把 VM_IO/VM_PFNMAP 写成已证实根因，就必须补对应 VMA。**

依据：Linux 6.6 的 GUP 确有拒绝这些 VMA 的路径；这不是所有 CANN/Ascend/Linux 版本的 ACL 内存统一属性。只需目标指针所属 VMA 的地址范围与 `VmFlags`，再确认目标内核的对应代码；不必导出整个进程内存或完整 smaps。[Linux GUP 源码](https://github.com/torvalds/linux/blob/v6.6/mm/gup.c#L969-L977)。

还要确认 E4 的 ACL 对象就是实际 L1 分配路径，且分配长度覆盖整个 9 MiB。裸指针、ctypes view 或 Python 强引用不自动禁止外部分配器显式 free。

### 2.3 `finally: continue` 的语言事实正确，但“所以永久阻塞”缺一段证据

**结论：必须移除 finally 内的 continue；它会丢弃正在传播的异常，但不能单靠这件事推出永久挂死。**

依据：Python 的 finally 执行 continue 时会丢弃保存的异常，包括 CancelledError。有限 for 循环也可能继续到结尾并正常完成。因此必须知道谁触发取消、是否到达 finally、是否卡在 unpin/free、是否发布 load 完成结果、等待方等哪个事件。[Python finally 语义](https://docs.python.org/3.10/reference/compound_stmts.html#finally)。

客户端 HTTP 超时不自动等于 `_execute_load` 被 cancel。若首次请求卡住时还没有发生取消，“吞取消”也不能解释最早的卡点。文档中的“永久”应先改为“在 120 秒以上观测窗口未完成”。

### 2.4 `unpin()` 的 free 分支存在，现场是否执行仍需数值

**结论：移除新增 pin/unpin 有根据；不要把“通常 ref_count=0”当成已经记录了 free。**

依据：公开 rc7 `unpin()` 在 `pin_count<=0 && ref_count<=0` 且有 parent allocator 时确实 free；但实际对象类型、初始计数及 parent allocator 需现场核对。即使 worker 已读完，提前 free 也可能发生在 controller 宣布目标可读之前。需记录 `pin前 → unpin前/后 → free/invalidate → load完成发布`。[公开实现](https://github.com/LMCache/LMCache/blob/05a013b29da78cf2321b9b46ec5039dde2fb0bb0/lmcache/v1/memory_management.py#L797-L825)。

“不加 pin”不等于“不需要生命周期保护”。继续依赖既有 controller reservation，覆盖源快照、目标 copy-back 和完成发布。

### 2.5 E5 是明显进步，但三项指标要校正

**结论：可以称两轮冷启动 L2 路径成功，不能称“已证明 36 个 token chunk、完全无重算、KV 内容全正确”。**

依据：

- 日志首先计的是 **36 个 object key / rank 分片**。若每 token chunk 对应 4 个 rank key，且单对象 9 MiB，则是 9 个 token chunk，即 2304 tokens 的完整块范围；不是 36×256 tokens。实际布局、尾块与 key 集合仍需核对。
- 36×9 MiB=324 MiB 的体积在上述假设下合理，但不能仅据日志当作物理 NVMe 吞吐。
- 文件增量 0 可能只是相同 key 去重：即使重新 prefill，`exists()` 也可以跳过写入。应记录实际 recomputed/prefill tokens 与 L2 缺失对照；命中时有少量尾部重算也可能正常。
- `prefetch_request_id=0` 表示有 controller 任务，不单独证明读过 SSD。`0 L1,36 L2` 是更强证据，但还要结合该 fork 的计数公式、load 完成和文件字节数。完整日志格式与公开版本是否完全相同，未核实。
- TTFT 需说明是否 streaming 首个有效生成 token；若仍使用非 streaming 的 curl 首字节时间，只能标 TTFB。
- HTTP 200 不证明 KV 值正确，应补已知模式的逐字节回环与端到端输出基线。

公开计数依据：[StorageManager](https://github.com/LMCache/LMCache/blob/05a013b29da78cf2321b9b46ec5039dde2fb0bb0/lmcache/v1/distributed/storage_manager.py#L693-L738)。

## 4. 具体怎么改：推荐的最小责任边界

**结论：保留 staging 方向，但将其 owner 放入同步 worker；写侧只在最终 direct 分支快照，读侧 worker 返回自有 bytes，协程完成 copy-back 后才置成功位。删除新增 pin/unpin 和 finally 内 continue。**

依据：原方案在 coroutine 中创建 mmap、await worker、finally release/close；取消 coroutine 不意味着 worker 已结束。可能出现释放正在使用的 view、BufferError、关闭失败或排队任务拿到已释放视图。只改变 release/close 顺序没有解决生命周期终点。

推荐数据流：

```text
写：有效源 reservation → bytes 快照 → worker 自有对齐 mmap → 完整 write
    → helper 正常返回 → 原有 rename / 完成通知

读：worker 自有对齐 mmap → 完整 read → bytes 结果 → worker 关闭 mmap
    → await 正常返回 → 仍受 reservation 保护的目标 cast('B') / copy-back
    → bitmap.set → 原有 load 完成通知

读等待被取消：没有 copy-back；worker 只访问自己的 mmap，完成后自行释放。
```

这版比“mmap 直接拷回”多一次读侧 snapshot copy，换取明确的取消边界；不是性能最优宣称。每个在途 key 额外峰值约两份大小（9 MiB 对象约 18 MiB，加对齐余量），总量按实际同时在途任务计算；逐批串行不等于全服务只有一个任务。后续如果要去掉这次复制，应另做完成等待/取消与资源交接设计，不混入最小修复。

### 4.1 对齐策略与适用前提

**结论：本候选面向已核验的目标部署，不宣称自动适配所有文件系统；仍须验证 staging 对齐能覆盖实际 DIO 要求。**

为不新增配置或依赖，候选沿用现有 `_os_disk_bs` 长度 gate，并用它与 `mmap.PAGESIZE` 的最小公倍数选取 staging 地址；多申请后切片保证实际指针满足所选 alignment。它不改变对象长度、不补齐文件、不改 KV 布局。

**应用前必须满足**：目标 `stx_dio_mem_align` 能整除所选 alignment，写/读 offset 及长度满足各自要求；若 statx 不可用，以目标内核/挂载资料和对照实验明确该条件。不能把 `_os_disk_bs` 本身宣传为标准 DIO 查询结果。条件不成立时不要套用这版定版补丁，应改为从目标文件获取真实契约，或明确选择 buffered。

### 4.2 为什么不是在 `_execute_store` 顶部直接换 bytes

**结论：快照必须放在 `if do_odirect:` 内，且在执行器提交前完成。**

依据：顶部赋值会让 buffered 分支也多一份拷贝，与原方案“buffered 零改动”矛盾。源在快照复制完成前仍需 reservation；不能称生命周期“完全解耦”。快照只解除此后的后台写对原区域的依赖。

### 4.3 读失败、格式与成功发布

**结论：只有完整读取且 copy-back 成功才 `bitmap.set(i)`；不要在 finally 中 continue、return 或发布成功。**

依据：`cast('B')` 对连续的 `<B` 字节 view 合理；它不把不连续布局变成连续，也不把只读内存变成可写。候选显式拒绝只读目标，并让不连续 cast 失败进入原有 per-key 异常路径。短读不拷贝部分数据、不置位。所有短暂 view 用 context manager 释放。

### 4.4 短写与临时文件

**结论：必须检查 write 返回值；短写直接报失败，不允许 rename 发布。**

依据：公开 helper 原先丢弃返回值。候选加 `O_TRUNC` 防止重用临时文件留下旧尾部，并在字节数不等时抛错。为保持改动小，暂不增加复杂续写；重试剩余数据会再次涉及地址与 offset 对齐。

同一 tmp 路径是否可能被并发写者使用必须核对。若有并发，不能只加 O_TRUNC；应改每任务唯一临时名，再走原子 replace。本候选以同 key 临时路径无并发写者为前提，未通过此前提不得合入。文件格式、key 名称和正式文件发布位置保持不变。

### 4.5 Ascend 自有仓库承载

**结论：优先在 LMCache-Ascend 构建中管理锁定 commit 的小 diff；本次不要求新建完整 adapter 框架。**

依据：当前修的是已部署 FS 实现的数个局部函数；为两处边界复制大段私有控制流并不更小。若你们已有合适的 Ascend FS plugin，可把同样 helper 放入既有实现。无论哪种，都需让构建实际应用、运行时 import 确认；不能仅放一个 diff 文件就算交付。

## 6. 如何验证没有引入相关回归

**结论：文档审查不能承诺绝对没有新问题；下面的定点检查覆盖此次改动直接触及的风险，通过后才可写“指定版本与配置验收通过”。**

| 检查 | 最小动作 | 必须满足 |
|---|---|---|
| 完整读写 / 字节格式 | 已知数据 9 MiB 写读、copy-back 到真实 `<B` 目标；加一例普通 B view | 原对象字节完全一致；没有 BufferError；所有必要 rank 齐备 |
| 短读 / EFAULT | 用截断实验文件及可控读取失败 | 不置命中位、不拷回不完整数据；其他 key 继续；批次正常完成时通知仍产生 |
| 短写 | 注入 write 返回一半，使用独立实验 key | 不 rename、不报告完整写成功；正式路径无截断文件 |
| 取消 | worker 开始后先阻塞，取消等待 coroutine，再放行 worker | CancelledError 传播；worker 不访问原目标；mmap 只由 worker 在结束后关闭；目标未晚写 |
| 关闭 / 资源释放 | 有在途读写时执行既有 close/cleanup，等待线程退出或完成 | 没有释放后访问、永久等待、持续增长的 staging/线程；controller reservation 最终清理 |
| buffered 不受影响 | 同一输入 `use_odirect=false`，比较路径与字节结果 | 不走新增 staging/bytes 快照；原有结果与失败处理保持 |
| 冷启动与真实复用 | 两轮无热身 L1 空/L2 有 + 一轮 L2 缺失对照 | 首请求有界结束、输出正确、实际 prefill/recompute 按命中范围减少；不能用文件增量替代 |

保留现有 close/取消协议不等于已经证明它完整：公开 FS close 会 cancel 协程，而不等价于等待所有 executor 任务退出。候选避免 worker 持有原目标，但 controller 的取消终态和关闭顺序仍必须从现场实现验证。若此项失败，按真实卡点单独修 cleanup，不在 finally 里伪造成功或手工 free。
