## 3. 问题与定位过程

### 3.1 写侧

1. 连续发送 3 条约 2400 字的 prompt。
2. HTTP 请求返回正常，但 L2 文件数为 0。
3. 日志出现 `Failed to O_DIRECT write` 和 `OSError: [Errno 14] Bad address`。
4. 用 `lmcache.__file__` 确认进程实际加载 `/workspace/LMCache/...` 的代码。
5. 定位到 `_execute_store` 中的 `buf = obj.byte_array`，之后通过线程池异步写入。
6. 原文推断：借用视图不持有底层内存，对象在 I/O 结束前被释放或内存池复用，构成 UAF。

写侧补丁原意：

```diff
- buf = obj.byte_array
+ buf = bytes(obj.byte_array)
```

原文解释：给异步写入提供独立拥有的副本。

原文报告修改后产生 28 个 9 MiB 文件，无相关错误和降级警告。

### 3.2 读侧

写补丁生效后，重启 LMCache server 与 vLLM，保留磁盘文件、清空进程内 L1，再发送相同前缀请求。

原文记录：

```text
Failed to O_DIRECT read ...
OSError: [Errno 14] Bad address
Incomplete O_DIRECT read ... expected 9437184, got 0
```

随后推理退回完整 prefill；文件仍存在，因此 store 的 `exists()` 分支跳过再次写入，文件增量为 0。原文指出：**文件不增加既可能是缓存命中，也可能是读失败后写入被跳过**。

原文把读侧也归因于借用视图跨线程导致的 UAF，提出以下结构。照片里的省略部分保持原样，并非可直接应用的完整 diff：

```python
for i, key in enumerate(keys):
    file_path = self._key_to_path(key)
    _obj = objects[i]
    _obj.pin()
    try:
        dst_buf = _obj.byte_array
        expected = len(dst_buf)
        num_read = None
        # 原有 O_DIRECT / buffered 分支保留
        # ...
    except FileNotFoundError:
        continue
    except Exception:
        logger.exception("FSL2Adapter failed to load %s", file_path)
    finally:
        _obj.unpin()
```

原文选择 `pin()` 而没有对读目标简单 `bytes()` 拷贝，因为只把数据读到副本、却不拷回原对象，推理端拿不到加载结果。

原文支持 pin 的依据是 `memory_management.py` 中的释放条件：`ref_count == 0` 且 `pin_count == 0`。

原文给出的成功日志为：

```text
Prefetch request completed (L1+L2): 28/28 retained keys
(28 L1, 0 L2) in 4.6 ms
Retrieved 1792 tokens in 0.043 seconds
```

**此处按照片保留 `28 L1, 0 L2`，不将其改写成 28 个 L2 命中。该证据的矛盾是本轮审查重点。**

## 4. 原文验证流程与判据

### 4.1 启动配置要点

原文启动前先停止旧的实验进程，并在写侧实验中清空实验缓存目录。以下保留关键配置，避免把原文的广泛杀进程、清目录命令包装为可直接复制的安全操作：

```bash
export LMCACHE_CHUNK_SIZE=256
export LMCACHE_MP_TRANSFER_MODE=engine_driven

lmcache server --l1-size-gb 100 --eviction-policy LRU \
  --supported-transfer-mode auto \
  --l2-adapter '{"type":"fs","base_path":"/mnt/gmem/l2cache","relative_tmp_dir":".tmp","use_odirect":true}'
```

vLLM 侧关键参数：

```bash
export ASCEND_RT_VISIBLE_DEVICES=4,5,6,7
vllm serve /mnt/gmem/models/Qwen3-8B \
  --served-model-name Qwen3-8B \
  --gpu-memory-utilization 0.92 --trust-remote-code \
  --tensor-parallel-size 4 --max-num-seqs 32 \
  --max-num-batched-tokens 32768 \
  --host 0.0.0.0 --port 8000 --no-enable-prefix-caching \
  --additional-config '{"enable_cpu_binding":false}' \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both"}'
```

原文要求每次重启后先发送短请求“你好”热身，以避开首个 load 请求挂住的问题。

### 4.2 四组用例

| 用例 | 操作 | 原文期望 |
|---|---|---|
| 写复现 | 不打补丁；重复构造长 prompt，发送 3 次 | 文件数 0，有写错误和 Bad address |
| 写回归 | 打写补丁；重复相同用例 | 示例 28 文件，每个 9 MiB，无写错误和降级日志 |
| 读复现 | 写补丁已打、读补丁未打；先保存前缀，再重启清 L1、保留 L2，热身后读相同前缀 | 有读失败或 incomplete read |
| 读回归 | 再打读补丁；重复上述读请求 | 无读错误，有 retained 与 Retrieved 日志，请求正常返回 |

照片中的读复现示例用一段关于缓存复用的中文重复 120 次创建约 8 KB 前缀。写复现则使用另一段 `O_DIRECT复现测试。` 重复 400 次。因此，执行读验证前需要单独确认**读测试的实际前缀已经完成预填充并落盘**，不能直接假定写复现生成的文件属于它。

### 4.3 原文认为必要的证据

- 实验缓存最终文件数与请求产生的对象数相符。
- 文件大小符合预期，本案例为 9,437,184 bytes。
- 无 `Failed to O_DIRECT write`、`Bad address`。
- 无 `Cannot use O_DIRECT` 警告。
- 读侧无 `Failed to O_DIRECT read` 或 `Incomplete O_DIRECT read`。
- 有 `Prefetch request completed` 与 `Retrieved ... tokens`。
- HTTP 成功但磁盘文件不增加且有错误日志，应视为缓存失败。

原文特别提醒：

- 小 prompt 的 TTFT 接近，不能单凭耗时判断命中。
- 文件增量为 0 不能单独判断命中。
- 在同一进程中删除 L2 文件，可能仍命中 L1；必要时重启清 L1 后再做负向实验。

## 6. 原文遗留问题

### 6.1 冷启动首个 load 请求卡住

原文观察：

- 重启 server + vLLM 后，第一个触发 L2 load 的请求可能长时间挂住。
- 客户端超时，curl 退出码 28。
- 第二个短请求热身后，再次请求正常，较大命中请求约 0.4–2 秒。
- 同期日志可能有 `Session ... has no lookup ipc key, skipping touch`，以及 affinity key 在后续请求才绑定的日志。
- 另见 session 清理、session not found。

原文推断为首次请求触发 IPC 注册、又等待该注册完成的“自举死锁”；列为待查，临时用短请求热身绕过。

待查点包括：注册时序、lookup key 创建、router、session 生命周期、TP=4 并发、`engine_driven` 和禁用 APC 的影响。

### 6.2 AffinityThreadPool 只有一个 worker

原文记录只有 1 个 worker slot，4 个 affinity key 共享线程，store/load 因而可能串行。

原文称“当前单实例验证不受影响”，并建议检查 worker 数配置、默认值和多实例扩容。

### 6.3 store 完成日志位置

vLLM 日志搜不到 `Stored`，但 LMCache server 的 `engine_driven_transfer.py` 中能看到，例如 `Stored 512 tokens in 0.203 seconds`。

原文认为这是日志位置或级别问题；需要同步确认两侧日志用途。
