# LMCache-Ascend SSD / O_DIRECT：技术审查与公开问题核对

审查日期：2026-10-10。输入为 10 张文档照片。原文整理见 [01_原文整理.md](01_原文整理.md)，落地方案见 [03_修复方案与实验计划.md](03_修复方案与实验计划.md)。

## 1. 审查结论

**不建议按原文的 `bytes() + pin/unpin` 两处修改直接合入，并宣称“O_DIRECT 读写 UAF 已修复”。**

原文完成了有价值的定位：把“推理 HTTP 成功”与“SSD 缓存工作”分开，识别了文件存在导致的假象，定位了 FS adapter 的实际加载文件，也做了重启后尝试读取。问题在于，它从错误消失直接跳到了根因与修复完成，中间缺少对齐、内存类型、生命周期责任与真实 L2 命中的验证。

| 用户关注的问题 | 本轮判断 |
|---|---|
| 问题是否存在？ | 原文的读写错误、缓存失效表现可信；网络已有高度相似的 FS L2 失效记录 |
| 已证明两个 UAF 吗？ | 没有。缺少提前释放时序证据，还存在对齐和特殊内存映射两类解释 |
| 写侧 `bytes()` 改得对吗？ | 作为定位实验有价值；作为 O_DIRECT 最终补丁不成立，因为不保证对齐，也不能修复复制前已释放 |
| 读侧 `pin/unpin` 改得对吗？ | 只可能覆盖部分释放路径；没有覆盖队列等待、MP 直接回收、取消与关闭路径 |
| 原有验证够吗？ | 不够。最关键的日志明确为 `28 L1, 0 L2`；没有数据逐字节回环、真实直通与无热身冷启动验收 |
| 能尽量只改 Ascend 仓库吗？ | 能。优先现有 MP L2 插件扩展或在 Ascend 构建中应用小补丁；调用方生命周期缺陷必要时仍需对依赖行为做局部修补 |

## 3. 关键发现

### F1 · P1：`EFAULT` 与 borrowed view 不足以证明 UAF

`TensorMemoryObj.byte_array` 使用 ctypes 从地址创建视图，该视图确实不拥有底层池内存。但“视图不拥有内存”只说明必须由其他对象或协议保证生命周期，不能证明此协议已经失效。

公开 L2 接口明确把内存生命周期交给调用方。StoreController 在提交前取得 L1 read reservation，在完成结果返回后释放。PrefetchController 为 load 预留写对象，收集结果后再转成可读状态。需要检查的是：**现场 fork 是否提前结束了这些 reservation，或者超时、清理、直接 free 绕过了它们**。[L2 接口](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/distributed/l2_adapters/base.py#L84-L104)，[StoreController](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/distributed/storage_controllers/store_controller.py#L599-L671)。

应并列保留以下假设：

| 假设 | 可观察特征 | 最有区分力的实验 |
|---|---|---|
| H1：实际地址 / 长度 / offset 未对齐 | 常见为 `EINVAL`；同一配置可能受分配器历史影响 | 记录真实指针与 DIO 对齐要求；普通对齐内存作对照 |
| H2：ACL host 映射不满足内核 direct I/O 的取页条件 | 对象持续存活仍 `EFAULT`；普通匿名内存成功 | 单线程强保活，ACL 内存直读写对比普通对齐 mmap |
| H3：内存提前回收或重用 | I/O 未结束时出现 free、invalidate、地址复用；也可能没有报错而直接读写错误数据 | 人为延长 I/O、施加池压力，记录 reserve/free/complete 时序 |
| H4：文件系统、内核或运行路径与假定不同 | 应用没输出降级警告，实际却未走所需 I/O 路径 | 指定 fd 与路径的系统调用证据、挂载和内核信息 |

Linux 6.6 的 GUP `check_vma_flags()` 对带 `VM_IO` / `VM_PFNMAP` 的映射直接返回 `-EFAULT`。这是“有效用户态地址也可能不适合 direct I/O”的明确反例；**它并不证明现场 `aclrtMallocHost` 必然具有这些标志**，必须检查该设备、CANN 与驱动版本的实际映射。[Linux 内核源码](https://github.com/torvalds/linux/blob/v6.6/mm/gup.c#L969-L977)。

另外，内存池回收通常只是把区间交回池，不一定解除虚拟地址映射。地址仍可访问时，UAF 更可能表现为错误内容，而不是必然产生 `EFAULT`。因此错误码不能代替数据正确性实验。

### F2 · P1：写侧 `bytes()` 副本不保证 O_DIRECT 地址对齐

原文修改后，实际系统调用直接收到 Python bytes。现有 `_execute_store` 只检查长度整除 `_os_disk_bs`，没有检查指针；`_write_with_odirect` 直接执行 `os.write(fd, buf)`。

O_DIRECT 的内存地址、长度和文件偏移限制依文件系统与内核而异。Linux 6.1 起可在支持的文件系统上通过 `statx(..., STATX_DIOALIGN)` 查询；`statvfs.f_bsize` 不能当作所有文件的精确 DIO 契约。[Linux open(2)](https://man7.org/linux/man-pages/man2/open.2.html)。

`bytes()` 同时改变了三个变量：所有权、地址、内存来源。复制后成功，可能是避开了原内存映射，也可能是改变了时序；不能据此单独归因于 UAF。

本机 CPython 3.10.11 的 4 个 9 MiB 副本，地址对 512 和 4096 的余数均为 96。这个反例仅证明 bytes 没有相应对齐保证，不证明 Linux 现场一定返回同一个错误。实测结果见 [host_probe_results.json](research/host_probe_results.json)。

**建议**：若采用复制方案，用经过验证的普通对齐 host staging buffer；写前复制进去，读后复制回来。若只是生命周期缺陷，应先修正确的 reservation，而不是无条件增加大块复制。

### F3 · P1：读侧 pin/unpin 不能作为完整保活方案

原文的局部 pin 有四个需要补齐的边界：

1. **开始太晚**：到 `_execute_load` 循环执行时才 pin，未保护从调用方提交到协程真正开始的等待窗口，也没有保护后续尚未轮到的对象。若调用方本来有完整 reservation，则这些 pin 可能是重复保护。
2. **实际释放不只走 ref_count_down**：MP `L1MemoryManager.free()` 会调用 allocator 的 `batched_free()`；公开 `TensorMemoryAllocator.free/batched_free` 不以 `pin_count` 为释放前提。只看 `memory_management.py` 那一处条件，不足以覆盖 MP 路径。[L1 manager](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/distributed/memory_manager/l1_memory_manager.py)，[Tensor allocator](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/memory_allocators/tensor_memory_allocator.py#L178-L250)。
3. **取消不等于线程完成**：等待 executor 的协程被取消后会执行 finally，但已经运行的线程任务一般仍继续。此时先 unpin，再由线程写目标内存，仍有风险。[Python executor 文档](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Future.cancel)。
4. **pin 不是 OS 内存注册**：此处 pin 修改对象管理计数；不会把一个不兼容 GUP 的 ACL 映射自动变为普通匿名内存，也不会修正地址对齐。

本机取消实验确实得到：`pin → unpin → caller_cancelled → worker_finished`。这验证了原补丁的通用取消漏洞，不代表已经证明现场服务会在正常请求中触发该路径。

正确责任应是：**从异步提交前到实际 worker 完成、load copy-back 完成，再到完成事件对外发布，内存都不能被回收或重用**。既有 controller reservation 能满足时应复用；不能满足时修提交/完成边界。仅持有 Python 对象引用也不能阻止显式 allocator free。

### F4 · P1：`28 L1, 0 L2` 与“SSD 读回已证明”不相容

照片成功日志明确标注 28 个 L1、0 个 L2。按字面，它证明这次统计从 L1 获得对象，而非这次从磁盘加载。

可能的解释包括：

- 摘录的是第二次请求，第一次失败/超时请求已经把数据预取到 L1。
- 热身或自动流程预先装入了相关数据。
- 实际没有重启持有 L1 的 server。
- fork 的日志是在 promotion 之后计数，而非记录命中来源。

最后一种需要对应 fork 代码证明，不能直接假定。也不能反过来断言磁盘一定没有读过。

`Retrieved 1792 tokens` 位于传输层，可能只是 L1 → NPU 的传输结果；HTTP 200 更不能证明缓存成功。验收要关联同一请求的 L1 初始 miss、L2 load task、文件 read/readv 字节数、copy-back 完成、NPU 实际复用和减少的 prefill。[Engine-driven transfer](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/multiprocess/modules/engine_driven_transfer.py)。

### F5 · P1：当前写函数可能把短写当作成功

公开 `_write_with_odirect` 丢弃 `os.write` 的返回值，外层在 helper 正常返回后就 rename 并报告写入预期字节数。若系统调用只写了部分数据，可能发布截断文件；之后 `exists()` 又使重写跳过。

本轮直接抽取公开版本的原 helper，注入“请求 4096，返回 2048”的写结果，helper 仍正常返回、没有异常。这是故障注入验证，不是真实磁盘短写复现。[FS 源码](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/distributed/l2_adapters/fs_l2_adapter.py#L575-L647)。

该问题也已被上游 [#4364](https://github.com/LMCache/LMCache/issues/4364) 指出。建议作为本次 SSD 正确性修复的一部分：完整写入并检查字节数后才发布；重试剩余数据时仍需满足 DIO 对齐。无法安全续写则失败，不可当作成功。临时文件应避免旧尾部残留，并防止并发同 key 写共享同一 tmp 文件。

### F6 · P1：冷启动问题不能用热身代替验收

原文发现首个请求挂住，这是独立的可用性缺陷。短请求热身可以帮助定位初始化差异，但不能把这条用例标为通过。

`Session ... has no lookup ipc key, skipping touch` 在公开版本中来自 **`LookupModule.end_session()` 的结束清理 / LRU touch 分支**，不是“建立 IPC 通道失败”的直接报错。这里的 lookup IPC key 是会话中保存的请求键元数据，不能仅凭名称解释成尚未建立的 OS IPC 连接。[对应源码](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/multiprocess/modules/lookup.py#L511-L546)。

小于一个完整 chunk、提前退出等路径可以没有有效的 lookup 工作。需要按 request ID 排除热身请求和结束清理日志混入，而不是把这条 warning 本身当作死锁根因。

本轮找到更具体的已知缺陷：scheduler 初始化 `_heartbeats = {}`，但 `_ensure_heartbeat_started()` 用 `is not None` 判断已启动，导致空字典时直接退出。该代码形态在公开 `v0.5.5rc7` 可见，相关 PR [#4764](https://github.com/LMCache/LMCache/pull/4764) 当前仍未合并。**应检查 fork 是否也保留这两处 guard，但修它并不等于已经解释“第二次请求解锁第一次”。**

### F7 · P2：验证命令和指标有误导点

| 原文判据 / 表述 | 校正 |
|---|---|
| `curl time_starttransfer` 称为 TTFT | 这是收到首个响应字节的时间。非 streaming chat 响应可能在生成完成才返回；应解析首个有效生成 token 事件 |
| “首请求永久挂起”同时用 30/60 秒 curl 超时判断 | 客户端超时只能证明观测窗口内没完成；应记录 server 内部 pending 状态、请求实际结局和超时边界 |
| 用 `find ... -type f` 统计文件 | 会包括 `.tmp` 内临时文件；仅统计该 adapter 的最终 key 文件，并排除旧文件 |
| 看最大几个文件均为 9 MiB | 不能证明其他文件完整；针对本轮预期 key 集合检查大小 |
| 3 次 prompt 预期必定产生 28 文件 | 文件数受 tokenizer、前缀共享、尾块保存、rank/key 布局影响；28 是案例值 |
| 文件数量不增加就认为静默失败 | 相同 key 去重时应不增加；必须结合本轮 key、错误与传输结果 |
| 没有 `Cannot use O_DIRECT` 就是真直通 | 只能证明没进入该应用降级分支；还需系统调用及目标文件系统证据 |
| overlay 文件系统上必定不能 O_DIRECT | 不是普遍成立；行为取决于内核、上层/下层文件系统与挂载方式 |
| 热身后重读成功就是冷启动通过 | 热身排除了最关键触发条件，应拆成独立用例 |

curl 的官方定义见 [CURLINFO_STARTTRANSFER_TIME](https://curl.se/libcurl/c/CURLINFO_STARTTRANSFER_TIME.html)。O_DIRECT 对齐及可能退回 buffered 的行为见 [open(2)](https://man7.org/linux/man-pages/man2/open.2.html)。

文件大小本身可以合理解释。按 Qwen3-8B 官方配置、BF16 KV、TP=4 且没有额外布局开销估算：

```text
每 rank 每 chunk KV bytes
= 36 layers × 2(K,V) × 256 tokens × (8 KV heads / 4 ranks)
  × 128 head_dim × 2 bytes
= 9,437,184 bytes = 9 MiB

1792 / 256 = 7 chunks
7 chunks × 4 rank files = 28 files
```

这说明数字在该布局假设下自洽，但文件数要结合真实 key 布局确认，不能跨模型或不同 dtype 复用。[Qwen 官方配置](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)。

### F8 · P2：TP rank、推理实例和两类线程池不能混为一谈

TP=4 通常是一个推理实例中的 4 个 rank，不等于 4 个独立服务实例。照片显示 4 个 affinity key，需要追踪 key 具体取自 worker 还是实例标识。

AffinityThreadPool 按 key 固定线程，相同线程内 FIFO 串行；FS adapter 自己又有循环逐个等待文件 I/O 的串行点。增加前者 worker 数并不自动消除后者串行。[Affinity 实现](https://github.com/LMCache/LMCache/blob/v0.5.5rc7/lmcache/v1/multiprocess/affinity_pool.py)，[FS 批内串行 issue](https://github.com/LMCache/LMCache/issues/4365)。

当前文档公开配置有 `--max-workers`、`--max-gpu-workers`、`--max-cpu-workers`；目标旧环境需用实际 `--help` 确认。建议正确性通过后对目标队列做 1 与 4 worker 的小规模 A/B，不能仅根据 TP 值机械设置，更不能称当前单实例必定无影响。[配置说明](https://docs.lmcache.ai/mp/configuration.html)。

## 6. 对原文结论的建议替换

原结论“读写各有一个 UAF，owned copy + pin 已修复”建议替换为：

> 已在指定实验环境观察到 FS L2 O_DIRECT 读写 EFAULT，且更改写入缓冲区和读侧 pin 后，错误日志减少并出现文件及取回记录。现有证据尚不能区分内存生命周期、实际地址对齐与 Ascend host 映射兼容性。写侧普通 bytes 缺乏 DIO 对齐保证，读侧局部 pin 未覆盖完整异步生命周期。补丁暂不作为正式修复验收通过；下一步用强保活内存对照、L2-only 回环和无热身冷启动实验确定最终修改。

这保留了原作者的实验进展，也避免把未经证明的根因固化到 PR、运维文档与后续排障中。
