# KS最少用例实验操作指南

零基础版 从证明缓存链路到确认具体根因

本指南用三个固定逻辑用例和一个按结果触发的修正闭环，确认KS问题的真实数据路径、性能现象和具体原因。仅当需要进一步证明“PP布局使池化收益变差”，才补四象限；不从一开始穷举模型、并发、命中率和并行组合。

“最少用例”不等于“每组只发一次请求”。前面的小样本用来找明显断点，只有需要判断性能差异时才增加重复与样本。本指南中的阈值和示例负载均为实验起点，不是客户已测结果。

## 阅读和执行顺序

1. 先读“入门基础”，看懂一条请求如何经过P、缓存和D；不用先读源码。
2. 读实验总表与准备步骤，和环境维护者一起填好地址、模型名、版本与配置。Linux命令在昇腾测试容器中执行；当前Windows电脑用于阅读、生成文件和整理结果。
3. 先做M1。若输出错误、分片缺失或传输失败，直接走对应M4，不再做大规模性能测试。
4. M1通过后做M2、M3；按决策表选一个追加验证。原始日志、输入清单和测量数据要一同保留。
5. 用结论模板填写证据。没有采到的指标填写NA和原因，不能填0或“通过”。

**环境默认：**详细流程以可使用客户原2P1D隔离测试环境为目标。只有单机时可做局部链路和小模型验证；没有昇腾环境时可准备数据、配置对照和表格，不能产生客户性能结论。本指南不假设未知的启动脚本、硬件容量或通用池化开关存在。

**零基础分工：**你可以负责运行已确认的客户端命令、保留文件、填写结果和按表判读；首次部署、切换connector、确认PP分层及增加源码计时，需要熟悉现场的人共同完成。命令中的中文占位值必须替换，截图里的旧镜像和参数不要直接套到未知服务器上。

## 基础1 先看一条请求：模型到底在做什么

### 基础1 1 请求、提示词与 token

把模型服务想成一家收到问题、阅读资料、逐字组织回答的工厂。一次用户提问及其上下文，就是一次“请求”。请求通常包含系统提示、历史对话、本轮问题和生成参数。

模型不会直接以“汉字个数”计量文本。它先用分词器把文本转换为一串编号，每个编号对应一个 token。token 可能是一段词、一个字符或其他文本片段，具体由分词器决定。因此“输入 4,096 token”不能直接改写为“输入 4,096 个汉字”。

模型权重是训练得到的参数，可以理解为工厂长期使用的设备与规则；输入文本是这一次订单的资料。推理是使用这些权重计算答案，通常不会在回答过程中重新训练模型。量化则是以较低精度表示权重或部分计算数据，目的是减少占用或改善执行效率；不同量化配置必须作为不同测试条件记录。

本次问题研究的是同一套模型在服务时如何保存、复用和传输中间计算结果，不是训练模型，也不是改变模型知道的知识。

### 基础1 2 prefill 与 decode：先阅读，再继续生成

一次常见的自回归生成包含两个阶段：

| 阶段 | 类比 | 实际工作 | 本次要观察什么 |
|---|---|---|---|
| prefill，预填充，简称 P | 先阅读收到的整份资料 | 对输入 token 计算各层状态，并形成后续生成需要的 KV | 是否真的少算了输入；是否在加载或保存缓存时等待 |
| decode，解码，简称 D | 根据已经读到和写出的内容继续回答 | 逐步生成新的 token，持续使用并扩展 KV | 首字后生成是否变慢；是否等待 P 侧移交 KV |

prefill 常有较强的计算需求；decode 常受数据访问与调度效率影响。这是理解方向，不是所有模型、批量和硬件下都成立的绝对判断。判断客户瓶颈仍要依靠测量。

“第一个 token 很晚出现”和“第一个 token 后输出很慢”是不同问题。前者需要看排队、prefill、缓存读取、P→D 交接等环节；后者还需要看 decode 执行、批量与请求间竞争。

## 基础2 KV Cache：缓存了什么，为什么能省计算

### 基础2 1 KV 不是已生成的答案

在注意力计算中，模型会用到 Key 和 Value，简称 K、V。KV Cache 是把这些中间状态保存下来，让后续计算复用。类比读长资料时做的“可继续使用的阅读笔记”，它既不是原文的简单副本，也不是问答结果的数据库。

不使用已保存的 KV 时，一些相同上下文需要重新计算；正确复用 KV 后，可以减少重复工作。模型仍需要完成新输入部分和后续生成，所以“缓存命中”不等于“不再进行推理”。

普通注意力、MLA 等模型结构的缓存形状和占用可能不同。本问题不应凭通用的“每层 K/V”示意图计算实际传输字节；应读取当前模型实际 KV 张量和连接器的元数据。

### 基础2 2 前缀复用：相同的开头才构成复用机会

例如两条请求分别是“共同背景资料 + 问题甲”和“同一背景资料 + 问题乙”。两者开头的 token 序列相同，就可能复用共同背景的 KV。判断还需要模型、tokenizer、缓存键、位置和相应运行配置匹配，不能只凭肉眼认为两段话意思相同。

“两段文字语义相近”不等于“可以直接复用同一份 KV”。相同文字放到不同上下文位置，也不能无条件视为同一个可复用前缀。

实验必须区分三件事：输入中有多少理论可复用的 token；缓存系统查到了多少；最终真正省去了多少 prefill 计算。只有最后一项直接连接到计算收益。

### 基础2 3 block 与 chunk：两种分块单位不能混写

缓存通常分块管理，好比书按页存放，避免每次申请一大片连续空间。

| 名称 | 定义与用途 | 注意事项 |
|---|---|---|
| KV block，KV 块 | 推理引擎管理 KV 的基本块；存在逻辑块与实际内存块的映射 | block 大小及内存布局由当前引擎配置决定 |
| chunk，缓存片段 | 外部缓存引擎进行索引、保存或加载的一段 token 对应的数据 | chunk 不一定等于一个 vLLM block；不能默认两者数量相同 |
| shape / stride | 张量的各维大小 / 沿各维移动时跨越的内存距离 | 数据量对了，步长或布局错了，仍可能读写错误 |
| cache key | 用于识别缓存对象的键 | 可能包含模型、token、rank、PP 阶段等维度，具体按实现核对 |

例如请求有可复用前缀，但长度未覆盖完整缓存块，实际可复用 token 可能少于文字上相同的部分。实验中的目标复用比例只是输入设计，实际有效比例必须另测。

## 基础3 数据放在哪里：NPU、HBM、主机内存与网络

把 NPU 视为执行模型计算的设备；HBM 是其附近的高速设备内存；Host 内存是主机 CPU 使用的内存；SSD 是持久存储。把 KV 从设备内存搬到 Host 或其他节点，可以扩大可保存的范围，但搬回时也需要时间。

| 位置或动作 | 直观解释 | 与 KS 实验的关系 |
|---|---|---|
| NPU | 执行张量计算的加速设备 | 要知道哪些设备负责哪个并行阶段 |
| HBM | NPU 使用的高速设备内存 | 模型权重、KV、工作空间等都会占用它 |
| Host / CPU 内存 | 主机内存，常称 DDR | 本地卸载缓存可能放在这里，并不等于共享池已开启 |
| SSD | 比内存更持久的存储层 | 容量、读写和缓存策略会改变端到端行为 |
| D2H / H2D / D2D | Device→Host / Host→Device / Device→Device | 分别记录设备到主机、主机到设备、设备之间的数据移动 |
| 内存注册 | 将一段内存及其范围交给传输系统识别和访问 | 注册地址或长度不匹配可能引发传输失败 |

“卡”“芯片”“进程”不是同一个计数单位。有的硬件一张物理卡含多个计算芯片；一个服务又会启动多个工作进程。不要把截图中的“16 个芯片”写成“16 张物理卡”。现场应分别记录物理节点、卡、可见设备和 worker 数量。

带宽描述单位时间能够传送多少数据；时延描述一次操作需要等多久。大块传输可能更受带宽影响，大量小块操作可能更受调用和同步时延影响。因此不能仅凭总字节数判断某个路径一定快或慢。

## 基础4 多个设备如何合作：先分清 PP、TP、DP 和 PD

### 基础4 1 PP：把不同层交给不同阶段

PP 全称 Pipeline Parallelism，流水线并行。可以类比一条生产线：第一站处理前面一组工序，第二站处理后面一组工序。模型的不同层被分配到不同 stage（阶段），请求依次经过这些阶段。

PP2 表示两个流水线阶段，不是两个 prefill 副本。某个阶段通常保存自己负责层的 KV。因此一条请求的 KV 可以分散在多个阶段上，但不要求外部缓存一定先把它们拼成“全模型一大块”。系统也可以分别记录和传输阶段片段。

一个阶段慢了，后续阶段可能等待；等待造成的空闲常称“流水线气泡”。PP 可以让模型分布到更多设备上，也可能改善适合的服务负载，但不是把阶段数翻倍就保证时延减半。

### 基础4 2 TP、DP 与 EP：分别切计算、复制服务、分配专家

| 方式 | 类比 | 精确定义 | 不应混同 |
|---|---|---|---|
| TP，张量并行 | 多个工人合做同一道工序 | 将某些层内部的张量计算分给多个设备，并进行必要通信 | 不是复制完整模型服务 |
| PP，流水线并行 | 不同工位负责不同工序 | 不同设备或设备组负责不同模型层区间 | 不是 prefill/decode 分离 |
| DP，数据并行 | 多条服务线接不同订单 | 多个模型副本处理不同请求或批次 | 增减 DP 会改变副本数和排队行为 |
| EP，专家并行 | 按任务送到相应专家工位 | 在 MoE 模型中把专家计算分配到不同设备 | 是否可组合及如何通信依赖模型和版本 |

例如把 DP2、TP8 改成 DP1、TP8、PP2，虽然总设备数可能不变，但同时减少了副本数、增加了流水线阶段。这是在比较两个部署方案，不能把所有差值都归因于“PP 开关”。

### 基础4 3 rank 与 group：编号一定要说明属于哪个范围

rank 是一个参与分布式计算的进程在某个通信范围内的编号。global rank 是全局编号，TP rank 是 TP 组内编号，PP rank 是所在流水线阶段的编号。group 是参加某类协作的进程集合。

用一个简化示例理解：PP2、TP2 可以由 4 个 worker 组成。第一个 PP 阶段有 2 个 TP worker；第二个 PP 阶段也有 2 个 TP worker。两个 TP 组都可以各自有一个“组内 rank 0”，但全局 rank 0 只有一个。具体编号与映射要以运行日志为准。

这正是最终分析报告中 first-rank 风险的关键：**“全局第一个 worker”与“每个 TP 组的第一个 worker”不是同一个集合。** 不能看到 first_rank 这个名字就认定每个 PP 阶段都有人保存缓存，也不能只凭这个名字断定必然丢缓存；需要把实际编号、保存者和广播范围列出来。

### 基础4 4 PD 分离与 2P1D：这是服务角色，不是模型切层

PD 分离把 prefill 和 decode 交给不同服务组。P 侧算完本次请求的输入后，需要将相应 KV 交给 D 侧，D 侧才能继续生成。

2P1D 表示两组 P 服务和一组 D 服务。它描述服务分工与副本安排；每一组内部还可以有自己的 TP、PP 等配置。两个 P 副本不是两个 PP stage。

一条简化的请求路线是：

`用户请求 → proxy 选择 P1 或 P2 → P 侧 prefill → P→D KV 交接 → D 侧生成 → 用户收到答案`

proxy 是入口路由组件。KVC 亲和是尽量把请求分给已经持有合适 KV 的实例，以减少重算或搬运；但过度集中路由也可能让某个 P 排队更久。因此高命中率与低时延未必同时出现。

## 基础5 “缓存开启”到底开启了什么

### 基础5 1 必须分开的四条路径

| 路径 | 缓存在哪里、谁复用 | 主要收益 | 不能据此声称 |
|---|---|---|---|
| 本地 APC，自动前缀缓存 | 当前模型实例复用自己已有的前缀 KV | 减少相同前缀的重复 prefill | 其他实例已成功从共享池读取 |
| 本地 CPU/SSD 卸载 | 当前实例将 KV 放到设备之外，再按需加载 | 增加可保存范围，可能降低设备内存压力 | 已开启跨实例或跨机器共享 |
| 外部共享缓存池 | 多个实例经外部存储与传输系统复用 KV | 使一个实例计算的结果可被其他实例利用 | 必须把全模型所有层作为一个不可分割对象 |
| P→D KV 传输 | 为同一次请求把 P 侧结果交给 D 侧 | 让 PD 分离的服务完成生成 | 已发生跨请求的前缀复用 |

一套系统可能同时使用四条路径。客户说“池化开启”时，必须找到对应的实际配置和数据流，不能只按名称猜测。

### 基础5 2 为什么“关池化”不能顺手关掉 P→D 传输

在 PD 分离部署中，P→D 交接是请求正确执行所需的路径。如果为了测试共享池收益把它一起关掉，服务可能无法完成同一种任务。这个对照回答不了“共享复用是否导致劣化”。

正确的第一步是确认两个能力是否有独立开关。测试共享复用时，模型、并行布局、路由和必要的 P→D 交接保持不变。若现场配置把两者绑定，应先说明无法直接进行单变量对照，而不是把启动失败当成性能下降。

### 基础5 3 冷缓存与暖缓存：必须说明冷暖的是哪一层

冷缓存指目标内容尚未在被测缓存中形成可用条目；暖缓存指事先已准备好目标内容。不能只说“已经预热”，还要写明本地 APC、CPU 缓存、外部共享池各自的状态。

验证跨实例共享的一种典型思路是：让 P1 先产生并成功发布某个前缀的 KV，再让 P2 处理带同一前缀的请求；同时确保 P2 本地没有这份 KV，并从日志确认读取来自外部池。若两次请求都落在 P1，只能证明某种缓存可能有效，不能单独证明跨实例共享已走通。

这里的清理与预热应使用受控测试命名空间、明确的缓存接口或隔离实例，不能为了制造“冷缓存”而随意删除现场公共数据。

## 基础6 软件组件地图：谁计算，谁管理，谁搬运

把服务理解为多层协作，能避免把不同软件的限制混成一个根因。

| 组件 | 在本问题中的职责 | 应保留的边界 |
|---|---|---|
| vLLM | 模型服务、请求调度与 KV 管理等推理框架能力 | 同名配置在不同版本中的行为可能变化 |
| vllm-ascend | vLLM 的昇腾适配实现与相关集成 | 具体模型、connector 和并行模式的支持需逐项确认 |
| connector，连接器 | 将推理框架的 KV 生命周期接到外部存储或传输实现 | “能加载连接器”只证明入口存在，不证明命中或性能 |
| AscendStoreConnector | 当前公开栈中的外部 KV Pool 接入路径之一 | 客户是否使用它，要看实际 kv_transfer_config |
| MooncakeConnectorV1 | 当前公开栈中的 P→D 传输路径之一 | 不能仅凭 Mooncake 名称认定它与 Store 的配置相同 |
| MultiConnector | 组合多个连接器的方式 | 必须辨认每个子连接器负责的方向和角色 |
| Mooncake Store | 提供缓存对象保存、查找和读取等存储侧能力 | 对象可以由上层按阶段分片组织 |
| Transfer Engine，传输引擎，简称 TE | 根据地址、目标区域和长度完成数据搬运 | 搬运成功不自动保证上层缓存语义正确 |
| HIXL | 本场景涉及的数据传输相关软件能力 | 实际调用路径、版本与内存模式均需确认 |
| fabric mem | 材料所述的一种内存访问/传输模式 | 是具体工程路径，不等同于全部 Mooncake 传输，也不是 PP 的别名 |
| LMCache / LMCache-Ascend | 另一条缓存引擎及其昇腾适配路线 | 其后端互斥或 first-rank 风险不能直接作为客户 Mooncake 根因 |

`use_layerwise` 表示某条实现是否以按层保存或加载的方式工作；PP 表示模型层如何分配到阶段。PP 阶段可以一次处理自己负责的多层 KV，因此 **PP 开启不自动要求 use_layerwise=true**。

源码中存在一个功能、公开文档称某路径支持 PP、现场正确加载并通过测试，是三种不同证据。当前代码的能力也不能倒推客户数周前的镜像已经具有相同能力。

## 基础7 缓存的一生：读路径之外，还要看写路径

### 基础7 1 写入端：计算完成不等于缓存已可复用

一段 KV 在 P 侧生成后，系统可能需要：准备待保存的数据和元信息 → PUT 写入 → 等待相关数据操作完成 → 使缓存条目对其他请求可见。实际实现可能合并或交错这些步骤，实验不能强行套用不存在的阶段名。

PUT 类比把书送到仓库。提交了“送书申请”不等于书已经到库，更不等于书目已经可检索。相应地，异步接口返回可能只代表任务已进入队列，不能把这时刻视为“缓存已经发布完成”。

异步保存可以与计算重叠，但后续要复用同一块缓冲区时，可能必须等待之前的保存结束。等待点可能出现在下一个调度步，因此“当前请求的 PUT 提交很快”不代表保存对整条流水线没有影响。

### 基础7 2 读取端：查到、取到、写对、少算是四件事

| 证据层次 | 最少要证明什么 | 只到这一层仍不能证明什么 |
|---|---|---|
| lookup，查找命中 | 索引说目标条目存在或有可复用 token | 数据尚未证明实际拿到 |
| GET / pull，读取完成 | 所需缓存分片成功读取 | 不证明所有 PP 阶段数据完整，也不证明写入位置正确 |
| writeback / scatter，写回完成 | 数据落入当前推理引擎所需的 KV 块与布局 | 不证明调度器真正跳过了相应计算 |
| effective reuse，有效复用 | 必要阶段齐全且相应 prefill 计算确实减少 | 不保证节省的计算大于查询、读写与同步成本 |

PP 场景中，一个阶段命中而另一个阶段缺少所需分片，不足以声称请求已经获得完整复用。具体完整性判断可能按阶段、cache group 或其他粒度聚合，必须以当前实现定义为准。

若读取失败，框架可能回退到本地重算。结果仍能正确生成，但付出了“失败搬运 + 重算”的额外代价。此时业务成功率可能很高，内部传输失败率却不为零，两者都需要记录。

### 基础7 3 关键路径：不能把所有耗时直接相加

假设计算需要 8 ms，缓存传输需要 5 ms。如果二者完全依次发生，该段耗时可能接近 13 ms；如果充分重叠，可能接近 8 ms；如果还有前置依赖或资源竞争，则又会不同。这些数字只是解释重叠关系。

关键路径是完成请求必须依次经过的最长依赖链。定位性能时要找到关键路径上实际增加的等待，而不只是寻找“累计耗时最多的函数”。多个 PP 阶段、多个请求和后台保存可以重叠，简单相加会把并行工作误算为用户等待。

## 基础8 怎样读实验结果：测试方法与指标基础

### 基础8 1 对照组、变量与用例

本指南把一个要回答的问题称为“逻辑用例”，它可以包含开与关等多个测试条件；一次运行是在一个条件下发送一批请求。重复运行用于估计自然波动。减少逻辑用例不等于只跑一次请求，必须同时报告条件数、运行轮数和请求数。

对照组是用于比较的基准条件；实验组只改变想研究的因素。若同时改镜像、TP、DP、PP、缓存引擎和数据集，虽然可能得到更好的分数，却很难知道是哪项改动起作用。

机制定位回答“为什么”；部署比较回答“这一整套配置是否更合适”。两者都合理，但结论不同。用户希望最少用例定位时，应先找同一现场配置里的异常，再只对这个异常做一项有针对性的改变，避免一开始穷举所有组合。

### 基础8 2 业务指标：用户究竟感受到什么

| 指标 | 定义与单位 | 读数注意事项 |
|---|---|---|
| 请求成功率 | 成功完成请求数 ÷ 发出请求数 | 说明超时、错误输出、取消是否算失败 |
| TTFT，首 token 时延 | 客户端发出请求到收到第一个输出 token 的时间，常用 ms | 包含客户端与服务链路可见的等待，不等于纯 prefill 计算 |
| E2E，端到端时延 | 请求发出到输出完成的总时间，常用 ms 或 s | 输入、输出长度不同会影响结果 |
| TPOT，每输出 token 平均时间 | 输出不少于 2 token 时，通常为 (E2E−TTFT) ÷ (输出 token 数−1) | 每请求计算还是对全体聚合，需要明确 |
| ITL，相邻输出间隔 | 流式输出中相邻 token 或事件之间的间隔 | 投机解码可能一批产生多个 token，不能无条件等同 TPOT |
| 输出吞吐 | 统计窗口内成功请求的输出 token 总量 ÷ 窗口时长，单位 tokens/s | 写明是否包含输入 token、失败请求，以及窗口范围 |
| 请求吞吐 | 完成请求数 ÷ 时间，单位 requests/s | 输入输出长度改变后，不可与 tokens/s 直接互换 |
| SLO，服务目标 | 事先约定的成功率、时延或吞吐要求 | “达标吞吐”需明确达到哪条时延和成功率条件 |

例如某请求 TTFT 为 0.5 s，E2E 为 2.5 s，输出 101 token，则按上述定义 TPOT 为 (2.5−0.5)÷100＝0.02 s，即 20 ms。这个平均值不能说明每一个 token 的间隔都等于 20 ms。

### 基础8 3 P50、P95、P99：平均值以外的等待

将一批请求的时延从小到大排列，P50 是中间位置附近的值；P99 是约 99% 样本不超过的值。P99 用于观察少数很慢的请求，通常称尾延迟。

P99 不是“最慢的 1% 的平均值”，也不是最大值。少量样本的 P99 容易被一两个请求支配。必须同时报告样本量，样本不足时不能凭 P99 的单个数字下稳定性结论。

### 基础8 4 到达率、并发与满载：压测工具如何发请求

开放式负载按计划到达率发请求，例如每秒 2 个；服务变慢时在途请求和队列可能增长。封闭式负载维持一定数量的并发请求，例如始终最多 8 个请求在处理，完成一个再发下一个。

QPS 常用于表示每秒请求数，但要分清“计划发送”“实际发送”和“成功完成”的口径。并发 8 不等于 QPS 8；工具里的 num-users 也不自动等于稳定并发。

低到达率适合观察单请求链路，却不一定能量出系统最大吞吐；高并发能暴露排队与资源竞争，却可能把缓存本身的代价和排队代价混在一起。因此初次定位通常先用少量请求确认正确性与路径，再在一个明确的业务负载点做性能对照。

### 基础8 5 缓存与传输指标：收益和成本要同时记录

| 指标 | 建议口径 | 为什么需要 |
|---|---|---|
| 理论可复用比例 | 设计为相同前缀的 token ÷ 总输入 token | 描述负载设计，不伪装成实际命中结果 |
| 外部逻辑命中率 | 由实际 lookup 返回定义，分别记录请求或 token 口径 | 检查索引发现了多少可用内容 |
| 有效外部复用率 | 归因于外部缓存且最终实际省去的 prefill token ÷ 该批总输入 token | 将外部收益与本地 APC 分开，不重复计数；明确块对齐等边界 |
| 传输失败率 | 失败传输次数 ÷ 传输尝试次数 | 必须说明重试按独立尝试还是一次逻辑操作统计 |
| 回退率 | 发生缓存失败重算的请求数 ÷ 相关请求总数 | 解释服务成功但性能变差的情况 |
| GET / PUT 字节数与次数 | 每请求、每阶段及整轮分别统计 | 区分读写成本、碎片化和重复传输 |
| 保存等待 / 读取等待 | 在确定事件边界之间测量的时长 | 关注关键路径上没有被其他计算隐藏的部分 |
| HBM / Host 峰值 | 相应资源的最大占用及采样频率 | 检查容量、淘汰、缓冲上限或资源竞争 |

如果当前系统不能直接输出“实际少算 token”，应将它标为待补充观测，或使用明确标注的可核查替代证据。不能用 lookup 命中 token 直接改名充当有效复用。

<!-- pagebreak -->

### 基础8 6 比值、百分点与交互项

时延从 100 ms 降到 90 ms，是降低 10%；成功率从 98% 到 99%，是上升 1 个百分点，相对提升约 1.02%。指标越大越好还是越小越好，必须先说明。

对“无 PP / 有 PP”各自的缓存开关收益，需要四组：A 无 PP 无复用；B 无 PP 有复用；C 有 PP 无复用；D 有 PP 有复用。若 Y 是可比较的同口径原始耗时，交互项为：

**I＝YD－YC－YB＋YA**。也就是先算D相对C的变化，再减去B相对A的变化。

前一项表示 PP 布局内“开复用改变了多少耗时”；后一项表示无 PP 布局内同一件事改变了多少。两者之差才是该尺度上的交互。若 I 为正，表示 PP 布局中的复用效果比另一布局更差一些，但必须同时检查两种布局是否还改变了 DP、TP 等条件。

例：A＝100 ms、B＝80 ms、C＝120 ms、D＝115 ms。无 PP 时复用节省 20 ms；有 PP 时仅节省 5 ms；I＝15 ms。但是 D 仍比 C 快，不能写成“PP 下开启缓存让请求变慢”。

交互项只能帮助描述对照结果，不能告诉我们具体是哪一行代码导致它，也不建议为了计算它而在资源不足时强行改动多个并行参数。

### 基础8 7 相关、候选原因与已确认根因

“开缓存时变慢”是现象；“某个等待变长”是定位线索；“只改变这一等待的实现，异常消失且指标恢复；恢复旧条件可再现”才更接近因果闭环。

公开 issue 描述相似故障，可以提升排查优先级；某个 PR 修复相关问题，可以提供对照候选。但 issue 自动关闭不等于已修复，PR 合并不等于客户已经使用，也不等于客户问题已经被实验解决。

实验停止条件应分层：配置不可启动、输出不正确、传输失败回退、有效复用不足、有效复用正常但净成本过高，分别形成不同结论。不要把它们统称为“池化与 PP 不兼容”。

## 实验总表和结论层级

### 这套实验能确认到哪一步

| 层级 | 想确认的结论 | 对应证据 |
|---|---|---|
| L1 现象 | 客户当前PP布局下，池化开关是否改变业务性能 | M2与M3的同配置重复对照 |
| L2 链路 | P1产生的KV是否真的被P2使用并减少计算 | M1完整证据链，M3持续验证 |
| L3 布局交互 | 两种明确并行布局中的复用收益是否不同 | 追加X1，解释资源与DP/TP差异 |
| L4 根因 | 哪一项实现或配置造成现场异常 | M4受控修正、异常消失、业务改善和回退复现 |

有限实验不能证明所有版本的“池化与PP永远兼容或永远冲突”。它能确认某个模型、版本、拓扑和负载下的现象与机制。M4可以在原PP布局上确认一个同步点造成的损失，不必为了修复一个具体问题强行先跑四象限。

### 最少逻辑用例

| 用例 | 实际条件数 | 要回答的问题 | 何时停止或追加 |
|---|---|---|---|
| M1 跨P链路与正确性 | 关池参考、P1预热后P2复用、新前缀负对照 | 远端缓存是否完整加载并真正少算 | 发现稳定错误就转M4 |
| M2 全未命中 | C0池关、D0池开，PP固定 | 没有复用收益时，查找和写池花多少代价 | 写失败或保存等待明显时选M4 |
| M3 稳定远端复用 | Cw池关、Dw池开且预热，PP固定 | 省下的计算能否抵消读写与同步开销 | 用时间线挑选一个根因分支 |
| M4 修正闭环 | O1原版、F单点修正、O2回退 | 候选原因是否真的贡献了业务劣化 | 达到结案条件就停止扩展 |
| X1 布局交互 | 复用C/D，再补A/B两组 | 是否有可观测的布局交互 | 仅要写PP相关交互结论时做 |
| X2 压力或路由 | 在已有组基础上增加一个条件 | 是否由排队、竞争或路由不均放大 | 只跟随已有信号，不全量扫描 |

前置健康检查、模型热身和缓存预热不是正式性能样本，但都会消耗时间，必须另外记账。M2/M3共有4种条件，做3对重复就是12轮；如果每轮200个请求，共2400个测量请求，另加预热请求。首次筛查可先每轮50个，共600个，发现明显故障即转定位；这些数字不保证P99或统计显著性。

## 准备二 构造真正可比的开关

### 只关闭共享池 保留PD传输

先复制现场配置为测试版，保留原件。若实际使用MultiConnector，且其中MooncakeConnectorV1负责PD、AscendStoreConnector负责共享池，则池关闭变体只移除Store子对象，保留PD子对象的全部原值、顶层角色、失败策略、并行布局和其他启动参数。

```text
池开：MultiConnector的子项 = [原PD对象, 原Store对象]
池关：MultiConnector的子项 = [原PD对象]
```

这只是结构示意，不能直接作为完整JSON启动。没有通用的enable_pool=false；不能删整个kv-transfer-config。consumer_is_to_put=false只影响相应消费者回写，并非全局关池。“绕过共享池读取、保留写入”的变体也不是完整池关基线。[官方组合职责](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/docs/source/user_guide/feature_guide/kv_pool.md#L166-L168)

### 隔离APC带来的假命中

推荐的机制诊断条件是所有组均关闭本地APC，但前提是目标版本支持独立关闭且不破坏外部路径；以实际help、配置和日志为准，不猜参数。它是一组诊断条件，最终还需恢复客户原APC设置，重跑最关键的业务对照。

若保留APC，就采用P1预热、未见过相同前缀的P2各读一次。池关参考也会在P2留下本地缓存，因此在后续暖池测量前要重新建立P2干净状态，或使用经过证明的隔离实例和缓存清理机制。不能把参考请求之后的P2直接当成“本地未命中”。每轮都核对本地命中，而非只相信操作顺序。

### 模型热身与缓存预热分开

每次服务重启后用与正式前缀不重叠的材料做模型热身，等待初始化和编译影响稳定。然后按用例决定是否预热共享池。预热结束应有PUT完成及必需分片可查的证据，固定sleep几秒不能替代。缓存容量不足导致预热条目被淘汰时，应缩小批次，不能把实际低命中当成已实现的高命中组。

| warm_seed.jsonl | 发到固定P1路径，形成共享缓存 | 预热流量不计入正式性能样本 |
| warm_measure.jsonl | 相同前缀、新后缀，发到固定P2路径 | 每条仅测一次，避免P2本地命中 |
| correctness.jsonl | M1抽取资料编号，最多3条 | 与池关参考比较，使用正常EOS |
| negative.jsonl | M1未预热的新前缀 | 应无测试资料的外部有效命中 |
| model_warmup.jsonl | 独立前缀的模型热身样例 | 5条不保证所有形状已热身，应观察稳定性 |
| manifest.json与expected_answers.json | 前缀ID、目标输出上限、预期编号 | 不是测量数据；不能作为成功证据 |

每一对开/关使用同一个测量文件；下一独立重复用r02、r03。N应与实际文件条数一致，50条文件不能配N=200期待自动补齐。M2与M3必须使用不同run-id，否则M2写入的缓存可能污染M3状态。正式测试前记录输入实际token分布和可复用上限，过长超出模型限制时调小paragraph-repeat并重新生成两组共有数据。

JSONL是一行一个JSON对象，不是一个大数组。官方v0.18 custom格式接受prompt字符串及output_tokens；多轮messages不能直接塞进这个字段。[格式源码](https://github.com/vllm-project/vllm/blob/bcf2be96120005e9aea171927f85055a6a5c0cf6/vllm/benchmarks/datasets.py#L1894-L2007)

## 准备四 校准客户端和计时

### 地址和模型名先确认

BASE必须是能完成PD全过程的测试入口。127.0.0.1只表示“执行当前命令的这台机器”；若服务不在本机，应填实际测试地址。API模型名从v1/models读取，TOKENIZER填压测环境可访问的同一模型目录。

```bash
BASE='http://实际测试入口地址:端口'
MODEL='从v1/models读取的模型ID'
TOKENIZER='/实际模型目录'
curl --fail --silent --show-error "$BASE/health"
curl --fail --silent --show-error "$BASE/v1/models"
python -c 'import pandas'
```

网关未转发health或metrics时可能404，直接在相应实例地址检查，不据此认定模型不能推理。先发一个不属于正式前缀的流式小请求，核对P/D日志和首输出事件。若鉴权由既有环境变量提供，沿用测试环境做法，不把密钥写入文档或结果表。

### 使用附件原始文本的固定清单命令

下列命令在官方vLLM 0.18源码中核对过参数；它与本次Ascend主线不构成已验证的安装组合。现场先检查保存的help；缺参数时用原bench.sh的等价方式，不能为了抄命令而直接升级服务。

```bash
CASE_FILE='data/m2-r01/cold.jsonl'
CASE_ID='m2-c0-r01'
N=50
C=1
mkdir -p "$RUN_DIR/$CASE_ID"
vllm bench serve \
  --backend openai-chat --base-url "$BASE" \
  --endpoint /v1/chat/completions \
  --model "$MODEL" --tokenizer "$TOKENIZER" \
  --dataset-name custom --dataset-path "$CASE_FILE" \
  --custom-output-len -1 --skip-chat-template \
  --disable-shuffle --no-oversample --num-prompts "$N" \
  --request-rate inf --max-concurrency "$C" \
  --temperature 0 --ignore-eos \
  --ready-check-timeout-sec 0 --num-warmups 0 \
  --percentile-metrics ttft,tpot,e2el --metric-percentiles 50,90,99 \
  --request-id-prefix "$CASE_ID-" \
  --save-result --save-detailed --result-dir "$RUN_DIR/$CASE_ID"
```

这个模式将每行prompt作为一个user消息，由服务器套一次聊天模板。不要先套好模板再发给chat接口。若需原样多轮回放，应使用客户原工具。若proxy只支持completions，则应先按实际模板渲染prompt，再改为backend openai和endpoint /v1/completions；这属于另一个固定输入协议，不能在同一对照中混用。

C=1只用于链路初测；正式轮改为客户代表并发C星并保持开关组相同。inf加并发上限是闭环负载，不等于固定QPS；如果客户问题来自固定到达率，使用原发包计划，记录客户端等待，避免并发上限把过载排队掩盖。M1正确性请求去掉ignore-eos，让模型自然结束。

## 准备五 避免把工具读数当成真实收益

### 首包不一定是首token

官方v0.18客户端用第一个带choices的SSE消息计TTFT，没有要求text或content非空。因此空角色包可能使bench TTFT比首有效token更早；chat实现还可能遗漏reasoning内容。先用3条小请求核对原始流：首choices是否含真实生成内容，推理字段是否算在目标SLO中。[计时源码](https://github.com/vllm-project/vllm/blob/bcf2be96120005e9aea171927f85055a6a5c0cf6/vllm/benchmarks/lib/endpoint_request_func.py#L262-L333)

未校准时把列名写成“bench TTFT”，不要称为首可见字时间，也不要拿它作客户首字SLO验收。若不匹配，让工程师在相同客户端版本中修正事件边界，所有组保持一致。服务端首token计时可另列用于内部定位，但不包含全部proxy与网络时间，不能替代客户端首字SLO。curl的time_starttransfer可能只是响应头，不能代替模型TTFT。

### token数量以实际输出为准

output_tokens是目标上限；ignore-eos用于固定长度性能测试，仍要检查实际输出数量。M1正确性与最后业务验收使用客户真实生成规则，不用“强制128 token”冒充业务输出。实际输出优先取服务端usage.completion_tokens；数SSE包不等于数token，MTP可能一包多个token。若流末usage缺失，官方bench会重新分词拼接文本，可能漏掉reasoning或特殊token；不能只信结果JSON的output_lens，固定长度验收还需确认计数来源。

chat模式下，custom预先计算的长度可能只含user正文、不含服务器模板；用服务端usage或相同模板的tokenizer复核输入长度。不要使用skip-tokenizer-init，这条custom实现可能把长度设为1，破坏统计。

### 预检查不能污染正式前缀

已明确将ready-check-timeout-sec和num-warmups设为0。v0.18 CLI的ready check默认就是0，但旧脚本或其他调用可能不同；启用时会拿测试首条作预热。独立热身在正式轮之前完成，使用不重叠材料。记录并发、实际发出请求数、失败和实际输出量，不能删掉失败样本后宣布性能更好。

### 每轮必须存下什么

将配置副本和diff、版本、输入JSONL、路由证明、预热完成证明、before/after指标、完整客户端结果、代表请求日志放入同一CASE_ID目录。正式性能轮日志级别一致；高频DEBUG或重型profile只用于另外的少量定位请求，不能一组开一组关。

## M1 用少量请求证明跨P复用

**目的：**先证明数据从P1走到了P2，并且真的少算且输出正常。本例用3个前缀，不计算性能提升百分比。

**前提：**两条完整PD入口能够分别固定选P1和P2，并由日志证明路由；池开配置已生效；APC已全组关闭，或P2被证明没有这些本地条目。D侧和必要PD链路保持不变。

1. 做池关参考。BASE设为固定P2的完整PD入口，CASE_FILE用correctness.jsonl，N=3、C=1、删除ignore-eos。运行两次，保存输出，确认参考本身是否稳定。预期编号在expected_answers.json中；若模型自己就不能按题作答，先调整题目再继续。
2. 建立干净状态并开池。若参考请求留下了APC，必须按已验证方式重建干净P2；不能只切Store开关后就假定本地未命中。模型热身使用独立材料。
3. 在固定P1的完整PD入口发送warm_seed.jsonl，N=3。记录实际发布者：可以是P1写池，也可能是D接收P1的KV后回写。保存各必需阶段的PUT成功与可查证据，证明KV来源于P1这批请求；等真正发布后才继续，不以接口返回或固定等待秒数代替。
4. 在固定P2入口发送相同correctness.jsonl，N=3、C=1、不强制忽略EOS。每个前缀只发一次，关联P2外部候选命中、GET成功、必要分片齐全、可用KV写回和prefill实算量。
5. 在P2发送negative.jsonl，N=3。它没有在P1预热，应没有测试资料的外部有效复用。相同公共模板若有少量命中，单列模板token，不把它算作资料复用。
6. 比较输出。先看资料编号是否正确，再比较稳定参考的token或文本；参考本身不确定时，输出不同不能自动判缓存损坏，需要重跑参考并检查更直接的缓存正确性证据。

**通过标准：**小样本全部成功；新增传输错误、超时和加载失败回退为0；暖请求外部有效复用大于0且与可复用边界相符；负对照无资料复用；必需阶段完整、实际计算减少、编号正确。任何一项不可观测就写“该环节未证实”。

预算示例：3条参考两遍、3条预热、3条复用、3条负对照，共15个请求，另计模型热身。若发现稳定PUT失败或输出问题，立即转对应M4；不要为了完成表格继续发几千条请求。

**必须避免：**D侧external计数可能包含PD交接；不能把D接到P的KV算成跨请求共享收益。M1重点关联P2的Store来源和减少计算，不重复累计各PP阶段的同一token。

## M2 全未命中对照找固定成本

**问题：**当共享池没有提供复用收益时，它的查询、PUT、发布和同步是否已产生明显代价？

| 组别 | PP和PD | 共享池 | 数据与状态 |
|---|---|---|---|
| C0 | 保持客户原配置 | 完整关闭共享读写 | 本轮cold.jsonl，APC状态固定 |
| D0 | 与C0相同 | 正常开启 | 完全相同文件，每个前缀只出现一次 |

先用独立diagnostic run-id生成3至5条C=1的时间线样本，不从正式cold.jsonl抽取，否则会提前写入正式冷前缀。50条筛查扩为200条正式轮也必须换新run-id。正式轮用同一个客户代表并发或到达计划；需确认差异时每组200条起、3对重复。各对顺序交替为关→开、开→关、关→开；每对使用新的r01/r02/r03前缀，两组共享同一文件。

“全未命中”要求实测总有效外部复用为0，并确认首个可缓存块内已有不同内容。若公共聊天模板本身形成可复用块，应使用已验证的隔离状态或适合现场的等价输入；若仍保留公共命中，就将用例改名为“零资料复用对照”，单列模板命中，不能把全部差值解释为纯未命中固定开销。

操作时只替换通用命令的BASE、CASE_FILE、CASE_ID、N与C。池状态由已经核对的服务配置切换，CASE_ID里写c0或d0不会替你修改服务。重启后的热身规则相同；正式发送前和结束后保存指标及日志。

**主指标：**校准后的TTFT P50或预先选择的客户指标；辅以P90、E2E、成功率、实际输出token数。重点观察PUT返回码、保存排队、发布完成、下一step缓冲重用等待以及各PP阶段空闲。

**判读：**D0变差只能说明“无复用收益时共享路径有净成本”，不能直接证明池化无用。若有PUT失败，先找错误；若保存等待与退化一起增大，选保存生命周期分支；若只有索引CPU时间升高，查lookup；若成本小，进入M3看真实收益。

异步PUT可能影响下一请求或下一step，应检查测量段末尾未排空的保存队列和延迟释放。性能轮至少记录“最后请求完成”和“保存积压恢复到轮前状态”两个时刻；预热和排空成本另报，避免把后台债务丢到下一组。不能用强制每步设备同步的方式来测原本异步的性能。

**失败条件：**测试资料在D0发生有效复用、两组负载不同、服务中途重启、APC混入或后台残留无法区分，该对作废并重建状态；不是将异常数据删掉后继续比较。

## M3 稳定远端复用确认净收益

**问题：**共享池确实让P2少算以后，业务是否仍然变慢？此用例与M2使用不同前缀集合。

| 组别 | 正式请求 | 预备状态 | 是否计入正式成绩 |
|---|---|---|---|
| Cw池关 | warm_measure.jsonl，固定走P2 | 模型已热身；共享复用关闭 | 正式请求计入 |
| Dw池开 | 同一个warm_measure.jsonl | P1运行warm_seed并确认发布；P2无本地条目 | P1预热不计入稳态时延，另报成本 |

1. 先估算本批缓存能否驻留，必要时从50条开始；若共享池驱逐或容量紧张，缩小批次，而不是将“预热过”当“仍在池里”。
2. Dw轮先把BASE切到固定P1入口发送warm_seed，确认所有目标条目发布及所需阶段完整；随后切到固定P2入口测量。不要在P2执行同一前缀的端点测试或自动预热。
3. Cw/Dw使用同一输入、生成参数、客户端版本、负载和请求顺序。每条P2测量请求只读一次；每对重复重新建立状态。若APC不能关闭，参考轮之后必须清除该污染或改用已隔离的干净P2实例。
4. 记录实际有效外部复用比例、prefill实算量、GET与写回、PUT、保存屏障、P→D交接、排队和业务指标。目标命中率不能代替测得命中率。
5. 先50条方向筛查；需要稳定判断时采用与M2相同的200条起、3对重复。不预设一定需要0/30/60/90%扫描。

| 观测结果 | 能得出的结论 | 最省用例的下一步 |
|---|---|---|
| 有hit但没少算 | 复用证据链未闭合 | 查第一处断点，转M4，不做吞吐解释 |
| 少算且TTFT改善 | 该条件下池有净收益 | 仅补客户差异最大的负载或路由条件 |
| 少算但GET或写回阻塞大 | 读取开销候选 | 只验证对应传输或布局改变 |
| 少算但PUT或保存等待大 | 保存生命周期候选 | 核对15636相关实际代码，再做M4 |
| 单请求正常，业务并发异常 | 排队、竞争或资源压力候选 | 只追加X2一个压力点 |

M3减去M2的差值不是纯GET成本：命中、计算量和写行为都不同。归因依靠各自开关对照和关键路径。稳态收益也不含冷启动总成本；若业务频繁换前缀，应再用真实混合负载做最终验收，而不是无限扩大机制实验。

## M4 用一次受控修正闭环根因

**触发条件：**M1出现稳定错误，或M2/M3出现能够对应到某环节的异常。选择最敏感、最短的那个负载，不把全部实验重新跑一遍。

| 阶段 | 服务条件 | 必须保持一致 |
|---|---|---|
| O1 | 客户原版或原配置，重现异常 | 请求、缓存状态、拓扑、负载、日志级别 |
| F | 同一基线上的一个有明确边界的修正 | 除修正项外全部相同 |
| O2 | 恢复O1，检查异常是否返回 | 同样重新热身和建立缓存状态 |

每个阶段至少保留功能证据和对应业务结果；性能信号使用前述独立重复规则，不能一轮O1、一轮F就认定统计显著。若回退涉及共享状态不兼容，则使用隔离环境的等价反事实对照，不带着新版本修改过的状态硬回退。

### 按信号选择唯一改动

| 已看到的信号 | 合理的单点验证方向 | 不能替代的证据 |
|---|---|---|
| 某PP阶段PUT失败 | 针对实际错误的地址、注册或生命周期修正 | 只看错误日志消失但没有完整保存和输出验证 |
| 保存屏障拖慢step | 同基线评估对应同步实现或15636适用补丁 | 同时升级全栈后只归因15636 |
| 逻辑命中而缺片 | 对明确层范围、rank或cache group映射做修正 | 打开layerwise就宣布已修复 |
| GET正常但实际少算不成立 | 对加载完成、失败回退或调度采用路径做修正 | 把lookup token直接改名为有效复用 |
| LMCache首rank作用域风险 | 另一路线逐stage核对保存者与TP广播源 | 作为客户Mooncake根因 |

**结案同时满足：**O1/O2同一异常可重复；F改善该环节而非把功能关掉；F改善预设业务指标；输出正确性、成功率与有效复用不退化；回退后异常和退化返回，或具备等价反事实。

若F只改善内部等待但SLO没有恢复，结论应是“该开销存在，但不是当前主要端到端瓶颈”或“仅解释部分损失”。补丁依赖多项变化时，记录完整变更集合，结论限定到该集合。修正和回退均由维护者在隔离测试环境执行，本指南没有让你直接修改生产服务。

## 只在需要时追加的两个分支

### X1 确认并行布局的交互

只要要写“PP放大了池化代价”，就不能仅凭C/D两组下结论。复用M2或M3的一组PP开数据，补A无PP池关、B无PP池开。模型、负载、APC、版本和非PP优化保持一致；A/B不能装下时不能偷偷改TP/DP还称只改PP。

对同口径平均耗时使用 **I＝YD－YC－YB＋YA**。例如A=100、B=80、C=120、D=115 ms，交互项15 ms，但D比C仍快5 ms；这只能说明复用收益从20 ms减到5 ms，不能说PP下开池增加15 ms。

即使固定TP和DP，改变PP也通常改变活跃设备数和层的分布，因此应报告两种具体布局，而不是抽离资源后的“纯PP效应”。使用平均值和重复差值，不能把P99相减当作阶段耗时。对吞吐分别报告B/A与D/C的收益，并说明是否在同一SLO下比较。[交互与混杂参考](https://www.itl.nist.gov/div898/handbook/pri/section5/pri594.htm)

### X2 只补一个压力或路由条件

| 已有线索 | 仅追加什么 | 应观察的变化 |
|---|---|---|
| C=1正常，客诉并发异常 | 同负载与缓存下增加客诉并发点 | 排队、保存积压、最慢stage和传输竞争 |
| 原亲和路由使某P很忙 | 原路由与已确认的均匀路由 | 各P队列、命中、实际负载与端到端SLO |
| 客诉只看P99 | 同一条件增加独立样本和持续时间 | 尾分布、错误和队列，不能混负载凑样本 |
| 要求最大服务能力 | 在两组各做小范围到达率搜索 | 最后一个稳定满足SLO的点，而非低QPS完成数 |

如果仅有单机资源，X1可用于小模型机制教学，但不能替代客户GLM的布局交互结论。单机时延也不是跨节点劣化的必然下界。

### 恢复客户真实条件做一次验收

机制实验若关闭了APC、固定了P2路由或强制输出长度，得到的是受控条件结论。完成定位后恢复客户原APC、路由、生成规则与真实长度分布，复验“原版与修正”的最关键对照；这一步才连接业务价值，不需要重跑所有教学用例。

## 指标口径和明确判据

### 开跑前选择一个主指标

若问题是首字慢，主指标选经过校准的TTFT；若问题是服务容量，选满足既定TTFT/TPOT与成功率SLO的有效服务能力。输入输出长度差异明显时先分桶。不要测完再挑一个变化最大的指标。

| 指标 | 计算或读取方法 | 判读边界 |
|---|---|---|
| 请求成功率 | 正常完成数除以实际发出数 | 超时、错误、取消独列，不从分母删掉 |
| 正确性通过率 | 符合测试答案或正确性规则的请求占比 | 与HTTP成功率分开；小样本不等于全面模型精度 |
| TTFT | 请求发出到首有效模型token，通常毫秒 | bench首choices口径须先校准 |
| E2E | 请求发出到完成的时长 | 失败请求另报，不用成功分位数掩盖失败 |
| TPOT | 输出大于1时，用E2E减TTFT再除以输出token数减1 | 取实际输出；一包不等于一个token |
| 输出tokens每秒 | 成功输出token总数除以测量窗时长 | 说明请求窗和排空窗，不混输入token |
| SLO达标请求每秒 | 同时成功且满足所有预设SLO的请求数除以测量窗 | 没有预设SLO就不能称达标容量 |
| 有效外部复用比例 | 归因外部池且实际少算的输入token除以总输入token | APC单列，PP/TP不重复累加 |
| 内部传输失败 | 失败尝试数和受影响请求数分别统计 | 服务成功也可能内部失败后重算 |
| 保存等待 | step因保存未完成而不能继续的等待 | 不是后台PUT总时长，多个rank不能直接求和 |

前端usage.prompt_tokens通常是输入长度，并不是“新计算的token”。不能仅凭它或lookup命中数声称实算下降；需要调度器/worker实算计数或经验证的等价证据。

### 筛查阈值和停止规则

示范阈值可约定“TTFT P50恶化至少10%且至少20 ms”，同时记录三对原始值和自然波动。这只是工程触发线，不是普遍真理；5%等更小变化若已导致客户SLO失败也应处理。三次同向只能形成筛查信号，差异与波动相当时增加重复，不能任选最好一次。

每轮200个样本的最慢1%只有约2个观测，P99不稳。需要P99验收时，数千至上万样本可作为起点，仍须观察区间、稳定性和真实持续负载，没有一个固定样本量自动保证可信。已形成M4闭环且业务验收通过就停止；未复现只能写“本条件未复现”。

## 现成指标和日志怎样读取

### 先采快照 再看正确的增量

METRICS_BASE填P1、P2或D实例的指标地址，各实例分别保存。它不一定等于proxy的BASE。文件后缀before和after不要互相覆盖。

```bash
METRICS_BASE='http://实际实例地址:端口'
curl --fail --silent --show-error "$METRICS_BASE/metrics" \
  > "$RUN_DIR/$CASE_ID/p2-before.prom"
# 正式测试完成后再次执行，文件名改为p2-after.prom。
```

counter是累计计数，用同实例同标签的after减before；gauge是当前状态，要在轮内采样看峰值；histogram的sum/count可求操作均值。服务重启使counter归零时应分段或作废该轮。所有轮使用相同采样频率，后台保存积压需持续观察至恢复。request-id-prefix用于客户端标识；proxy若重写请求ID，应保存客户端到P/D的映射，不能假定所有节点编号天然相同。

| 指标或字段 | 能说明什么 | 不能说明什么 |
|---|---|---|
| prefix_cache_queries_total及prefix_cache_hits_total | 相应引擎的本地前缀查询与命中 | 共享池GET成功 |
| external_prefix_cache_queries_total及external_prefix_cache_hits_total | connector返回的外部候选命中 | 在MultiConnector/PD下自动等于Store净收益 |
| request_prefill_kv_computed_tokens | 新计算prefill token分布 | 只靠累计值就能匹配任意请求 |
| ascend_store_load_get_duration_seconds | 当前非layerwise每worker的Backend.get时长 | 所有rank时长相加就是请求等待 |
| ascend_store_load_get_keys_total | 完成get调用中传入的key数 | 成功命中key数或成功复用token数 |
| ascend_store_delayed_release_requests及ascend_store_delayed_release_blocks | 异步保存导致暂不能释放的引用状态 | 唯一物理block字节数或总排队量 |
| num_requests_waiting及num_requests_running | 队列及执行中的请求 | 纯缓存开销 |

上表省略共同前缀vllm:；目标服务中不存在的字段写NA。GET均值可用1000乘以sum增量除以count增量，单位毫秒；count增量为0时写“无样本”，不写0 ms。当前Ascend字段与vLLM 0.18通用字段分属不同源码快照，存在性以现场为准。[Ascend指标定义](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/metrics.py#L82-L128)

## 指标不够时只补最少的观测

先使用已有日志和指标。只有无法回答“哪里多等了”时，才由工程师对客户版本增加下列有限计时，并将观测补丁保持在所有对照组一致。不要每token打印，不要为了计时强制每步NPU同步。

| 位置 | 最少字段 | 作用 |
|---|---|---|
| lookup入口和返回 | request_id、输入token、本地命中、候选外部token、起止时间 | 判断查找与命中承诺 |
| GET边界 | 请求、PP/TP/group、key数、字节、提交与完成、错误码 | 判断分片与读取成本 |
| PUT入队和实际执行 | batch/request、入队、开始、完成、成功失败key数 | 分开排队和真正传输 |
| 保存屏障 | 等待起止、batch、stage及对应step | 找到未被重叠隐藏的等待 |
| 加载被采用和实际计算 | 成功加载token、实算token、失败重算 | 连上“命中→少算” |
| PD交接 | P→D独立传输开始与完成、字节 | 与共享池GET分开 |

当前后端PUT会记录失败key，但外层调用返回不可靠地代表全部key成功。因此只在外层测耗时不够，还要保留后端返回码。[PUT路径](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py#L1178-L1185)

主机perf_counter_ns可量同一进程内的间隔，但异步提交耗时不是设备执行耗时；跨节点绝对时间需要校时。能按request_id关联仍不表示各节点时钟已对齐。必要时只抓少量设备级trace，并与无重型profile的正式成绩分开。

### 一个教学例子

假设O1与O2的TTFT P50分别为120和123 ms，F为92 ms；保存关键等待从约25 ms降到3 ms，实际复用、输出和成功率相同。这个模式支持保存等待有重要贡献，但仍应查看独立重复与负载条件。反之若等待降了22 ms，TTFT仍约120 ms，应继续查其他关键路径，不能把内部改善直接写成用户收益。

这些数字不是实测结果。填写附件表格时只填实际采集值；并行事件存在重叠，不能要求内部各段改善之和恰好等于TTFT变化。

## 结果记录和结案模板

附件提供四张空表：run_manifest.csv记录实验条件，request_evidence.csv记录M1证据链，stage_events.csv记录需要补充的事件，comparison.csv记录每轮指标。它们只是约定记录格式，不是服务已经自动输出的字段。

每个正式轮使用唯一run_id，至少记录CASE_ID、池状态、APC、P路由、PP/TP/DP、版本、数据文件、并发或到达率、模型热身与池预热状态。写清planned、sent、completed和failed数量；超时请求也保留，不能以成功样本替换后凑N而不报告额外请求。

### 用这一段形成有证据的最终结论

“在【模型与权重】【软件提交】【P/D并行拓扑】【池路径】【APC与路由】【长度分布】【并发或到达计划】条件下，M1证实/未证实【跨P发布、加载、完整性与实际少算】。M2/M3的主指标由【基线逐轮值】变为【候选逐轮值】，差异【范围】；失败与正确性【结果】。异常集中于【具体阶段和事件】。M4只改变【补丁或配置集合】后，该异常【变化】，业务【变化】，回退【结果】。因此确认【具体贡献或根因】，尚不能推出【未覆盖的模型、拓扑或负载】。”

### 判读速查

| 结果 | 可以写 | 不可以写 |
|---|---|---|
| 启动失败 | 当前版本与配置不可用 | 运行时吞吐劣化已复现 |
| M1没有外部完整复用 | 路径或观测未完成，需要定位断点 | 池化没收益所以理论不成立 |
| M2有成本，M3有收益 | 两类负载下收益边界不同 | 仅凭M2否定全部池化 |
| C/D退化，未跑A/B | 当前PP布局下组合退化 | PP交互已被证明 |
| 新镜像变快，多项组件都换了 | 新组合改善 | 某一个PR是唯一根因 |
| 单点修正加回退闭环 | 该变更对已测异常有因果贡献 | 所有环境的问题均解决 |
| 只有单机或小模型结果 | 已测子场景结论 | 客户GLM跨节点性能已验证 |

**停止标准：**已形成明确故障闭环并满足业务验收，就不再扩展无关扫描。差异小于当前测量分辨能力时写“未分辨”；未复现时只追加最相关现场差异，不用一句“理论上兼容”替代实证。

| CSV | 逗号分隔的表格文本 | 可用Excel打开；空表字段不是服务现成自动采集值 |
| Bash与PowerShell | Linux常用终端语言与Windows终端语言 | 指南的服务命令为Bash，不能直接粘贴到PowerShell执行 |
| 容器与镜像 | 隔离运行环境与其打包模板 | 相同名称的镜像可能被更新，需记录实际镜像标识和组件版本 |
| 环境变量 | 进程启动时读取的配置值 | 修改终端变量不表示已运行服务自动生效；以实际配置和日志为准 |
| Prometheus指标 | 常见文本格式的监控指标 | /metrics端点可能在各实例，proxy未必转发 |
| counter | 单调累计计数器 | 用同标签前后差；重启归零后不能直接相减 |
| gauge | 当前状态量 | 观察轮内变化或峰值，前后差不是累计发生量 |
| histogram | 按区间累计的分布 | sum除count可得该操作均值；分桶也影响分位估计精度 |
| label与delta | 指标标签与增量 | 按同实例、模型、引擎维度比较，防止把不同计数混合 |
| SLO goodput | 满足服务目标的有效完成速率 | 与单纯完成吞吐不同，超时或不达标请求不能算达标 |
| EOS | End Of Sequence，生成结束标记 | ignore-eos用于强制长度的诊断，不代表真实用户输出规则 |
| seed | 随机种子 | 有助复现输入或生成，但不保证分布式计算完全确定 |
| NA | 不可用或没有采到 | 不等于0；缺指标不能写为零错误或零耗时 |
| diff与patch | 变更差异与补丁 | 用于证明只改预定项；完整镜像升级不等于单点修正 |
| UT | Unit Test，单元测试 | 通过不能代替NPU通信、模型正确性和业务性能测试 |

## 附录二 先做自查

1. 一套部署写“2P1D、P 侧 PP2”。这里的两个“2”分别数什么？
2. 两次请求都路由到 P1，第二次很快。能否直接确认跨实例共享缓存有效？还缺哪条证据？
3. lookup 返回命中 3,000 token，但实际只少算 1,000 token。评估计算收益应使用哪个数字？其余部分需要查什么？
4. PP2、TP2 示例中有两个 TP 组。每个组的 rank 0 是否一定是 global rank 0？
5. PUT 提交只用了 0.1 ms，但下一步等待缓冲区 20 ms。能否说保存成本只有 0.1 ms？
6. A＝100、B＝80、C＝120、D＝115 ms。缓存是否让 PP 配置变慢？它在两种布局中的收益是否相同？
7. 脚本设置每秒 0.3 个请求且服务始终不排队，测到的完成吞吐能否直接称为系统最大能力？
8. 换新镜像的同时将 DP2 改成 DP1、加上 PP2，并调整输入长度，性能改善。能否直接确认某个 PP 补丁已修复根因？

## 附录三 自查答案

1. 2P1D 的 2 是 P 服务组或副本数量；PP2 的 2 是一个模型实例内部的流水线阶段数。
2. 不能，可能只是 P1 本地 APC 命中。需要证明目标请求由缺少本地条目的另一个实例处理，并实际从共享池加载且有效少算。
3. 使用已证实归因于外部缓存的实际少算部分评估收益。继续核对块对齐、阶段完整性、加载失败、写回、回退及调度是否采用命中结果。
4. 不一定。每个 TP 组有自己的组内 rank 0；全局 rank 0 只有一个。必须核对映射和广播范围。
5. 不能。异步提交不是完成，缓冲重用等待可能把保存成本转移到下一步，应看完整生命周期和关键路径。
6. 缓存让 PP 配置从 120 ms 变为 115 ms，仍改善 5 ms；无 PP 时改善 20 ms，收益不同。交互项 15 ms，不能改写为 PP 下开缓存增加 15 ms。
7. 不能。它主要反映该发送负载下的服务表现，需要在明确负载与 SLO 下探索容量才能谈最大能力。
8. 不能。多个因素同时变化，只能暂时说明新部署的结果不同；需做针对候选原因的受控对照并连接异常与业务指标。
