# KS问题最终分析结论

零基础增补版 含基础知识 名词解释和实验确认路径

这份报告帮助你先看懂大模型推理、KV缓存和并行部署，再理解KS问题的分析证据与确认方法。结论仍是：现有资料不支持“池化与PP先天冲突”；具体客户根因需要在实际版本、拓扑和负载中，通过受控实验确认。

本版保留原报告的独立分析、源码证据与对比结论，补充完整入门章节，并将每项关键判断对应到最少实验用例。它没有把新编写的操作方案当成已经执行的实验结果。源码核对基准为2026年10月3日，客户聊天为2026年8月及9月。

## 基础1 先看一条请求：模型到底在做什么

### 基础1 1 请求、提示词与 token

把模型服务想成一家收到问题、阅读资料、逐字组织回答的工厂。一次用户提问及其上下文，就是一次“请求”。请求通常包含系统提示、历史对话、本轮问题和生成参数。

模型不会直接以“汉字个数”计量文本。它先用分词器把文本转换为一串编号，每个编号对应一个 token。token 可能是一段词、一个字符或其他文本片段，具体由分词器决定。因此“输入 4,096 token”不能直接改写为“输入 4,096 个汉字”。

模型权重是训练得到的参数，可以理解为工厂长期使用的设备与规则；输入文本是这一次订单的资料。推理是使用这些权重计算答案，通常不会在回答过程中重新训练模型。量化则是以较低精度表示权重或部分计算数据，目的是减少占用或改善执行效率；不同量化配置必须作为不同测试条件记录。

本次问题研究的是同一套模型在服务时如何保存、复用和传输中间计算结果，不是训练模型，也不是改变模型知道的知识。

### 基础1 2 prefill 与 decode：先阅读，再继续生成

一次常见的自回归生成包含两个阶段：

| 阶段 | 类比 | 实际工作 | 本次要观察什么 |
|---|---|---|---|
| prefill，预填充，简称 P | 先阅读收到的整份资料 | 对输入 token 计算各层状态，并形成后续生成需要的 KV | 是否真的少算了输入；是否在加载或保存缓存时等待 |
| decode，解码，简称 D | 根据已经读到和写出的内容继续回答 | 逐步生成新的 token，持续使用并扩展 KV | 首字后生成是否变慢；是否等待 P 侧移交 KV |

prefill 常有较强的计算需求；decode 常受数据访问与调度效率影响。这是理解方向，不是所有模型、批量和硬件下都成立的绝对判断。判断客户瓶颈仍要依靠测量。

“第一个 token 很晚出现”和“第一个 token 后输出很慢”是不同问题。前者需要看排队、prefill、缓存读取、P→D 交接等环节；后者还需要看 decode 执行、批量与请求间竞争。

## 基础2 KV Cache：缓存了什么，为什么能省计算

### 基础2 1 KV 不是已生成的答案

在注意力计算中，模型会用到 Key 和 Value，简称 K、V。KV Cache 是把这些中间状态保存下来，让后续计算复用。类比读长资料时做的“可继续使用的阅读笔记”，它既不是原文的简单副本，也不是问答结果的数据库。

不使用已保存的 KV 时，一些相同上下文需要重新计算；正确复用 KV 后，可以减少重复工作。模型仍需要完成新输入部分和后续生成，所以“缓存命中”不等于“不再进行推理”。

普通注意力、MLA 等模型结构的缓存形状和占用可能不同。本问题不应凭通用的“每层 K/V”示意图计算实际传输字节；应读取当前模型实际 KV 张量和连接器的元数据。

### 基础2 2 前缀复用：相同的开头才构成复用机会

例如两条请求分别是“共同背景资料 + 问题甲”和“同一背景资料 + 问题乙”。两者开头的 token 序列相同，就可能复用共同背景的 KV。判断还需要模型、tokenizer、缓存键、位置和相应运行配置匹配，不能只凭肉眼认为两段话意思相同。

“两段文字语义相近”不等于“可以直接复用同一份 KV”。相同文字放到不同上下文位置，也不能无条件视为同一个可复用前缀。

实验必须区分三件事：输入中有多少理论可复用的 token；缓存系统查到了多少；最终真正省去了多少 prefill 计算。只有最后一项直接连接到计算收益。

### 基础2 3 block 与 chunk：两种分块单位不能混写

缓存通常分块管理，好比书按页存放，避免每次申请一大片连续空间。

| 名称 | 定义与用途 | 注意事项 |
|---|---|---|
| KV block，KV 块 | 推理引擎管理 KV 的基本块；存在逻辑块与实际内存块的映射 | block 大小及内存布局由当前引擎配置决定 |
| chunk，缓存片段 | 外部缓存引擎进行索引、保存或加载的一段 token 对应的数据 | chunk 不一定等于一个 vLLM block；不能默认两者数量相同 |
| shape / stride | 张量的各维大小 / 沿各维移动时跨越的内存距离 | 数据量对了，步长或布局错了，仍可能读写错误 |
| cache key | 用于识别缓存对象的键 | 可能包含模型、token、rank、PP 阶段等维度，具体按实现核对 |

例如请求有可复用前缀，但长度未覆盖完整缓存块，实际可复用 token 可能少于文字上相同的部分。实验中的目标复用比例只是输入设计，实际有效比例必须另测。

## 基础3 数据放在哪里：NPU、HBM、主机内存与网络

把 NPU 视为执行模型计算的设备；HBM 是其附近的高速设备内存；Host 内存是主机 CPU 使用的内存；SSD 是持久存储。把 KV 从设备内存搬到 Host 或其他节点，可以扩大可保存的范围，但搬回时也需要时间。

| 位置或动作 | 直观解释 | 与 KS 实验的关系 |
|---|---|---|
| NPU | 执行张量计算的加速设备 | 要知道哪些设备负责哪个并行阶段 |
| HBM | NPU 使用的高速设备内存 | 模型权重、KV、工作空间等都会占用它 |
| Host / CPU 内存 | 主机内存，常称 DDR | 本地卸载缓存可能放在这里，并不等于共享池已开启 |
| SSD | 比内存更持久的存储层 | 容量、读写和缓存策略会改变端到端行为 |
| D2H / H2D / D2D | Device→Host / Host→Device / Device→Device | 分别记录设备到主机、主机到设备、设备之间的数据移动 |
| 内存注册 | 将一段内存及其范围交给传输系统识别和访问 | 注册地址或长度不匹配可能引发传输失败 |

“卡”“芯片”“进程”不是同一个计数单位。有的硬件一张物理卡含多个计算芯片；一个服务又会启动多个工作进程。不要把截图中的“16 个芯片”写成“16 张物理卡”。现场应分别记录物理节点、卡、可见设备和 worker 数量。

带宽描述单位时间能够传送多少数据；时延描述一次操作需要等多久。大块传输可能更受带宽影响，大量小块操作可能更受调用和同步时延影响。因此不能仅凭总字节数判断某个路径一定快或慢。

## 基础4 多个设备如何合作：先分清 PP、TP、DP 和 PD

### 基础4 1 PP：把不同层交给不同阶段

PP 全称 Pipeline Parallelism，流水线并行。可以类比一条生产线：第一站处理前面一组工序，第二站处理后面一组工序。模型的不同层被分配到不同 stage（阶段），请求依次经过这些阶段。

PP2 表示两个流水线阶段，不是两个 prefill 副本。某个阶段通常保存自己负责层的 KV。因此一条请求的 KV 可以分散在多个阶段上，但不要求外部缓存一定先把它们拼成“全模型一大块”。系统也可以分别记录和传输阶段片段。

一个阶段慢了，后续阶段可能等待；等待造成的空闲常称“流水线气泡”。PP 可以让模型分布到更多设备上，也可能改善适合的服务负载，但不是把阶段数翻倍就保证时延减半。

### 基础4 2 TP、DP 与 EP：分别切计算、复制服务、分配专家

| 方式 | 类比 | 精确定义 | 不应混同 |
|---|---|---|---|
| TP，张量并行 | 多个工人合做同一道工序 | 将某些层内部的张量计算分给多个设备，并进行必要通信 | 不是复制完整模型服务 |
| PP，流水线并行 | 不同工位负责不同工序 | 不同设备或设备组负责不同模型层区间 | 不是 prefill/decode 分离 |
| DP，数据并行 | 多条服务线接不同订单 | 多个模型副本处理不同请求或批次 | 增减 DP 会改变副本数和排队行为 |
| EP，专家并行 | 按任务送到相应专家工位 | 在 MoE 模型中把专家计算分配到不同设备 | 是否可组合及如何通信依赖模型和版本 |

例如把 DP2、TP8 改成 DP1、TP8、PP2，虽然总设备数可能不变，但同时减少了副本数、增加了流水线阶段。这是在比较两个部署方案，不能把所有差值都归因于“PP 开关”。

### 基础4 3 rank 与 group：编号一定要说明属于哪个范围

rank 是一个参与分布式计算的进程在某个通信范围内的编号。global rank 是全局编号，TP rank 是 TP 组内编号，PP rank 是所在流水线阶段的编号。group 是参加某类协作的进程集合。

用一个简化示例理解：PP2、TP2 可以由 4 个 worker 组成。第一个 PP 阶段有 2 个 TP worker；第二个 PP 阶段也有 2 个 TP worker。两个 TP 组都可以各自有一个“组内 rank 0”，但全局 rank 0 只有一个。具体编号与映射要以运行日志为准。

这正是最终分析报告中 first-rank 风险的关键：**“全局第一个 worker”与“每个 TP 组的第一个 worker”不是同一个集合。** 不能看到 first_rank 这个名字就认定每个 PP 阶段都有人保存缓存，也不能只凭这个名字断定必然丢缓存；需要把实际编号、保存者和广播范围列出来。

### 基础4 4 PD 分离与 2P1D：这是服务角色，不是模型切层

PD 分离把 prefill 和 decode 交给不同服务组。P 侧算完本次请求的输入后，需要将相应 KV 交给 D 侧，D 侧才能继续生成。

2P1D 表示两组 P 服务和一组 D 服务。它描述服务分工与副本安排；每一组内部还可以有自己的 TP、PP 等配置。两个 P 副本不是两个 PP stage。

一条简化的请求路线是：

`用户请求 → proxy 选择 P1 或 P2 → P 侧 prefill → P→D KV 交接 → D 侧生成 → 用户收到答案`

proxy 是入口路由组件。KVC 亲和是尽量把请求分给已经持有合适 KV 的实例，以减少重算或搬运；但过度集中路由也可能让某个 P 排队更久。因此高命中率与低时延未必同时出现。

## 基础5 “缓存开启”到底开启了什么

### 基础5 1 必须分开的四条路径

| 路径 | 缓存在哪里、谁复用 | 主要收益 | 不能据此声称 |
|---|---|---|---|
| 本地 APC，自动前缀缓存 | 当前模型实例复用自己已有的前缀 KV | 减少相同前缀的重复 prefill | 其他实例已成功从共享池读取 |
| 本地 CPU/SSD 卸载 | 当前实例将 KV 放到设备之外，再按需加载 | 增加可保存范围，可能降低设备内存压力 | 已开启跨实例或跨机器共享 |
| 外部共享缓存池 | 多个实例经外部存储与传输系统复用 KV | 使一个实例计算的结果可被其他实例利用 | 必须把全模型所有层作为一个不可分割对象 |
| P→D KV 传输 | 为同一次请求把 P 侧结果交给 D 侧 | 让 PD 分离的服务完成生成 | 已发生跨请求的前缀复用 |

一套系统可能同时使用四条路径。客户说“池化开启”时，必须找到对应的实际配置和数据流，不能只按名称猜测。

### 基础5 2 为什么“关池化”不能顺手关掉 P→D 传输

在 PD 分离部署中，P→D 交接是请求正确执行所需的路径。如果为了测试共享池收益把它一起关掉，服务可能无法完成同一种任务。这个对照回答不了“共享复用是否导致劣化”。

正确的第一步是确认两个能力是否有独立开关。测试共享复用时，模型、并行布局、路由和必要的 P→D 交接保持不变。若现场配置把两者绑定，应先说明无法直接进行单变量对照，而不是把启动失败当成性能下降。

### 基础5 3 冷缓存与暖缓存：必须说明冷暖的是哪一层

冷缓存指目标内容尚未在被测缓存中形成可用条目；暖缓存指事先已准备好目标内容。不能只说“已经预热”，还要写明本地 APC、CPU 缓存、外部共享池各自的状态。

验证跨实例共享的一种典型思路是：让 P1 先产生并成功发布某个前缀的 KV，再让 P2 处理带同一前缀的请求；同时确保 P2 本地没有这份 KV，并从日志确认读取来自外部池。若两次请求都落在 P1，只能证明某种缓存可能有效，不能单独证明跨实例共享已走通。

这里的清理与预热应使用受控测试命名空间、明确的缓存接口或隔离实例，不能为了制造“冷缓存”而随意删除现场公共数据。

## 基础6 软件组件地图：谁计算，谁管理，谁搬运

把服务理解为多层协作，能避免把不同软件的限制混成一个根因。

| 组件 | 在本问题中的职责 | 应保留的边界 |
|---|---|---|
| vLLM | 模型服务、请求调度与 KV 管理等推理框架能力 | 同名配置在不同版本中的行为可能变化 |
| vllm-ascend | vLLM 的昇腾适配实现与相关集成 | 具体模型、connector 和并行模式的支持需逐项确认 |
| connector，连接器 | 将推理框架的 KV 生命周期接到外部存储或传输实现 | “能加载连接器”只证明入口存在，不证明命中或性能 |
| AscendStoreConnector | 当前公开栈中的外部 KV Pool 接入路径之一 | 客户是否使用它，要看实际 kv_transfer_config |
| MooncakeConnectorV1 | 当前公开栈中的 P→D 传输路径之一 | 不能仅凭 Mooncake 名称认定它与 Store 的配置相同 |
| MultiConnector | 组合多个连接器的方式 | 必须辨认每个子连接器负责的方向和角色 |
| Mooncake Store | 提供缓存对象保存、查找和读取等存储侧能力 | 对象可以由上层按阶段分片组织 |
| Transfer Engine，传输引擎，简称 TE | 根据地址、目标区域和长度完成数据搬运 | 搬运成功不自动保证上层缓存语义正确 |
| HIXL | 本场景涉及的数据传输相关软件能力 | 实际调用路径、版本与内存模式均需确认 |
| fabric mem | 材料所述的一种内存访问/传输模式 | 是具体工程路径，不等同于全部 Mooncake 传输，也不是 PP 的别名 |
| LMCache / LMCache-Ascend | 另一条缓存引擎及其昇腾适配路线 | 其后端互斥或 first-rank 风险不能直接作为客户 Mooncake 根因 |

`use_layerwise` 表示某条实现是否以按层保存或加载的方式工作；PP 表示模型层如何分配到阶段。PP 阶段可以一次处理自己负责的多层 KV，因此 **PP 开启不自动要求 use_layerwise=true**。

源码中存在一个功能、公开文档称某路径支持 PP、现场正确加载并通过测试，是三种不同证据。当前代码的能力也不能倒推客户数周前的镜像已经具有相同能力。

## 基础7 缓存的一生：读路径之外，还要看写路径

### 基础7 1 写入端：计算完成不等于缓存已可复用

一段 KV 在 P 侧生成后，系统可能需要：准备待保存的数据和元信息 → PUT 写入 → 等待相关数据操作完成 → 使缓存条目对其他请求可见。实际实现可能合并或交错这些步骤，实验不能强行套用不存在的阶段名。

PUT 类比把书送到仓库。提交了“送书申请”不等于书已经到库，更不等于书目已经可检索。相应地，异步接口返回可能只代表任务已进入队列，不能把这时刻视为“缓存已经发布完成”。

异步保存可以与计算重叠，但后续要复用同一块缓冲区时，可能必须等待之前的保存结束。等待点可能出现在下一个调度步，因此“当前请求的 PUT 提交很快”不代表保存对整条流水线没有影响。

### 基础7 2 读取端：查到、取到、写对、少算是四件事

| 证据层次 | 最少要证明什么 | 只到这一层仍不能证明什么 |
|---|---|---|
| lookup，查找命中 | 索引说目标条目存在或有可复用 token | 数据尚未证明实际拿到 |
| GET / pull，读取完成 | 所需缓存分片成功读取 | 不证明所有 PP 阶段数据完整，也不证明写入位置正确 |
| writeback / scatter，写回完成 | 数据落入当前推理引擎所需的 KV 块与布局 | 不证明调度器真正跳过了相应计算 |
| effective reuse，有效复用 | 必要阶段齐全且相应 prefill 计算确实减少 | 不保证节省的计算大于查询、读写与同步成本 |

PP 场景中，一个阶段命中而另一个阶段缺少所需分片，不足以声称请求已经获得完整复用。具体完整性判断可能按阶段、cache group 或其他粒度聚合，必须以当前实现定义为准。

若读取失败，框架可能回退到本地重算。结果仍能正确生成，但付出了“失败搬运 + 重算”的额外代价。此时业务成功率可能很高，内部传输失败率却不为零，两者都需要记录。

### 基础7 3 关键路径：不能把所有耗时直接相加

假设计算需要 8 ms，缓存传输需要 5 ms。如果二者完全依次发生，该段耗时可能接近 13 ms；如果充分重叠，可能接近 8 ms；如果还有前置依赖或资源竞争，则又会不同。这些数字只是解释重叠关系。

关键路径是完成请求必须依次经过的最长依赖链。定位性能时要找到关键路径上实际增加的等待，而不只是寻找“累计耗时最多的函数”。多个 PP 阶段、多个请求和后台保存可以重叠，简单相加会把并行工作误算为用户等待。

## 基础8 怎样读实验结果：测试方法与指标基础

### 基础8 1 对照组、变量与用例

本指南把一个要回答的问题称为“逻辑用例”，它可以包含开与关等多个测试条件；一次运行是在一个条件下发送一批请求。重复运行用于估计自然波动。减少逻辑用例不等于只跑一次请求，必须同时报告条件数、运行轮数和请求数。

对照组是用于比较的基准条件；实验组只改变想研究的因素。若同时改镜像、TP、DP、PP、缓存引擎和数据集，虽然可能得到更好的分数，却很难知道是哪项改动起作用。

机制定位回答“为什么”；部署比较回答“这一整套配置是否更合适”。两者都合理，但结论不同。用户希望最少用例定位时，应先找同一现场配置里的异常，再只对这个异常做一项有针对性的改变，避免一开始穷举所有组合。

### 基础8 2 业务指标：用户究竟感受到什么

| 指标 | 定义与单位 | 读数注意事项 |
|---|---|---|
| 请求成功率 | 成功完成请求数 ÷ 发出请求数 | 说明超时、错误输出、取消是否算失败 |
| TTFT，首 token 时延 | 客户端发出请求到收到第一个输出 token 的时间，常用 ms | 包含客户端与服务链路可见的等待，不等于纯 prefill 计算 |
| E2E，端到端时延 | 请求发出到输出完成的总时间，常用 ms 或 s | 输入、输出长度不同会影响结果 |
| TPOT，每输出 token 平均时间 | 输出不少于 2 token 时，通常为 (E2E−TTFT) ÷ (输出 token 数−1) | 每请求计算还是对全体聚合，需要明确 |
| ITL，相邻输出间隔 | 流式输出中相邻 token 或事件之间的间隔 | 投机解码可能一批产生多个 token，不能无条件等同 TPOT |
| 输出吞吐 | 统计窗口内成功请求的输出 token 总量 ÷ 窗口时长，单位 tokens/s | 写明是否包含输入 token、失败请求，以及窗口范围 |
| 请求吞吐 | 完成请求数 ÷ 时间，单位 requests/s | 输入输出长度改变后，不可与 tokens/s 直接互换 |
| SLO，服务目标 | 事先约定的成功率、时延或吞吐要求 | “达标吞吐”需明确达到哪条时延和成功率条件 |

例如某请求 TTFT 为 0.5 s，E2E 为 2.5 s，输出 101 token，则按上述定义 TPOT 为 (2.5−0.5)÷100＝0.02 s，即 20 ms。这个平均值不能说明每一个 token 的间隔都等于 20 ms。

### 基础8 3 P50、P95、P99：平均值以外的等待

将一批请求的时延从小到大排列，P50 是中间位置附近的值；P99 是约 99% 样本不超过的值。P99 用于观察少数很慢的请求，通常称尾延迟。

P99 不是“最慢的 1% 的平均值”，也不是最大值。少量样本的 P99 容易被一两个请求支配。必须同时报告样本量，样本不足时不能凭 P99 的单个数字下稳定性结论。

### 基础8 4 到达率、并发与满载：压测工具如何发请求

开放式负载按计划到达率发请求，例如每秒 2 个；服务变慢时在途请求和队列可能增长。封闭式负载维持一定数量的并发请求，例如始终最多 8 个请求在处理，完成一个再发下一个。

QPS 常用于表示每秒请求数，但要分清“计划发送”“实际发送”和“成功完成”的口径。并发 8 不等于 QPS 8；工具里的 num-users 也不自动等于稳定并发。

低到达率适合观察单请求链路，却不一定能量出系统最大吞吐；高并发能暴露排队与资源竞争，却可能把缓存本身的代价和排队代价混在一起。因此初次定位通常先用少量请求确认正确性与路径，再在一个明确的业务负载点做性能对照。

### 基础8 5 缓存与传输指标：收益和成本要同时记录

| 指标 | 建议口径 | 为什么需要 |
|---|---|---|
| 理论可复用比例 | 设计为相同前缀的 token ÷ 总输入 token | 描述负载设计，不伪装成实际命中结果 |
| 外部逻辑命中率 | 由实际 lookup 返回定义，分别记录请求或 token 口径 | 检查索引发现了多少可用内容 |
| 有效外部复用率 | 归因于外部缓存且最终实际省去的 prefill token ÷ 该批总输入 token | 将外部收益与本地 APC 分开，不重复计数；明确块对齐等边界 |
| 传输失败率 | 失败传输次数 ÷ 传输尝试次数 | 必须说明重试按独立尝试还是一次逻辑操作统计 |
| 回退率 | 发生缓存失败重算的请求数 ÷ 相关请求总数 | 解释服务成功但性能变差的情况 |
| GET / PUT 字节数与次数 | 每请求、每阶段及整轮分别统计 | 区分读写成本、碎片化和重复传输 |
| 保存等待 / 读取等待 | 在确定事件边界之间测量的时长 | 关注关键路径上没有被其他计算隐藏的部分 |
| HBM / Host 峰值 | 相应资源的最大占用及采样频率 | 检查容量、淘汰、缓冲上限或资源竞争 |

如果当前系统不能直接输出“实际少算 token”，应将它标为待补充观测，或使用明确标注的可核查替代证据。不能用 lookup 命中 token 直接改名充当有效复用。

### 基础8 6 比值、百分点与交互项

时延从 100 ms 降到 90 ms，是降低 10%；成功率从 98% 到 99%，是上升 1 个百分点，相对提升约 1.02%。指标越大越好还是越小越好，必须先说明。

对“无 PP / 有 PP”各自的缓存开关收益，需要四组：A 无 PP 无复用；B 无 PP 有复用；C 有 PP 无复用；D 有 PP 有复用。若 Y 是可比较的同口径原始耗时，交互项为：

**I＝YD－YC－YB＋YA**。也就是先算D相对C的变化，再减去B相对A的变化。

前一项表示 PP 布局内“开复用改变了多少耗时”；后一项表示无 PP 布局内同一件事改变了多少。两者之差才是该尺度上的交互。若 I 为正，表示 PP 布局中的复用效果比另一布局更差一些，但必须同时检查两种布局是否还改变了 DP、TP 等条件。

例：A＝100 ms、B＝80 ms、C＝120 ms、D＝115 ms。无 PP 时复用节省 20 ms；有 PP 时仅节省 5 ms；I＝15 ms。但是 D 仍比 C 快，不能写成“PP 下开启缓存让请求变慢”。

交互项只能帮助描述对照结果，不能告诉我们具体是哪一行代码导致它，也不建议为了计算它而在资源不足时强行改动多个并行参数。

### 基础8 7 相关、候选原因与已确认根因

“开缓存时变慢”是现象；“某个等待变长”是定位线索；“只改变这一等待的实现，异常消失且指标恢复；恢复旧条件可再现”才更接近因果闭环。

公开 issue 描述相似故障，可以提升排查优先级；某个 PR 修复相关问题，可以提供对照候选。但 issue 自动关闭不等于已修复，PR 合并不等于客户已经使用，也不等于客户问题已经被实验解决。

实验停止条件应分层：配置不可启动、输出不正确、传输失败回退、有效复用不足、有效复用正常但净成本过高，分别形成不同结论。不要把它们统称为“池化与 PP 不兼容”。

## 1 最终结论

**可以确认的是一项客户报告的组合性能问题，不能确认的是其根因。** 客户在GLM-5系列、昇腾、Mooncake与HIXL路径中反馈“池化与PP一起有劣化”。原始材料没有劣化比例、完整启动配置、逐请求日志或对照测量，因而不足以证明“KV池化与PP先天不兼容”。

本次公开源码核对反而表明：缓存对象可以按PP阶段、rank和本地层范围组织；池化不要求将全模型所有层的KV先收集成一块。真正需要定位的是**具体版本和配置下的分片适配、保存与加载生命周期、有效复用，以及额外开销对流水线关键路径的影响**。

| 最终判断 | 证据状态 | 对当前工作的意义 |
|---|---|---|
| 池化与PP存在必然结构冲突 | 不支持该结论 | 删除其作为根因的表述，保留为具体实现可能不匹配的假设 |
| 保存同步与写池链路值得优先排查 | 有直接上游修复和相似故障依据 | 补测PUT、发布完成、后台保存、缓冲复用屏障，不能只测读缓存 |
| LMCache材料可直接解释客户Mooncake故障 | 不成立 | 两条路线分别取证；LMCache用于候选方案与兼容性审查 |
| 原四象限实验可直接执行并归因 | 需要修订 | 修正DP/TP混杂、池化路径不一致、缺少基线项等问题 |
| 客户根因及劣化幅度已经确定 | 未确定 | 保留明确待取证项，以客户实际栈完成闭环 |

**优先顺序：**先冻结客户实际版本和P/D拓扑，确认“池化”的实际数据流；如包含共享缓存复用，在原2P1D部署中保持必要的P→D传输，只切换共享复用；优先检查PP阶段写池、保存同步和失败回退；再根据日志决定是否检查分片地址、有效命中或资源竞争。LMCache替代路线另行验证。

本报告给出的是完成源码核对后的最终分析判断与可执行取证方案，状态为“分析完成，客户环境复现未完成”。这两个状态不能合并为“已定位根因”。

## 3 独立分析的问题模型

### 3.1 三类缓存路径必须区分

本地前缀缓存是在当前实例内复用已有KV；外部共享缓存是在实例之间通过存储与传输复用KV；PD传输则是将本次请求在P侧生成的KV交给D侧继续解码。这三类能力可能同时存在，但收益来源、数据流和开关不同。

2P1D表示服务角色和副本数量，PP表示一个模型实例内部按层划分阶段。“两个P组”不能等同于“PP2”；一个跨两个物理节点的PP实例也不等同于两个独立P副本。

在当前上游，外部缓存可由AscendStoreConnector加Mooncake后端实现；P→D交接可由MooncakeConnectorV1承担，二者可经MultiConnector组合。客户实际是否使用这组实现，仍要以完整kv_transfer_config为准。[依据：官方KV Pool职责说明](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/docs/source/user_guide/feature_guide/kv_pool.md#L5-L9)

### 3.2 池化收益取决于有效复用和关键路径成本

一次查找显示命中，不代表所有PP阶段需要的KV均可用；传输成功也不代表已写入正确的NPU缓存，更不代表调度器实际跳过了对应prefill计算。需要连通“查找命中→分片齐全→加载完成→实际少算”的证据链。

池化能够带来的收益，是实际省下的计算及可能获得的容量收益；代价包括索引查找、GET和PUT、缓存发布、注册与拷贝、同步等待及失败重算。判断应看关键路径上未被计算重叠隐藏的净成本，不能把并行执行的所有操作耗时简单相加。

对PP而言，某个阶段的额外等待、负载不均或保存屏障就可能拖慢整条流水线；无需先假设存在“全模型KV收集”。对PD而言，P侧节省计算也未必变成端到端收益，D侧服务能力、路由排队和P→D交接都可能限制吞吐。

### 3.3 路由亲和与共享缓存可能相互影响

P侧KVC亲和可提高本地或近端命中，也可能把请求集中到少数副本，引入排队与负载不均。共享池能减少重算，但可能增加远端读写和共享链路竞争。因此需要同时观察每个P副本的有效复用率、排队时间、负载和远端流量，不能只追求总命中率。

独立分析阶段的判断是：现场现象可以由实现缺口、额外开销或实验混杂解释；应先确定实际链路与故障签名，再选择验证假设。该判断随后得到公开源码的支持。

## 4 客户路线的源码结论

### 4.1 池化没有全模型整块这一强制前提

Mooncake Store接受字符串key与多个buffer及其长度；Transfer Engine处理源地址、目标区域、偏移和长度，底层不要求一个对象对应完整模型的所有层。由此可按PP阶段组织对象，但底层通用接口本身不保证上层适配正确。[Store多buffer接口](https://github.com/kvcache-ai/Mooncake/blob/0d1a8040faebb7c127c8901840a38c2ff57e80c5/mooncake-store/include/pyclient.h#L382-L410)；[传输请求结构](https://github.com/kvcache-ai/Mooncake/blob/0d1a8040faebb7c127c8901840a38c2ff57e80c5/mooncake-transfer-engine/include/transport/transport.h#L60-L80)

vllm-ascend的AscendStore进一步提供直接证据：PoolKey包含pp_rank等分片维度，worker按本阶段实际KV张量建立地址、stride和每块字节数；D回写P侧布局时存在按PP partition拆分key、地址与长度的处理。因此“命中后必须先gather全模型缓存”不是普遍实现事实。[PoolKey定义](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/metadata.py#L120-L163)；[本地KV几何](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py#L963-L987)

### 4.2 PP支持是版本和路径相关的

当前MooncakeConnectorV1读取P侧并行拓扑，但明确断言decode侧PP为1。这意味着原整理稿“P/D组内都开PP”的表述需要降为待核实项；若客户D侧确实PP大于1，要确认其connector、runner、自研改动或分支，不能直接套用当前默认实现。[D侧约束](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_p2p/mooncake_connector.py#L2222-L2242)

当前Mooncake Store的layerwise后端也有PP支持及拓扑校验，但相关支持于9月22日合入，晚于9月21日的客户反馈。当前代码能反驳“原理上永不支持”，不能证明客户当时所用版本已经支持。[当前layerwise校验](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/backend/mooncake_layerwise.py#L177-L198)

### 4.3 HIXL fabric mem需按角色和版本核对

当前Mooncake代码只允许Store初始化路径启用相应fabric mem选项，普通P2P传输引擎不会直接继承这个开关；Store和PD传输还可按角色选择不同链路。这说明“底层都是HIXL”不能替代实际传输路径的确认。[Store专用开关](https://github.com/kvcache-ai/Mooncake/blob/0d1a8040faebb7c127c8901840a38c2ff57e80c5/mooncake-transfer-engine/src/transport/ascend_transport/ascend_direct_transport/ascend_direct_transport.cpp#L187-L201)

需核对实际内存分配和注册方式、D2H/H2D/D2D路径、buffer pool及异步配置。这里的约束属于具体版本的工程实现，不能上升为PP与池化的数学或架构必然性。

## 6 候选原因和可证伪条件

优先级按客户路线相关性、公开证据直接性和取证成本排序，不表示已经估计出发生概率。先检查启动和输出正确性，再讨论性能。

| 优先项 | 候选原因 | 支持线索 | 最小验证与排除条件 |
|---|---|---|---|
| 1 | PP阶段写池或保存同步开销 | 11478、15636、12763 | 逐阶段PUT、队列、发布完成和缓冲复用等待；若无失败且关键路径等待很小，应降级 |
| 2 | 层或rank分片元数据不匹配 | PoolKey及stage本地地址的适配要求 | 核对层范围、cache group、shape、stride、块字节、注册长度、键维度；用输出一致性检查区分正确性故障 |
| 3 | 命中承诺未变成有效复用 | 完整分片与调度跳过计算需联动 | 同请求比较逻辑命中、成功加载、实际少算token；若三者一致，转向成本分析 |
| 4 | Store与PD传输竞争或配置不匹配 | 角色链路分离及fabric历史变更 | 分开记录GET、PUT、P→D流量和失败；核对注册模式、通道、HIXL版本及初始化日志 |
| 5 | 流水线等待与路由负载不均 | PP关键阶段及P侧粗糙亲和策略 | 每stage利用率、每P队列、D等待、批量大小与路由分布；固定路由做对照 |
| 6 | 工作负载和实验口径混杂 | 尚无一致对照，原方案改变并行布局 | 固定长度、到达率、缓存状态及其他开关；看劣化是否仍存在 |

### 6.1 需要补齐的请求时间线

从请求到达开始，记录路由与P排队、外部lookup、GET与写回、prefill各PP阶段、PUT及缓存发布、P→D交接、D等待、首token和完成。部分动作会重叠，应按依赖关系找到关键路径，而非把各段平均时长直接求和。

PUT可能影响当前请求，也可能通过保存队列、下一步缓冲重用或缓存发布时间影响后续请求。只比较“命中请求的pull耗时”，会漏掉这一类已被上游修复记录指出的开销。

### 6.2 根因成立需要形成闭环

较强的根因证据应同时满足：同一部署下现象可重复；日志或时间线显示候选环节异常；一个针对该环节的受控变更改善异常及业务指标；恢复原条件能再次出现问题，或有等价的反事实对照。仅有静态代码分支、相关PR或一次跑分差值都不足以结案。

## 7 LMCache代码证据的复核

这一节审查的是第二批材料提出的替代路线。它可以发现LMCache自身的兼容性风险，但不作为客户Mooncake根因证据。已同时核对LMCache与LMCache-Ascend的v0.4.4，以及本次检出的公开主线快照。

### 7.1 E1至E8的最终判定

| 项目 | 已核实的代码事实 | 对原解释的修正 |
|---|---|---|
| E1 后端互斥 | P2P或PD与use_layerwise同时启用会被拒绝 | 校验没有读取PP参数，不能推出PP本身不支持；截图配置为layerwise false且未开P2P/PD |
| E2 首rank保存 | MLA路径可仅首rank维护缓存，其他rank被标为passive | 它原本用于重复KV去重；须检查PP下作用域，不能直接宣布非首rank全部丢层 |
| E3 异步保存限制 | layerwise保存分支断言不能store_async | 适用于该分支执行时，并非所有PP服务启动必报错 |
| E4 失败重算 | P2P pull失败可将块标为invalid，交给vLLM重算 | 日志出现才证明请求触发；源码有回退不代表现场已回退 |
| E5 传输通道 | 支持hccl和hixl，示例有不同推荐等级 | 属于LMCache支持矩阵，不等于客户Mooncake fabric路径 |

## 8 LMCache替代路线的具体风险

### 8.1 首rank判定和TP广播作用域不一致

在截图对应的classic connector、MLA及save_only_first_rank启用路径中，上游将metadata.worker_id设为parallel_config.rank，first_rank判定固定为全局worker 0；广播函数却来自get_tp_group。对DP1、TP8、PP2的常规布局，第二个阶段是全局rank 8至15，其TP组内源rank 0实际是全局rank 8。

vLLM v0.18.0源码已经交叉确认这些rank语义。因此，“只有全局0为active”与“每个TP组需要自己的发送者”存在明确的静态作用域不一致风险，值得在LMCache验证中优先检查。仍不能据此指定运行结果一定是死锁、丢层或退化，更不能把它迁移为客户Mooncake根因。

验证时逐worker记录global rank、TP rank、PP rank、metadata.worker_id、first_rank、use_mla、passive、层范围及storage_manager，再用同一前缀的连续请求检查各stage的保存、广播与实际命中。不要把关闭first-rank或打开layerwise直接当成修复；它们还会改变lookup worker、缓存容量和传输行为。

依据：[LMCache元数据和广播绑定](https://github.com/LMCache/LMCache/blob/6fbec463e3c047fffb4e22c97508f03b057de3bc/lmcache/integration/vllm/vllm_service_factory.py#L145-L215)、[first_rank定义](https://github.com/LMCache/LMCache/blob/6fbec463e3c047fffb4e22c97508f03b057de3bc/lmcache/v1/metadata.py#L53-L70)、[vLLM组内广播源语义](https://github.com/vllm-project/vllm/blob/bcf2be96120005e9aea171927f85055a6a5c0cf6/vllm/distributed/parallel_state.py#L593-L605)、[TP和PP分组](https://github.com/vllm-project/vllm/blob/bcf2be96120005e9aea171927f85055a6a5c0cf6/vllm/distributed/parallel_state.py#L1538-L1569)。

### 8.2 原实验没有配置跨实例池化

截图YAML配置local_cpu、use_layerwise false、store_async true，kv_role为kv_both。它表明本地缓存可保存和加载；在没有额外环境覆写时，enable_p2p和enable_pd默认为false，没有controller与peer配置，不能声称已覆盖跨实例共享或客户Mooncake路径。[P2P默认值](https://github.com/LMCache/LMCache/blob/6fbec463e3c047fffb4e22c97508f03b057de3bc/lmcache/v1/config.py#L131-L135)；[真正的P2P实例配置](https://github.com/LMCache/LMCache-Ascend/blob/19c13d849d6bcdea6316cdd8674fae210b3326f4/examples/kv_cache_reuse/share_across_instances/p2p_sharing/instance1.yaml#L1-L25)

### 8.3 硬件和版本表述需收紧

当前GLM-5.1指南写的是8张卡、每卡2芯片，共16个芯片，推荐布局为DP2乘TP8。改成PP2乘TP8不属于同一已验证配置；“16芯片”也不能写成“16张物理卡”。指南在本次主线存在，v0.4.4 tag中没有；指南建议安装v0.4.4，并不表示该tag内已经包含指南。

截图中的A2八设备一定能启动、权重约280GB，以及所有docker补丁都必须应用，均缺乏对应范围的验证。应按实际checkpoint、HBM、目标路径和版本判断；单机能启动不代表2P1D跨实例问题已经复现。[GLM指南的硬件与软件条件](https://github.com/LMCache/LMCache-Ascend/blob/19c13d849d6bcdea6316cdd8674fae210b3326f4/docs/recommended_deployment_guide/glm5.1/glm5.1-single-node-lmcache-deployment-guide-ddr-vs-hbm.md#L7-L63)

## 10 修订后的实验设计

### 10.1 第一轮直接回答客户问题

先确认客户所称“池化”是否包含跨请求共享复用或其他卸载路径。如包含共享复用，保留客户模型、量化、2P1D、P/D并行拓扑、MTP、EP、图模式、批量上限和路由策略，比较共享复用关闭与开启。必要的P→D KV传输必须保留；若一个开关同时关闭PD传输与共享复用，应先拆清配置，不能当成有效对照。

最少实验先以M1确认完整跨P复用，再以M2全未命中、M3稳定远端复用各做开关对照，记录业务指标及关键路径。混合或低复用负载只按现场差异追加；无PP布局也仅在需要确认交互时追加。这样可避免一开始换引擎或改并行布局而丢失原问题。

### 10.2 四象限只在可比条件下使用

| 组别 | PP | 共享缓存复用 | 作用 |
|---|---|---|---|
| A | 关 | 关 | 对照基线 |
| B | 关 | 开 | 无PP布局内的复用效果 |
| C | 开 | 关 | PP布局的无复用基线 |
| D | 开 | 开 | 客户关注的组合效果 |

对同口径原始成本Y，交互项为：**I＝YD－YC－YB＋YA**，等价于比较“PP下开复用的成本变化”和“无PP下开复用的成本变化”。若Y为耗时，正值表示在该加性尺度上出现额外成本；它不是未加限定的普遍“冲突损失”。

对吞吐，更直接的结果是分别报告B/A与D/C的增益比例，并结合相同SLO下的有效服务能力。尾分位数、比值与平均阶段时间不能混加。重复实验需报告波动或区间，不把三次同向当成统计显著。[交互与混杂的方法依据](https://www.itl.nist.gov/div898/handbook/pri/section5/pri594.htm)

### 10.3 分开部署决策和机制定位

固定总资源时，从DP2TP8切换为DP1TP8PP2会改变副本数；从TP8切换为TP4PP2会改变张量并行。它们可以回答“哪个完整部署更适合负载”，不能回答“PP单独导致多少损失”。若资源不允许保持DP和TP，就如实报告比较边界，不强行称为单变量实验。即使TP和DP相同，改变PP通常仍改变活跃设备数或层分布，因此四象限首先确认的是两种具体并行布局的复用效果差异。

单机用于验证启动、缓存完整性、rank作用域和局部等待；跨节点用于验证实际拓扑下的传输、竞争和端到端业务表现。节点数、链路和缓存容量改变后，劣化可能增大也可能减小，不能将单机数值自动标为跨机下界。

## 11 负载和观测要求

### 11.1 控制请求与缓存状态

固定输入输出token长度分布、生成参数、负载强度、请求数及持续时间。调整前缀复用比例时尽量维持总输入长度分布，通过预热指定前缀控制复用机会；0%、30%、60%、90%只是可选目标档位，不要求全部扫描；最少用例先测全未命中和稳定复用，最终以实际有效外部token复用率为准。

分别记录本地APC命中、外部逻辑命中、加载成功、完整阶段覆盖及实际少算token。跨rank完整命中不能用某一个rank的命中率代替；具体算法应与实际分层和cache group语义一致。0%复用档仍是识别固定开销与资源竞争的必要对照，不能简单排除。

开放式到达率与封闭式并发上限回答不同问题。固定qps为0.3的试验不能直接量出最大吞吐；用户数也不等于稳态并发。重复同一数据和随机种子可能留下缓存，应记录清理、预热及运行顺序。[vLLM压测指标与负载说明](https://docs.vllm.ai/en/latest/benchmarking/cli/)

### 11.2 每组最少保留的数据

| 层面 | 最少记录项 | 用于区分什么 |
|---|---|---|
| 业务 | 成功率、tokens/s、TTFT、TPOT、E2E的P50/P90及SLO；样本足够时看P99 | 业务劣化类型；满载与未满载的差别 |
| 请求 | request_id、长度、到达率或并发、路由、逻辑命中、实际少算token | 请求是否可比，复用是否真实 |
| PP阶段 | 层范围、TP/PP rank、group、shape/stride、每块字节、KV就绪时间 | 分片完整性和最慢阶段 |
| 读写 | lookup、GET、PUT、发布、写回、队列等待、保存屏障 | 读成本、写成本及未隐藏的等待 |
| 传输 | Store与PD分别统计字节、调用数、重试、失败及回退 | 数据量、碎片化、共享资源竞争 |
| 资源 | 各stage利用率、HBM、Host缓存、P队列、D等待、链路状态 | 容量压力、流水线气泡与调度不均 |

TPOT和ITL在投机解码下不应无条件互换；跨进程时钟需对齐，或使用单侧可比较时间线。先确认profile中确实能看到所需事件，再依赖其作分阶段结论。

### 11.3 结果分类

不能启动归为配置或接口兼容问题；输出不一致归为正确性问题；失败回退归为可靠性与重算问题；有效复用正常而指标变差归为性能问题。每类需要不同证据，不能用统一的“兼容性劣化”掩盖差别。尾延迟样本量不足时，应保留不确定性。

## 14 怎样把分析结论变成实验结论

### 14 1 不同判断需要不同证据

| 本报告中的判断 | 最少实验 | 通过之后能确认什么 |
|---|---|---|
| 外部命中应真正减少prefill | M1 来源P1的KV经实际发布者写池，P2首次加载 | 已测前缀的分片完整、实际少算与正确性 |
| 写池和保存等待可能贡献开销 | M2全未命中开关对照，再按信号做M4 | 具体保存环节对该条件下退化的贡献 |
| 命中并不保证端到端有收益 | M3同输入同负载，核对有效复用和业务指标 | 实际省计算后净收益的正负及大小 |
| PP布局可能改变池化收益 | 在C/D基础上追加X1的A/B | 两种已声明并行布局的复用效果差异 |
| 一个具体补丁或配置是根因 | M4原版、单点修正、回退或等价反事实 | 该变更对可重复异常和业务结果的因果贡献 |
| LMCache首rank存在作用域风险 | 另立LMCache路线，逐stage核对active保存者与TP广播源 | 仅该LMCache版本和路径的实际运行结果 |

三个固定用例对应多个条件与重复轮，不是只发三次请求。推荐从M1的3个前缀及M2/M3每条件50条筛查开始；需要稳定判断时每条件200条起、3对重复。新增样本、模型热身和共享池预热都另计成本；P99验收通常需要更多同条件样本。

### 14 2 最先做什么 最后如何结案

先冻结实际P1/P2/D版本与配置，确认“池化”的真实数据流及APC状态。在完整PD服务路径中固定路由，不绕过D；关共享池时保留必要P→D交接。先证明P2本地未命中、外部必要分片齐全、加载被采用及prefill实算减少，再讨论收益。

M2定位没有复用收益时的查询和写池代价；M3确认真正少算后的净收益。若已有稳定错误或明显等待，只选最敏感负载做M4，不强行完成全量参数扫描。恢复原条件后异常返回，且针对性修正同时改善异常、业务和正确性，才足以将候选原因升级为已确认贡献或根因。

仍要注意版本和计时：当前Ascend已有GET与保存延迟释放指标，但目标版本未必有；vLLM 0.18客户端的首choices计时未必等于首有效token，必须校准。benchmark输出的命中、token和成功数都应说明口径，不能把缺失指标当0。[Ascend指标](https://github.com/vllm-project/vllm-ascend/blob/4ebb3090fc3c13c26557dcaae353882e70246649/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/metrics.py#L82-L128)；[客户端计时实现](https://github.com/vllm-project/vllm/blob/bcf2be96120005e9aea171927f85055a6a5c0cf6/vllm/benchmarks/lib/endpoint_request_func.py#L262-L333)

若改变整套镜像后变好，只能确认新组合改善；若只测单机或小模型，只能报告该子场景；若M2/M3均正常，只能写当前条件未复现。机制实验完成后恢复客户原APC、路由、输出规则与真实负载，再验收最关键的原版与修正对照。

| graph与kernel | 图执行与设备计算内核 | 首次编译、捕获或加载可能带来启动成本，需独立模型热身 |
| dtype与metadata | 数据类型与元数据 | 前者影响数据表示和字节数，后者记录地址、层范围及布局等信息 |
| cache group与cache family | 缓存组与缓存类别 | 实现区分不同缓存结构的维度，不等于一个用户请求 |
| ACL与VMM | 昇腾运行时API及虚拟内存管理相关接口 | 影响内存分配、地址映射与注册；不是缓存命中算法 |
| ADXL | 相关传输实现所用的软件接口名称 | 与HIXL及具体后端的关系以版本和初始化日志为准，不按名称推断 |
| API与HTTP | 程序接口与网页服务常用请求协议 | 客户端向地址发请求；返回200不保证缓存收益或输出正确性 |
| URL与端口 | 服务地址与同一地址下的服务编号 | localhost或127.0.0.1只指当前执行命令的机器 |
| SSE与流式输出 | Server Sent Events，逐事件返回响应 | 首事件可能为空；事件数不等于token数 |
| JSON与JSONL | 对象数据格式与每行一个JSON对象的文本文件 | 本指南custom数据是一行一条请求，不是外层数组 |
| CSV | 逗号分隔的表格文本 | 可用Excel打开；空表字段不是服务现成自动采集值 |
| Bash与PowerShell | Linux常用终端语言与Windows终端语言 | 指南的服务命令为Bash，不能直接粘贴到PowerShell执行 |
| 容器与镜像 | 隔离运行环境与其打包模板 | 相同名称的镜像可能被更新，需记录实际镜像标识和组件版本 |
| 环境变量 | 进程启动时读取的配置值 | 修改终端变量不表示已运行服务自动生效；以实际配置和日志为准 |
| Prometheus指标 | 常见文本格式的监控指标 | /metrics端点可能在各实例，proxy未必转发 |
| counter | 单调累计计数器 | 用同标签前后差；重启归零后不能直接相减 |
| gauge | 当前状态量 | 观察轮内变化或峰值，前后差不是累计发生量 |
| histogram | 按区间累计的分布 | sum除count可得该操作均值；分桶也影响分位估计精度 |
| label与delta | 指标标签与增量 | 按同实例、模型、引擎维度比较，防止把不同计数混合 |
| SLO goodput | 满足服务目标的有效完成速率 | 与单纯完成吞吐不同，超时或不达标请求不能算达标 |
| EOS | End Of Sequence，生成结束标记 | ignore-eos用于强制长度的诊断，不代表真实用户输出规则 |
| seed | 随机种子 | 有助复现输入或生成，但不保证分布式计算完全确定 |
| NA | 不可用或没有采到 | 不等于0；缺指标不能写为零错误或零耗时 |
| diff与patch | 变更差异与补丁 | 用于证明只改预定项；完整镜像升级不等于单点修正 |
| UT | Unit Test，单元测试 | 通过不能代替NPU通信、模型正确性和业务性能测试 |

## 附录二 先做自查

## 附录三 自查答案

1. 2P1D 的 2 是 P 服务组或副本数量；PP2 的 2 是一个模型实例内部的流水线阶段数。
2. 不能，可能只是 P1 本地 APC 命中。需要证明目标请求由缺少本地条目的另一个实例处理，并实际从共享池加载且有效少算。
3. 使用已证实归因于外部缓存的实际少算部分评估收益。继续核对块对齐、阶段完整性、加载失败、写回、回退及调度是否采用命中结果。
4. 不一定。每个 TP 组有自己的组内 rank 0；全局 rank 0 只有一个。必须核对映射和广播范围。
5. 不能。异步提交不是完成，缓冲重用等待可能把保存成本转移到下一步，应看完整生命周期和关键路径。
6. 缓存让 PP 配置从 120 ms 变为 115 ms，仍改善 5 ms；无 PP 时改善 20 ms，收益不同。交互项 15 ms，不能改写为 PP 下开缓存增加 15 ms。
7. 不能。它主要反映该发送负载下的服务表现，需要在明确负载与 SLO 下探索容量才能谈最大能力。
8. 不能。多个因素同时变化，只能暂时说明新部署的结果不同；需做针对候选原因的受控对照并连接异常与业务指标。
