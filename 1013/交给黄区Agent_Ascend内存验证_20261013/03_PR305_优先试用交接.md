# PR #305 优先试用：给黄区 Agent 的交接

结论：先验证 #305 是否让实际缓存服务的 L1 内存池恢复到主仓的普通 CPU `torch.empty` 分配路径，再验证这块内存能否同时用于文件直接读写和 NPU 传输。补丁已加载、路径已切换、现场故障已解决是三个不同结论，必须分别回报。

本文件可以单独交给另一侧 Agent。旧交接中的 #174 C++ 改造暂缓；这里先试 #305，主仓与环境版本保持现场基线。另一侧只需通过文本回传，不需要传原始文件。

## 1. 故事背景与目标

结论：我们希望通过改变内存来源解决兼容性问题，减少每次文件读写增加临时复制的需要。

LMCache-Ascend 现场报告：某类 `aclrtMallocHost` 内存直接用于 O_DIRECT 文件读写时失败，增加普通内存中转后恢复。具体内核拒绝机制尚未核实。原主仓 PR #5687 已关闭，本轮不恢复提交。

导师提到 `torch.empty`。新候选 #305 正好删除 Ascend 对 `LazyMemoryAllocator` 的替换，使这类缓存池恢复到主仓的普通 CPU Tensor 分配，再通过 `NpuPinMemoryBackend` 注册给 NPU。它不是 `torch.empty(..., pin_memory=True)`，也不是给原来的 ACL 内存套一层 `torch.frombuffer`。

```text
A 组：现场原方案（如果该替换实际启用）
LazyMemoryAllocator → Ascend 替换 → alloc_pinned_ptr → aclrtMallocHost

B 组：仅应用 #305
LazyMemoryAllocator → 主仓普通 CPU torch.empty
                    → 分块 aclrtHostRegister → 文件与 NPU 使用
```

“延迟扩容”在这里指逐步注册、逐步开放池容量；不能理解成 torch 每次只申请一个 64 MiB 小 Tensor。主仓先建立覆盖最终容量的 backing Tensor。

## 5. 最短验证路径

### E0：证明补丁和分配路径真的变了

结论：B 组的类方法来自主仓 lazy allocator，真实池来自普通 Tensor，并实际执行注册，才算路径切换生效。

记录 A/B 类方法来源、池首地址、实际 allocator 类型、注册调用与返回值。可在独立验证脚本或隔离测试服务中为真实注册/解绑调用添加计数日志，保持参数、返回值与原行为不变。不能 mock ACL、强制返回成功，或用自造普通 Tensor 代替实际池后声称服务已切换。

B 组不能继续打印 `Routed LazyMemoryAllocator pool through alloc_pinned_ptr`。但这条日志消失、`LMCACHE_ASCEND_PATCHED=True` 或全局标志不存在，都不能单独作为成功依据。

旧 `probe_memory.py --mode native` 调用的是 C++ `alloc_pinned_ptr`，#305 没改这个入口；该探针结果不能证明 #305 生效。需要使用真实 `LazyMemoryAllocator` 产生的池或对象。

### E1：小池、真实后台扩容与生命周期

结论：先用小池发现注册和清理问题，再使用现场真实容量；不做主机注册额度耗尽实验。

使用现场类接口建立实际 lazy allocator：建议初始 64 MiB、最终 192 MiB，即 `67108864` 与 `201326592` 字节；对齐值满足实际文件系统需求。设置合理超时，等待真实后台扩容线程完成，不手工把容量或注册结果改成完成。

对于与公开参考实现一致的 B 组：初始注册 64 MiB，后台再注册两块 64 MiB；成功记录应覆盖整个 192 MiB，通常为三个登记区间。现场实现不同则按实际初始/最终容量解释计数，不能硬凑三个。

观察 `_curr_size`、`_final_size`、`_pin_record` 及真实 ACL 返回值。扩容到 100% 不代表每块注册都成功，因为源码允许注册失败后继续扩容。

在同一独立进程中创建、完成操作、关闭并释放三轮；旧对象及视图不再使用后再进行下一轮。每轮确认：扩容线程结束、成功注册对应的解除注册成功、没有新增 `507899` / `107002` 等错误。若解除注册失败，停止下一轮，保留记录，不继续制造泄漏。

不要把 `close()` 没有异常当成解绑成功。公开参考 lazy `close()` 未检查 `unpin_memory()` 返回值；需要观察实际解绑返回值。NPU 操作未确认完成时，不释放底层内存。

小池通过后，再对实际现场容量运行一轮后台扩容和关闭检查。不要为了匹配 PR 描述，盲目申请 64/128/351 GiB。

### E2：同一缓冲的文件直接写读和 NPU 数据链

结论：必须验证 PR 恢复后的真实池内存，不能用普通中转复制掩盖失败。

- 使用真实池中的一块已开放内存，另测后台新扩容区域；按现场 API 取得对象或切片。记录实际文件读写所接收的地址与长度。
- 建议复用历史 9 MiB（`9437184` 字节）或现场实际对象大小，主动写入已知模式；`torch.empty` 内容未经初始化不能用于比较。
- 查询目标挂载的 O_DIRECT 要求，分别记录地址、长度、文件偏移的余数。ACL 的页范围注册处理不是文件系统地址对齐的证明。
- 直接把该池内存交给文件写和文件读，记录实际返回字节数，并逐字节比较。读验证使用独立预制数据，避免一次写失败使读实验无法判断。
- 不使用 `bytes()`、额外 mmap staging 或旧主仓中转补丁作为本次直接读写的传入缓冲。原中转补丁仍在时，不能用它带来的成功作为 #305 证据。
- 对相同内存完成已知 NPU 数据 → CPU 池 → 文件写 → 文件读 → NPU 的完整链，核对数据。观察 NPU 到 CPU（D2H）和 CPU 到 NPU（H2D）两方向，并在最终校验及释放前等待设备操作完成。

通用 `copy_` 数据正确，只证明这一 API 链通过；不能自动证明真实 MP native 传输、映射指针或异步性能正确。后者由 E3 验收。

### E3：真实 MP 服务的最小验收

结论：低层通过后，在原传输模式和实际 TP 配置下复测现场场景，才可声称现场行为符合预期。

复用之前的服务验证方式，使用独立测试缓存与进程：

1. 首轮生成数据，确认真实 L2 文件写成功。
2. 等待写入完成，正常关闭本次自有服务进程，保留测试 L2 文件。
3. 重启本次服务，确认 L1 是新池，磁盘数据来自上轮；首先发送预期命中 L2 的请求。
4. 记录第一个 load 请求及第二个请求：是否完成、L2 实际读取、加载数量、设备传输、HTTP 状态和输出正确性。
5. 正常关闭，确认后台线程与注册资源清理。若两组首个请求都挂死，#305 尚不能解释或解决这部分现象。

HTTP 200 或第二次请求正常都不足以单独通过。必须确认第一请求未挂死，且确实完成 L2 恢复并将正确数据交给 NPU。A 组不能复现时可记录 B 组功能通过，但不能下“已证明修复原故障”的结论。

## 6. 固定判定表

结论：按最弱未完成环节限定结论，不以一次成功代替整条路径验证。

| 结果 | 可下结论 | 下一步 |
|---|---|---|
| 只确认候选文件加载，真实 allocator 未变 | 补丁文件已加载；行为未生效或不适用 | 查实际入口、配置和进程 |
| 普通 Tensor 池与注册调用已确认 | 分配路径切换生效 | 继续 E1–E3 |
| 文件通过，但注册失败或 NPU 失败 | 文件兼容性改善；设备侧未通过 | 不进入正常使用，分析错误 |
| 文件和 NPU API 链通过，MP 未测 | 低层功能通过；真实 MP 未核实 | 继续 E3 |
| B 正确运行，但出现 pin 失败后回退同步 | 基本功能通过；注册与异步目标未通过 | 不能当完整验收 |
| A 可复现、B 路径已变且 E1–E3 通过 | 该版本配置下，#305 对现场问题有修复证据 | 保留复现与修复数值 |
| A 无法复现、B E1–E3 通过 | 候选在该环境功能通过；原故障修复因果未核实 | 如实记录，不追加大范围实验 |
| 清理失败或重建后错误累积 | 生命周期验收未通过 | 停止循环，定位注册/解绑 |
| 实际非 lazy | #305 不覆盖本次实际分配入口 | 回到实际入口分析 |

本次不保证其他 CANN/驱动、其他设备、严格页缓存绕过或性能收益；没有实测的项目写“未核实”。
