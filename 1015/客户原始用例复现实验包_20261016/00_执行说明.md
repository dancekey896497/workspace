# 客户原始配置：本侧 NPU 复现实验包

日期：2026-10-16。

**结论：本包落实两条互补链路：真实 MP 服务复刻客户配置，以及同一个真实 L1 对象经过 NPU 多平面搬运前后的 native FS 对照。客户完整 DS 请求链路仍未核实，不把小样例成功写成客户问题已解决。**

这是本轮执行入口，替代此前只安排单个组件实验的执行顺序。PR305按已经应用推进；不重查安装、不分析退出 core、不升级依赖、不修改业务源码。已有 Qwen 正配额实验无需再做。

## 1. 已知事实与本轮目标

**结论：目前只有客户 LMCache server 的启动基线，还没有客户 DS/vLLM 完整启动命令和真实 KV 布局。**

- 客户 server 原命令保存在 [客户原始启动命令.sh](客户原始启动命令.sh)。这个文件是原始记录，不要原样执行而占用原端口、目录及容器名。
- 客户报告主仓 `0.5.6rc6.dev7`、Ascend `0.5.6rc6.dev1`，已手工覆盖 PR305 的 `__init__.py`。接受这一前提，不以版本字符串没有变化认定补丁未应用。
- 用户报告 GPU 同参数能通：提高 NPU 专属路径排查优先级；GPU 实际 allocator、KV 布局、配额与系统调用证据未取得，不要求另一侧提供 GPU 环境。
- 本侧此前使用不同镜像、MainB 源码副本和普通 K/V 格式16，已完成小链路落盘；测试文件系统为 overlay，未证明等同客户 SSD 挂载。
- Qwen buffered 正配额成功，以及未配额时写后清理，均已有证据。它们不证明客户 DS 的 DIO 路径正常。
- 客户 AI 文本中的未对齐 guard 来自合成 buffer 实验；**真实 DS 失败对象的地址、长度及原始错误仍未核实**。

这次不重复问机主。由本侧 NPU Agent 执行，尽可能使用客户原镜像和实际 SSD 文件系统；做不到的差异照实记录并继续机制验证。

## 2. 原命令真正控制了什么

**结论：原命令未显示必然违反 O_DIRECT 条件的参数；它同时启用写盘和写后清理两条机制，不能只看目录空。**

以下默认值核对于公开主仓固定提交 `240506edf5146613b015e9e2e51189f1fc099b76`，它是已记录 dev7 的候选，不声称是客户精确 commit。

| 项目 | 源码结论 | 不能直接推断的内容 |
|---|---|---|
| 未显式写 lazy / init / align | 默认请求 lazy=true、init=20 GiB、align=4096 | 后端 pin 不支持时可能关闭 lazy，实际 allocator 须从运行信息确认 |
| L1=512 GiB | 最终容量上限；默认保存策略不必等池装满就提交 L2 | 不能据此说“没满所以没落盘”，也不能说首次一定 pin 512 GiB |
| 顶层 LRU | L1 淘汰 | 不是 L2 写入开关 |
| L2 IsolatedLRU | 按实际 salt 的配额清理 L2 | 这段脚本没登记 quota，不代表不存在外部登记 |
| use_odirect=true | 请求启用直接 I/O | 不等于每个对象实际 open 都带 O_DIRECT |
| chunk-size=4096 | 本次 MP 保留该逻辑 chunk 配置 | 不等于所有 DS group 的实际 slots 都是4096 |
| shm-size / ipc / memlock | 容器共享内存及锁页环境 | 不能单独保证对象地址、长度、映射与生命周期满足 DIO |

依据：[CLI默认值](https://github.com/LMCache/LMCache/blob/240506edf5146613b015e9e2e51189f1fc099b76/lmcache/v1/distributed/config.py#L811)、[默认保存策略](https://github.com/LMCache/LMCache/blob/240506edf5146613b015e9e2e51189f1fc099b76/lmcache/v1/distributed/storage_controllers/store_policy.py#L113)、[未知salt配额为0](https://github.com/LMCache/LMCache/blob/240506edf5146613b015e9e2e51189f1fc099b76/lmcache/v1/distributed/quota_manager.py#L86)、[零配额清理比例](https://github.com/LMCache/LMCache/blob/240506edf5146613b015e9e2e51189f1fc099b76/lmcache/v1/distributed/storage_controllers/eviction_controller.py#L347)。

## 3. 执行顺序与停止规则

**结论：执行一次环境记录、一个格式17的真实 MP 输入、一个同对象组件对照；额外对照只在对应信号出现时做。**

| 编号 | 实验或检查 | 能回答的问题 | 执行条件 |
|---|---|---|---|
| R0 | 记录镜像、已加载源码、真实挂载及已有日志 | 前次成功与客户基线究竟差在哪里？ | 必做；只读，已有结果引用即可 |
| R1 | 客户存储配置 + 格式17合成 KV + 真实 MP server | 没提交、写失败、还是写后清理？ | 必做新路径；不用原 bench 的格式16输入 |
| R1b | 同输入，仅移除 L2 eviction | 清理是否掩盖了持久文件？ | R1写后删或无法分清清理时才做；不重做正配额矩阵 |
| R1c | 恢复512GiB上限/20GiB初始注册，仍只提交小输入 | 小池是否漏掉原配置的初始注册规模差异？ | 小池通过且本侧资源允许时做一次；资源不足标未核实，不填满池 |
| R2 | 同一个 Lazy 对象，CPU填充写读→NPU格式17搬运→写读 | NPU搬运前后内容、范围、映射或同步是否出现异常？ | 必做；它覆盖未测过的 mixed dtype / 非整页逻辑长度 |
| R2b | 旧 adapter 无物理长度 view 时，显式参考 padded view | 普通 I/O 回退是否遮住了真实 DIO？ | 默认 view 确认回退时才做；仅测试参考，不当生产补丁 |
| R3 | 对首个真实错误补最小观测 | 定位应修 Ascend、主仓NPU模块还是通用存储代码 | 仅失败后；按第7节选择，不铺开新矩阵 |

客户端正常退出不是 L2 成功证据；客户端退出134也不能覆盖已独立确认的 server store 结果。本轮不调查该 core。

各组串行运行。取证完成后停止上一组自建server再开下一组，保留文件和日志；避免同时注册多个池，让本轮实验自己的内存占用干扰下一组。R2组件不需要MP server。

## 5. R1：真实 MP 路径，保持客户的存储参数

**结论：先用小池覆盖完整保存链；小池成功不能排除 512 GiB 规模相关问题。**

下面只改测试名称、目录、端口、HTTP监听范围和 L1 规模，并显式写出目标版本的 lazy/align/default-store 配置；保留 `chunk=4096`、driven、fs_native、DIO=true、4个worker、原 IsolatedLRU 参数。`run_server.sh` 不创建 Docker、不更换镜像，只在既有测试容器中启动服务。

## 6. R2：同一个 L1 对象经过 NPU 搬运前后的写盘

**结论：这一步把“NPU有没有把待写文件的数据准备好”与“文件系统能不能接受这个缓冲”分开。**

记录符号的白话含义：B是整座内存池的起点，o是对象在池里的偏移，p是对象首字节地址，q是最终交给文件系统的首字节地址。L是有效数据量，P是实际分配的整块容量，N是本次交给文件系统的字节数。正常整对象路径应有 `p=B+o`、`q=p`、`L≤N≤P`；地址对齐是检查这些地址能否整除所要求的粒度，不是检查数据内容。

```bash
"$PY" "$PACK/probe_npu_dio_chain.py" --describe
"$PY" "$PACK/probe_npu_dio_chain.py" --help
"$PY" "$PACK/probe_npu_dio_chain.py" --base-path "$WORK" --device-index 0
```

设备编号按本侧实际空闲设备调整。脚本使用真实 Lazy、真实 Ascend 多平面 D2H、真实 native FS，不经过替代 I/O buffer；NPU stream完成后才提交本轮诊断写盘。源对象、目标对象、view、allocator及NPU plane一直持有到完成。

几何是官方 `dsa_c8_4` 缩小样例：NL2/NB4/BS16/实际slots64，4plane每slot1282字节。逻辑 L=164096，A4096时物理 P=167936，尾部3840。它用于检查非整页逻辑长度，不能把这个slots64直接当作MP服务的chunk4096。

默认使用**当前真实 adapter 的 view 规则**。若旧B接口没有 padding，默认结果应显示逻辑长度及DIO回退，而非伪造DIO通过。这时才执行R2b：

```bash
"$PY" "$PACK/probe_npu_dio_chain.py" --base-path "$WORK" --device-index 0 --padded-view-reference
```

R2b只在脚本内按公开新版规则构造原地址P字节view，不改生产adapter；报告必须标“参考契约”。不能单凭它通过就认定需要给客户补 padding，也不能把旧B行为外推客户版本。

如果本侧已有 `strace`，可将R2该次运行包在 `strace -f -e trace=openat,read,write,pread64,pwrite64 -s 80 -o "$WORK/r2_syscalls.log"` 后，查本轮新key的open是否带 `O_DIRECT`。没有就标实际系统调用未核实，不安装工具。MP如需trace，只附加本轮自建server PID，并在使用后停止自己的tracer；不附加他人服务。

## 7. 首个失败决定修复方向

**结论：先用真实错误定断点，再选择最小改动；现在没有依据追加 allocator 或 driver 补丁。**

| 真实证据 | 解释与下一步 | 修改边界 |
|---|---|---|
| server无本轮提交，客户端/传输先失败 | 尚未到SSD；先查注册格式、请求、transfer完成，不归因O_DIRECT | 实际出错的connector/主仓NPU/Ascend函数 |
| store明确成功，同key随后删除 | 写盘成立，目录空来自清理；看实际salt配额 | 优先部署配置/配额登记；确有接口缺口再做Ascend适配 |
| `O_DIRECT buffer address is not aligned...`且真实q%D非0 | native在系统调用前拒绝该地址 | 查实际allocator、B/o与view偏移；只修产生错误指针的位置，不删guard |
| 地址齐，N不齐且native自动回退 | 该对象不是实际DIO验证 | 核当前adapter padding接口与物理槽位；不能只改长度越过已分配范围 |
| 传输所需字节大于真实槽位，或搬运后L1内容已错 | NPU几何/长度/暂存拷贝先出错 | 优先Ascend描述符和kernel调用；若错误源于主仓NPU plan则修该模块 |
| 地址、提交范围合法，且实际write返回EFAULT | 进入了系统调用，不能再只说“地址未对齐” | 查host/device alias、注册覆盖、映射与owner有效性；先保留该对象和完成顺序证据 |
| 未等NPU完成时错，等待后正确 | 有同步/提交时机问题；尚不能单凭此解释EFAULT | 修实际提前提交的完成通知，不用全局sync作最终补丁 |
| 同对象R2通过而真实MP失败 | 缩小到对象交接、异步生命周期或MP使用的布局/地址差异 | 在首个失败任务处加诊断，不重做已通过的组件矩阵 |
| 全部通过 | 当前环境机制链通过，客户DS/原挂载/规模尚未排除 | 不提交猜测补丁，列最小剩余差异 |

对于真实 EFAULT，后续最小补证应是**同一独立普通CPU分配注册前后**的DIO对照，或首个失败对象的原始地址/范围/完成顺序，按实际失败点选择其中一个。不要对已经由Lazy注册的区域再次手动HostRegister，不通过提前free或取消任务制造损坏来“证明UAF”。这种对照尚未预执行，也不以“注册会移动CPU指针”为前提。

若server只报某task失败而缺少native原始error，仅在本轮专用副本的native completion解包位置增加诊断：记录同条completion的future id、ok、error、result_bools，并关联提交时的key和view地址/长度。不改变结果、缓冲、线程或完成顺序；回传这一个诊断hunk。不能用R2错误替代真实MP失败任务的错误。

主仓也包含 NPU 专属实现，故“只在NPU出错”不自动意味着一定改 Ascend。普通注册不会移动同一CPU Tensor地址；源码见 [NpuPinMemoryBackend](https://github.com/LMCache/LMCache/blob/240506edf5146613b015e9e2e51189f1fc099b76/lmcache/v1/platform/devices/npu/pin_memory.py#L247)。

## 8. 退出、回传和当前验证状态

**结论：正常路径保留证据；超时不能当任务已取消，不能直接释放仍可能被server访问的NPU owner。**

- 仅停止本轮 `server.pid` 对应且进程命令已核实的测试server，优先普通TERM；不使用 `pkill -9 -f "lmcache server"`，不停止原有服务。
- MP脚本若报告 `cleanup_safe_to_release=false`，按提示先确认本轮server已退出，再创建本次指定的 `server.stopped` marker，让client结束；不要因超时就kill client、释放owner并继续发请求。
- R2组件若报告 `NPU_COMPLETION_UNKNOWN_OWNERS_RETAINED`，说明自己的NPU stream同步失败，不能用停止MP server代替确认。它会持有内存、每5秒仅重试同一stream同步；确认成功才释放，并仍记失败，不会转成通过。持续失败则保留进程和错误，不强行释放，也不重置他人正在使用的设备。
- 保留JSON、server.log、新key文件与运行命令。回传文本即可，不要求传core或原始大文件。
