# L2 目录为空：本地复现与日志定位指南

结论：先用最小实例证明“真实写入”，再分别改变 L2 清理策略和 O_DIRECT 开关。这样能区分没有产生保存任务、写入失败、写入后被清理三种情况，不需要先把 512 GiB L1 填满。

本指南面向用户或另一侧 Agent。命令以 Linux Bash 为准；不直接在 Windows PowerShell 执行。源码已核对，本文命令完成语法检查；本机没有执行真实 LMCache MP/Ascend 复现，运行结果仍须现场记录。

## 1. 先理解要看哪条链路

结论：目录为空只是结果，不能说明链路断在哪里。

```text
客户端产生新的 KV
  → 写入 L1 完成
  → StoreController 提交 L2 任务
  → fs_native 写临时文件并改名为最终文件
  → 可选：L2 驱逐线程清理文件
```

公开主干默认 `--l2-store-policy default`：新数据写完 L1 后安排异步写 L2，并保留 L1。L1 驱逐与这一步是两件事，不需要等 512 GiB L1 满。[默认策略](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/distributed/storage_controllers/store_policy.py#L113)

这里的 `cache_salt` 可以先理解成“数据所属用户或分组的标记”。`IsolatedLRU` 按这个标记单独管理配额。MP 服务把未登记的配额按 0 处理；只要该组有数据就超额，实际使用 100% 清理比例，覆盖配置中的 `eviction_ratio:0.1`。没有设置 `max_capacity_gb` 也不会使这条隔离清理路径自动关闭。[清理分支](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/distributed/storage_controllers/eviction_controller.py#L347)、[接线条件](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/distributed/storage_manager.py#L205)

## 2. 本地需要什么环境

结论：配额清理可以在已配置好的完整 Linux CPU LMCache 环境复现；Ascend 特定内存与 O_DIRECT 兼容性，需要 Ascend 环境及相应文件系统。

| 环境 | 能证明什么 | 不能据此证明什么 |
|---|---|---|
| 完整 Linux CPU LMCache，已具备 fs_native 扩展 | R0/R1 的真实服务写盘、配额清理 | Ascend 内存来源或 NPU 传输 |
| 与目标同镜像、同设备环境的 Linux/Ascend 测试容器 | R0/R1/R2，以及该环境的实际分配路径 | 未测版本、未测模型和并行配置 |
| 当前 Windows 文档工作区 | 阅读、命令语法检查 | 真实 MP 或 NPU 复现 |

优先在目标同镜像的专用测试容器中操作，复用原设备、驱动挂载和依赖。若使用原脚本创建新容器，保留设备环境，改用独立容器名、测试目录和端口，额外加入 `-e LMCACHE_LOG_LEVEL=DEBUG`。不把生产服务作为实验对象。

进入测试容器后，下文命令在**同一个 Bash 会话**执行。服务端口示例为 15555，HTTP 示例为 18080；先用 `ss -lnt` 确认未占用。没有可用资源时保留只读证据并停止，不通过关停他人服务腾资源。

不需要为了这个存储问题先启动 DeepSeek 模型。优先使用主仓自带 `lmcache bench server`，它构造 KV 输入并向真实 MP 服务发请求。它不等同于真实模型/TP8 验收。

## 3. 先保留原实例证据

结论：在另开最小复现前，先看原实例是否已经有明确错误，避免不必要的实验。

在宿主机执行；输出目录必须是本次新建的：

```bash
export ORIGINAL_CONTAINER="DeepSeekV4-flash-0731-lmcache-mp-server"
export EVIDENCE_DIR="$(mktemp -d /tmp/lmcache-l2-evidence_XXXXXXXX)"
docker logs --timestamps --since 30m "$ORIGINAL_CONTAINER" > "$EVIDENCE_DIR/original.log" 2>&1
docker inspect --format '{{.Config.Image}} {{.Image}}' "$ORIGINAL_CONTAINER" > "$EVIDENCE_DIR/image.txt"
grep -E 'Created FS native|Routed LazyMemoryAllocator|Submitted store task|L2 store task|Store task .*failed|over quota|evicting ratio|write failed|Bad address|Invalid argument' "$EVIDENCE_DIR/original.log"
```

如果原日志已存在 `over quota`、`limit=0`、`evicting ratio=1.00`，优先验证 R1。若已存在写入失败，优先做 R0/R2。INFO 日志通常看不到成功提交和完成的 DEBUG 日志，缺少成功日志不能当成没有发生写入。

脚本原挂载对应关系是：容器 `/ssd/lmcache` ↔ 宿主 `/modeldata/lmcache_ssdcache`。确认查看的是同一个实例、同一个挂载；不要将另一个容器的目录或日志混进结论。

## 4. 测试会话初始化

结论：采用新子目录、小池和独立端口，即可开始定位；先保持软件版本不变。

在专用测试容器里执行：

```bash
command -v lmcache
head -n 1 "$(command -v lmcache)"
lmcache server --help
lmcache bench server --help
ss -lnt
```

根据 `lmcache` 的 shebang 找到它实际使用的 Python，设置 `PY` 为同一个解释器。下例的 `python3` 只有在确实匹配时才能照用；不匹配就改为查到的绝对路径。

```bash
export PY="$(command -v python3)"
export RPC_PORT=15555
export HTTP_PORT=18080
export HTTP_URL="http://127.0.0.1:${HTTP_PORT}"
export LMCACHE_LOG_LEVEL=DEBUG
export DIAG_ROOT="$(mktemp -d /ssd/lmcache/l2_diag_XXXXXXXX)"
printf '%s\n' "$DIAG_ROOT"
"$PY" - <<'PY'
import inspect
import sys
import lmcache
from lmcache.v1.memory_allocators.lazy_memory_allocator import LazyMemoryAllocator

print("python:", sys.executable)
print("lmcache:", lmcache.__file__)
print("device_type:", getattr(lmcache, "torch_device_type", "unknown"))
plugin = sys.modules.get("lmcache_ascend")
print("loaded ascend plugin:", getattr(plugin, "__file__", None))
print("lazy init:", inspect.getsourcefile(LazyMemoryAllocator.__init__))
PY
```

`DIAG_ROOT` 是本次自建目录，且在目标缓存文件系统上。测试服务只使用其中每组自己的 `cache` 子目录；不把原缓存根目录作为测试服务 base_path，不删除原数据。若复现 CPU 配额路径且没有该挂载，可将创建目录的位置改为自己可写的本地 Linux 目录，并注明文件系统与目标不同。

### 4.1 选择客户端与服务分配模式

结论：Ascend 场景保持 NPU 路径；纯 CPU 场景才使用 CPU 客户端。不要用 CPU 实验冒充 NPU 验收。

在 Ascend 环境：

```bash
export CLIENT_MODE=gpu
LAZY_ARGS=(--l1-use-lazy)
```

CLI 的参数名是 `gpu`，当前参考实现内部按 `torch_device_type` 分配。启动后必须确认客户端实际打印张量在 `npu`，不能仅凭参数名认定设备。该 NPU CLI 组合本侧未实机核实；遇到 CLI/传输注册不兼容，停止这个入口，复用现场已有的 vLLM 请求脚本，不自动升级。[设备选择源码](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/cli/commands/bench/server_bench/helpers.py#L265)

在**实际为 CPU 后端的完整 Linux 环境**，仅复现配额清理时，改用：

```bash
export CLIENT_MODE=cpu
LAZY_ARGS=(--no-l1-use-lazy)
```

不要只在已经使用 NPU 后端的进程里将客户端模式改成 CPU，就假定整条分配与传输路径都变成 CPU。

## 5. 固定三组实验

结论：R0/R1 区分“写后删”，R0/R2 区分“O_DIRECT 开关相关失败”。不要同时改软件版本、分配器、清理策略和 I/O 开关。

| 组别 | O_DIRECT | L2 eviction | 目的 |
|---|---|---|---|
| R0 | false | 无 | 基线：真实请求能写入并保留文件 |
| R1 | false | IsolatedLRU | 先有配额留文件，再撤销配额观察清空 |
| R2 | true | 无 | 与 R0 对比，检查直接写入是否失败 |

每组使用同一镜像、同一解释器、同一设备/客户端模式、同一 KV 形状、同一池大小；缓存目录各自新建。示例将 L1 与初始容量都设为 1 GiB，避免默认初始 20 GiB 与小最终池冲突。小池复现存储逻辑，不验证原 512 GiB 的容量或注册额度。

### 5.1 通用启动命令

结论：先设置当前组的三个变量，再执行本节启动块；换组前正常关闭本次自建服务。

R0 的变量：

```bash
export CASE=R0
export DIO=false
export L2_EVICTION=none
```

R1 的变量改为：

```bash
export CASE=R1
export DIO=false
export L2_EVICTION=isolated
```

R2 的变量改为：

```bash
export CASE=R2
export DIO=true
export L2_EVICTION=none
```

一次只选一组。每选定一组，执行：

```bash
export CASE_DIR="${DIAG_ROOT}/${CASE}"
if mkdir "$CASE_DIR"; then
  mkdir "$CASE_DIR/cache"
else
  printf 'Cannot create a new case directory: %s\n' "$CASE_DIR"
  unset CASE_DIR
fi
```

如果目录原已存在，停止本组，换新的 CASE 名；不要继续复用旧文件或删除它。然后生成 JSON 并启动：

```bash
: "${CASE_DIR:?Create a new case directory before starting}"
L2_JSON="$("$PY" - "$CASE_DIR/cache" "$DIO" "$L2_EVICTION" <<'PY'
import json
import sys

base, dio, policy = sys.argv[1:]
spec = {"type": "fs_native", "base_path": base, "num_workers": 4,
        "use_odirect": dio == "true"}
if policy == "isolated":
    spec["eviction"] = {"eviction_policy": "IsolatedLRU",
                        "trigger_watermark": 0.8, "eviction_ratio": 0.1}
print(json.dumps(spec))
PY
)"
printf '%s\n' "$L2_JSON" > "$CASE_DIR/adapter.json"
lmcache server \
  --host 127.0.0.1 \
  --port "$RPC_PORT" \
  --http-host 127.0.0.1 \
  --http-port "$HTTP_PORT" \
  --chunk-size 4096 \
  --supported-transfer-mode lmcache_driven \
  --l1-size-gb 1 \
  --l1-init-size-gb 1 \
  "${LAZY_ARGS[@]}" \
  --eviction-policy LRU \
  --worker-reap-timeout-seconds 0 \
  --l2-adapter "$L2_JSON" \
  > "$CASE_DIR/server.log" 2>&1 &
export SERVER_PID=$!
printf '%s\n' "$SERVER_PID" > "$CASE_DIR/server.pid"
printf 'case=%s pid=%s directory=%s\n' "$CASE" "$SERVER_PID" "$CASE_DIR"
```

检查启动结果：

```bash
tail -n 60 "$CASE_DIR/server.log"
curl -fsS "$HTTP_URL/healthcheck"
curl -fsS "$HTTP_URL/status" > "$CASE_DIR/status_before.json"
curl -fsS "$HTTP_URL/quota" > "$CASE_DIR/quota_before.json"
```

`healthcheck` 没就绪时先等服务初始化，检查日志；设置合理的启动等待上限，例如 60 秒。进程退出、接口不可用、FS native 扩展缺失、无设备或注册/内存失败时，停止本组并记录原始错误。这些不能算成文件落盘实验失败。

确认日志包含 `Created FS native L2 adapter`，且目录、odirect 值符合本组。若实际版本的 CLI 不接受某个参数，用现场 `--help` 核实等价参数；不静默切换传输模式或后端。

### 5.2 定义一个小流量入口

结论：必须产生完整的新 chunk；仅服务启动、仅 L1 命中或只收到 HTTP 200，都不能证明进行了 L2 写入。

在同一个 Bash 会话定义一次：

```bash
run_one_sequence() {
  local sequence_id="$1"
  lmcache bench server \
    --rpc-url "tcp://127.0.0.1:${RPC_PORT}" \
    --url "$HTTP_URL" \
    --mode "$CLIENT_MODE" \
    --transfer-mode lmcache_driven \
    --tp-size 1 \
    --num-tokens 8192 \
    --kvcache-shape-spec '(2,512,16,8,128):float16:2' \
    --start "$sequence_id" \
    --end "$((sequence_id + 1))" \
    --interval 0.5 \
    > "$CASE_DIR/client_${sequence_id}.log" 2>&1
  local client_rc=$?
  printf 'sequence=%s client_exit=%s\n' "$sequence_id" "$client_rc"
  return "$client_rc"
}
```

该形状约分配 64 MiB KV，使用 1 个测试 worker、2 层；不是 DeepSeek 的结构。8192 tokens 能覆盖两个 4096-token 完整块。**不要用 CLI 默认的 512 tokens 测试本例**，否则可能直接出现 `SKIP: ... tokens < chunk_size ...`，没有有效保存任务。[分块处理](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/cli/commands/bench/server_bench/client.py#L195)

`lmcache mock` 不可替代本命令：它只生成示例指标，不连接服务。如果当前镜像无该 bench 命令，使用现有 vLLM 流量入口：保持已验证的 connector 配置，发一条新前缀且能产生完整可保存 chunk 的请求，并确认 L1 写入完成。不能只靠字符数推断 token 数。

客户端的 `cold_store_succeeded` 或 `CHECKSUM MATCH` 主要证明客户端/缓存传输链，**不保证异步 L2 已成功，也不保证数据来自 L2**；L2 必须另看服务日志和文件状态。

## 6. R0：先证明“能够写入并保留”

结论：R0 不通过，就先修正流量入口或查普通写入失败，不继续把结果归因于配额或 O_DIRECT。

按 R0 配置启动后执行：

```bash
run_one_sequence 10001
tail -n 60 "$CASE_DIR/client_10001.log"
grep -E 'Submitted store task|L2 store task|Store task .*failed|Failed to submit store' "$CASE_DIR/server.log"
find "$CASE_DIR/cache" -maxdepth 1 -type f -printf '%f %s\n'
curl -fsS "$HTTP_URL/status" > "$CASE_DIR/status_after.json"
```

等待 L2 任务完成，按条件观察，不以固定睡眠后目录仍空作为失败证据。小流量可给 30 秒观察窗口；仍没有完成/失败结果就记录为“L2 任务未完成或未确认”，并检查控制器 pending/in-flight 与线程状态。

预期：出现 L2 提交与完成 DEBUG 日志，文件存在且大小非零；后续仍保留。文件数依实际布局确认，不硬性要求恰好两个。`/status` 中 pending/in-flight 为 0 只能说明当前没有待处理任务，不证明历史一定成功或从未提交。

## 7. R1：受控复现“写进去，然后被删”

结论：先让文件确定存在，再撤销配额，可清楚观察先写后删的完整时序，避免只捕捉到一个空目录。

正常停止 R0 后，按 R1 配置新启动。主仓 bench 的默认 `cache_salt` 是空字符串，HTTP 用 `_default` 表示。真实业务如果使用了其他 salt，必须操作其实际值，不能把 `_default` 当成通配符。[默认键](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/multiprocess/custom_types.py#L50)、[HTTP 映射](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/multiprocess/http_apis/quota_api.py#L25)

### 7.1 给测试数据一份足够大的配额，先写进去

结论：测试样例的数据量低于 1 GiB 配额的 80%，应可保留；以返回值与实际用量核实。

以下写操作只对**本次专用测试服务**执行，不能指向原生产服务端口：

执行 PUT/DELETE 前，必须同时核对本次 `SERVER_PID` 仍是自建命令，以及 `/status` 中 FS adapter 的 `base_path` 是本组新目录。只看到端口能响应不够；若测试进程启动失败，端口可能属于其他实例，不得继续写配额。

```bash
curl -fsS -X PUT "$HTTP_URL/quota/_default" \
  -H 'Content-Type: application/json' \
  --data '{"limit_gb":1}' \
  > "$CASE_DIR/quota_set.json"
curl -fsS "$HTTP_URL/quota/_default" > "$CASE_DIR/quota_positive_before.json"
run_one_sequence 20001
grep -E 'Submitted store task|L2 store task|Store task .*failed|over quota' "$CASE_DIR/server.log"
find "$CASE_DIR/cache" -maxdepth 1 -type f -printf '%f %s\n' > "$CASE_DIR/files_before_delete.txt"
curl -fsS "$HTTP_URL/quota/_default" > "$CASE_DIR/quota_positive_after.json"
```

看到 L2 完成、文件存在后再继续。若连这一步都没有写入成功，先查失败，不能声称配额删除已复现。`quota_set.json` 应显示成功，查询应 `exists:true`；用量由已成功计量的 L2 数据驱动。

### 7.2 撤销本测试实例的配额，观察清理

结论：删除配额后进入 `limit=0` 分支，这与原脚本从未给该 salt 登记配额的判断条件一致。

```bash
curl -fsS -X DELETE "$HTTP_URL/quota/_default" > "$CASE_DIR/quota_delete.json"
curl -fsS "$HTTP_URL/quota/_default" > "$CASE_DIR/quota_zero.json"
grep -E 'over quota|evicting ratio|Store task .*failed' "$CASE_DIR/server.log"
find "$CASE_DIR/cache" -maxdepth 1 -type f -printf '%f %s\n' > "$CASE_DIR/files_after_delete.txt"
```

清理线程约按秒轮询；继续观察直到出现清理日志并确认文件数下降。10 秒仍无结果就保存状态，检查是否有读取锁、删除超时、实际策略/配额与预期不一致，不重复盲改。不要因第一次 grep 跑得早、日志还没出现而判失败。

预期组合：先有成功 store；后有 `limit=0`、`evicting ratio=1.00`；配额查询 `exists:false`；原文件随后消失。清理日志表示控制器已进入该分支，**还要结合最终文件状态确认删除完成**。

如需严格补看“最初就没登记”的现象，在仍无配额时发送一条新序列，例如 `run_one_sequence 20002`。预期它也会写入后清理；使用新序列避免全命中 L1，导致没有新的 L2 保存任务。此步只在需要确认原始起点时补做。

## 8. R2：单独检查 O_DIRECT 写入失败

结论：去掉 L2 eviction 后再开启 O_DIRECT，才能排除“写后清理”的干扰。

正常停止 R1，按 R2 配置新启动，保持与 R0 同样的客户端模式、KV 形状和软件版本：

```bash
run_one_sequence 30001
tail -n 60 "$CASE_DIR/client_30001.log"
grep -E 'Routed LazyMemoryAllocator|Created FS native|Submitted store task|L2 store task|Store task .*failed|Failed to submit store|O_DIRECT|Bad address|Invalid argument|write failed' "$CASE_DIR/server.log"
find "$CASE_DIR/cache" -maxdepth 1 -type f -printf '%f %s\n'
curl -fsS "$HTTP_URL/status" > "$CASE_DIR/status_after.json"
```

| R0 / R2 结果 | 可以得出的结论 |
|---|---|
| R0 成功、R2 成功且文件保留 | 这个小样例没有复现 O_DIRECT 写入失败；原场景是否不同仍未核实 |
| R0 成功、R2 已提交但任务失败 | 存在与 O_DIRECT 开关相关的失败，需要具体 errno 和缓冲路径证据 |
| R0/R2 都失败 | 不能归因于 O_DIRECT，先查共同失败环节 |
| R2 没有确认新 KV/L2 提交 | 尚未进入可判断的直接写入阶段 |

`Routed LazyMemoryAllocator pool through alloc_pinned_ptr (aclrtMallocHost)` 是旧 Ascend 替换的路径线索，**不是一次 write 的地址来源证明**。若要与 #305 归因对应，仍需确认真实池与传入缓冲。

`use_odirect:true` 也是配置证据，不等于系统调用一定带 O_DIRECT。当前 native connector 会根据长度等条件决定是否使用；需要严格证明时看 `openat` 标志。即使拿到 EFAULT，也不能仅凭它唯一认定 ACL 映射；生命周期、地址有效性等具体内核分支仍未核实。

用户已有同环境的 #305 验收可以复用。如果需要确认这套不同镜像是否同一问题，再在隔离副本中只应用 #305，保持 R2 条件不变；不要求无条件重新跑完整验收矩阵。

## 9. 看什么日志才能判断

结论：按“提交—完成—清理—最终文件”串起来看，不单独依赖任何一条成功或失败消息。

下表中的 `<id>` 等表示现场数值；下面示例均为**预期格式示意，不是本机实测日志**。

| 日志或状态 | 等级 | 说明 | 不能单独证明什么 |
|---|---|---|---|
| `Created FS native L2 adapter: ... odirect=...` | INFO | 该后端创建、配置已读取 | 有请求或已写盘 |
| `Submitted store task <id> to adapter <n> with <k> keys.` | DEBUG | 已向 L2 adapter 提交任务 | 写入已成功 |
| `L2 store task <id> completed: adapter <n>, <k> keys.` | DEBUG | 该 L2 批次报告成功 | 文件之后仍会保留 |
| `Store task <id> to adapter <n> failed for keys: ...` | WARNING | L2 批次失败 | 是 EFAULT、EINVAL，或由哪种具体内存机制导致 |
| `Failed to submit store task to adapter ...` | ERROR | 提交阶段抛异常 | 文件系统 write 已执行 |
| `cache_salt=... over quota (bytes=..., limit=0, watermark=0.80); evicting ratio=1.00.` | INFO | 未登记/零配额触发完整清理 | 删除一定已完成；还需文件/删除结果 |
| `SKIP: ... tokens < chunk_size ...` | 客户端输出 | 该样例没有完整块可保存 | L2 已经尝试写入 |
| `/status` 控制器 `is_healthy:false` / pending 或 in-flight 长期不降 | 状态 JSON | 控制器异常或任务未收尾的线索 | 具体磁盘错误原因 |
| HTTP 200、bench `CHECKSUM MATCH`、warm hit | 客户端/HTTP | 请求或部分数据链通过 | L2 落盘、L2 命中或磁盘数据正确 |

### 9.1 典型“写后删”证据链

结论：成功完成在前，零配额清理在后，再确认文件消失，支持配额清理解释。

```text
DEBUG Submitted store task 7 to adapter 0 with 2 keys.
DEBUG L2 store task 7 completed: adapter 0, 2 keys.
INFO  cache_salt='' over quota (bytes=<正数>, limit=0, watermark=0.80); evicting ratio=1.00.
文件快照：存在非零文件 → 随后文件数为 0
```

并发线程的单行打印可能交错，按任务、salt、文件和时间共同关联；不要只对孤立几行作结论。NPU I/O 失败与配额删除可以同时出现在不同任务上。

### 9.2 典型“写失败”证据链

结论：已提交、失败、没有该任务的成功完成，支持 L2 写入任务失败；原始 errno 未取得时就保持未知。

```text
DEBUG Submitted store task 8 to adapter 0 with 2 keys.
WARNING Store task 8 to adapter 0 failed for keys: ...
文件快照：没有对应最终文件
```

当前 `NativeConnectorL2Adapter` 虽然接收 completion 的 `error` 字符串，但该分支没有把它打印出来。因此不能承诺 DEBUG 开启后就一定看到 `write failed: Bad address`；上一轮提到这类错误是可能证据，不是必有日志。[错误消费分支](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/lmcache/v1/distributed/l2_adapters/native_connector_l2_adapter.py#L508)

另外，native FS 写失败会删除临时文件；目录没有 `.tmp` 不代表从未尝试 write。[失败清理](https://github.com/LMCache/LMCache/blob/f42f3d94b10b7d0d576fde0feb2aaae8987c4d35/csrc/storage_backends/fs/connector.cpp#L184)

## 10. 只有通用失败时，如何拿具体系统调用错误

结论：仅在 R2 已出现真实提交与失败、但缺原始错误时，追加一次短时 syscall 观察；不一开始就抓所有系统调用。

在本测试容器的另一个终端，使用已有 `strace`，附着**本次自建服务 PID**。先从本组 `server.pid` 读取，核对命令与端口；不能附着原服务或其他进程。若工具不存在、没有权限、ptrace 会影响现场时，记录“原始 errno 未核实”，不自动安装或改全局设置。

下面示例的 CASE_DIR 由另一个终端先按本次打印路径设置；不要沿用别的实验目录：

```bash
SERVER_PID="$(cat "$CASE_DIR/server.pid")"
ps -p "$SERVER_PID" -o pid=,args=
timeout --signal=INT 30s strace \
  -f -tt -T -yy \
  -e trace=openat,write,pwrite64,rename,renameat,renameat2,unlink,unlinkat \
  -e raw=write,pwrite64 \
  -o "$CASE_DIR/syscalls.log" \
  -p "$SERVER_PID"
```

在这 30 秒内，从原测试会话发送一个新序列，例如 `run_one_sequence 30002`。`-e raw=write,pwrite64` 保留指针、长度与返回值，避免输出 KV payload。短时附着会影响时序，不能据此做性能比较。`timeout` 结束 strace 通常返回非零，不等于服务退出；确认已正常脱离，服务仍在。

```bash
grep -E 'O_DIRECT|EFAULT|EINVAL|ENOSPC|EACCES|EBADF|rename|unlink' "$CASE_DIR/syscalls.log"
```

按同线程、同文件描述符、同 cache 路径关联：

| syscall 证据 | 解释 |
|---|---|
| 目标缓存文件 `openat` 带 `O_DIRECT`，对应 write 返回 `EFAULT` | 直接写入发生了地址访问失败；具体原因还要结合地址来源/生命周期 |
| 对应 write 返回 `EINVAL` | 需要查对齐、文件系统与调用参数，不能直接等同于原 EFAULT |
| `ENOSPC` / `EACCES` 等 | 磁盘空间或权限等其他失败，应按实际错误处理 |
| 完整写入、最终 rename 成功，随后 unlink | 支持“成功后删除”；结合配额日志确认是否由 IsolatedLRU 触发 |
| write 失败后 unlink 临时文件 | 写入失败的善后，不是 L2 驱逐的证据 |

raw syscall 的 fd/数值可能显示为十六进制；根据同线程的 open 返回值关联。不要把 stdout 日志文件的 write 当成缓存文件的 write。

## 11. 如何正常停止并切换下一组

结论：只停止当前手动创建并核对过的测试服务，保留所有证据目录。

```bash
ps -p "$SERVER_PID" -o pid=,args=
```

确认仍是本组 `lmcache server`、端口与记录一致后：

```bash
kill -TERM "$SERVER_PID"
wait "$SERVER_PID"
tail -n 40 "$CASE_DIR/server.log"
```

`wait` 可能因信号退出返回非零；结合日志与进程状态解释。确认旧实例退出、端口已释放后再设置下一组 CASE/DIO/L2_EVICTION 并启动。不要使用 `pkill`、`killall`、全目录删除，也不要清空原 L2。

## 12. 最终判定与定位路径

结论：用下面的分支收敛原因，明确写出证据边界。

```text
是否有真实新 KV、L2 提交？
  ├─ 未确认：查客户端、完整 chunk、L1 完成通知、adapter/controller
  └─ 有：L2 任务是否成功？
       ├─ 否：先与 R0 比较；取 errno、确认 O_DIRECT 和缓冲来源
       └─ 是：文件是否随后消失？
            ├─ 是：查配额日志、实际 salt、删除调用与最终文件
            └─ 否：查观察目录/实例是否错误；文件已正常保留
```

| 最终证据 | 可定稿的结论 |
|---|---|
| R1 先成功存盘，撤销配额后 limit=0/ratio=1.00，文件消失；恢复配额的新数据保留 | 该版本配置下已复现 IsolatedLRU 零配额导致的“写后删” |
| R0 成功；R2 提交后失败；实际 O_DIRECT 与 errno 已取得 | 该版本挂载下已复现直接写入失败；按 errno 限定，底层映射机制未必已确定 |
| R0 成功、R2 失败，但没有具体 errno | 已确认与开关相关的任务失败，具体系统调用原因未核实 |
| 原配置同时有多个任务的写失败与零配额清理 | 两种现象同时存在，应分别处理，不能用单一原因覆盖 |
| 小样例全通过 | 当前样例未复现，不能证明 512 GiB/原模型/原版本场景不存在问题 |

如果只有低层失败的判断，不宣称重启首 load 挂死也已解释。#305 改变 lazy 内存来源，但不会修改 IsolatedLRU 配额语义。用户报告的 #305 现场成功作为已有证据保留，不代表另一套镜像已完成同样验证。
