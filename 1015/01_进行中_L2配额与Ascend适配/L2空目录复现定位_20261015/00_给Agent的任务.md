# 给另一侧 Agent：复现并区分 L2 空目录的两种原因

结论：请先复现“写入后被配额清理”，再单独检查“O_DIRECT 写入失败”；不要把目录为空直接等同于写入没发生。

请阅读同目录 `01_本地复现与日志定位指南.md`，在现有 Linux/容器环境执行。结果按 `02_文本回传模板.md` 贴回，无需传原始文件。

背景：用户已报告 #305 在其现场验证可以解决 O_DIRECT 不写入的问题。本轮检查另一个全部使用主干的启动配置：`lmcache_driven`、L1 512 GiB、`fs_native`、`use_odirect:true`，并给 L2 配了 `IsolatedLRU`，但命令里没有登记 cache_salt 配额。公开主干会把未登记的配额按 0 处理，并清理该 salt 的全部 L2 数据。因此两个原因可能独立存在，也可能同时存在。

执行顺序：

1. 保留目标原服务的日志与只读状态，不先改变原服务配置。
2. 使用自有目录、独立端口和现有版本，建立最小测试实例；不清缓存、不停止别人的任务、不升级环境。
3. R0：关闭 O_DIRECT，不配 L2 eviction，证明测试流量能真正写入 L2。
4. R1：关闭 O_DIRECT，配置 IsolatedLRU。先登记测试配额并确认文件存在，再删除本测试实例的配额，观察完整清理日志。必要时再发送一条新序列，验证“从未登记配额”的等价状态。
5. R2：移除 L2 eviction，保持与 R0 相同的其他条件，只开启 O_DIRECT；观察写入成功还是失败。
6. 如果 R2 失败而 R0 成功，需要时取具体系统调用错误。原始 errno 没有拿到时，写“未核实”，不能把通用失败日志改写成 EFAULT。
7. 用户已有同环境的 #305 证据可复用；只有需要核对另一个环境时，才追加同配置的 #305 对照，不把它变成必跑的大矩阵。

主仓已有 `lmcache bench server` 可构造 KV 并走真实缓存服务，通常无需加载 DeepSeek 模型。它构造的是测试输入，不覆盖模型推理或真实 DeepSeek/TP8 验收。CLI 不兼容时复用现有 vLLM 请求脚本，不为此升级。不要用 `lmcache mock`，该命令只生成示例指标，不连接缓存服务。

严格区分：客户端 STORE 完成、L2 提交、L2 写入成功、配额清理、最终文件状态。每个结论给出对应日志；没有证据的写“未核实”。
