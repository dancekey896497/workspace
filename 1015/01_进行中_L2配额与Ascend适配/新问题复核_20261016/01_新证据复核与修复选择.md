# 新证据复核：DS、O_DIRECT、对齐与 PR305

日期：2026-10-16。原文保留在[反馈1](../../../新问题交互/反馈1.txt)与[机主本地的分析](../../../新问题交互/机主本地的分析.txt)。

## 1. 先给结论

**结论：可能存在 PR305 未覆盖的 O_DIRECT 故障；但目前还不能认定 DS 的真实故障就是地址未对齐，也不能据 Qwen 成功排除 DS 的问题。下一步优先抓真实失败对象，而不是继续构造非对齐 buffer。**

| 问题 | 当前判断 | 依据／限定 |
|---|---|---|
| 昨天的正配额实验是否通过？ | **通过，来自现场文字回传** | Qwen3-8B、TP4、buffered、空 salt 8 GiB；16 文件、2.25 GiB 保留至 T60 |
| 这是否证明 DS 的 O_DIRECT 正常？ | 不能证明 | 该组明确 `use_odirect=false`，不是 DS 或 DIO 验收 |

| 是否可能之前恰好没复现？ | **可能，但具体原因未核实** | 模式、分配源、版本、对象布局、文件系统及实际 DIO 开启情况都可能不同 |

另外，2026-10-16 在线核实 **PR305 已合并**，当前 Ascend main 为 `b813e970075983e94e86cc2911a40b1c00e7c780`。这不代表现场镜像已经包含它。[S1]

## 2. 昨天的反馈应如何收口？

**结论：Qwen buffered 场景的零配额清理可以收口，不必再重复同组实验；DS 的写入失败单列处理。**

反馈中最终数据相互吻合：

```text
prompt_tokens = 17416
完整 chunk / rank = floor(17416 / 4096) = 4
TP4 → 16 个对象
16 × 150,994,944 bytes = 2,415,919,104 bytes = 2.25 GiB
配额触发水位 = 8 × 0.8 = 6.4 GiB
最终 2.25 GiB < 6.4 GiB，持续至 T60，未观测到新增驱逐。
```

这与先前无配额全清、去掉策略保留文件的实验组合，支持此前 IsolatedLRU 的定位。它与原来的 O_DIRECT 内存兼容问题可以同时成立。

两类故障也可能叠加在机主服务中：DIO 先写失败；修好写入后，如果仍未登记 IsolatedLRU 配额，文件又会被清理。因此对照要隔离 eviction，或确保配额足够，不能只根据目录最终是否为空判断 DIO。

原文三处表述需要限定，原始文件不修改：

1. 已记录 LazyMemoryAllocator 扩容日志，却又写“主仓未启用 lazy”，两者矛盾；应以实际实例和加载函数为准，后一句待订正。
2. T5 时完成对象计数是 8、文件数是 12，说明采样不同步，不能概括为“成功计数总先于文件”。最终收敛更可靠。
3. 驱逐指标未出现不等于读取到一个精确的 0；应写“未观测到新增驱逐，文件和用量持续保留”。

PR305 的有效性仍保留你此前已报告的现场通过结论；本次“等价补丁 + 没有 routing 日志”不能替代所有函数来源的检查。主仓副本没有 commit、最终协商模式未核实，也应继续保留。

## 3. 为什么机主的“决定性验证”还差一环？

**结论：它验证了 connector 的拒绝规则，没有把该规则关联到真实 DS 失败任务。**

真实 FS 路径的先后顺序是：[S2][S3]

```text
目标文件已存在 → 直接返回成功
否则：检查是否可启用 O_DIRECT
  长度不满足 connector 的 D 倍数 → 本版降级普通 I/O
  长度满足，但地址不满足 → 抛“地址未对齐”，尚未 open/write
  两者满足 → 打开 O_DIRECT 文件，再实际 write
```

因此，合成样本的明确地址错误可以确认它触发了 guard。但还缺少：

- 真实失败 task/future/key 对应的原始 error。
- 真实 L1 对象 `obj.data_ptr` 和最终 memoryview 起点。
- 池基址、对象偏移、有效 align、实际提交长度与 FS D。

`ctypes` 与 `mmap` 对拍还同时改变了分配来源和映射属性，不是所有底层性质都仅差地址。该样本的 guard 明确指向地址检查，但不能推导真实业务也有相同输入。

### 两个容易误读的信号

**结论：任务失败率、目录为空都不足以单独指定具体根因。**

- native SET 完成是批次聚合结果。一个对象失败会使批次 `ok=false`，此前对象或其他 tile 可能已经写成。因此“所有 task 失败”不等于“每个对象地址都不齐”。[S4]
- wrapper 收到了原始 `error`，store 分支却未打印，机主对这处可观测性缺口的描述与公开源码一致。优先让它输出原始错误，而不是继续从通用 failed 日志猜测。[S5]

历史曾有 573 万 inode，不能证明曾经将 O_DIRECT 从 false 改 true；过去配置和版本时间线**未核实**。

## 4. 对齐问题已有完全相关的上游修复

**结论：这类问题确实可能发生，而且上游已经修过；不能把“普通 torch.empty”直接等同于“4096 对齐”。**

主仓 [PR4367][S6] 于 2026-08-07 合并，修复 Lazy pool 的基址对齐。当前代码超额分配 `A-1` 字节，再选取对齐的共享 storage 切片，并检查最终基址。切片保留原 storage 所有权，不会丢失原分配。[S7]

现场主仓被称为“9-29 副本”，日期晚于这个修复，但没有 Git commit，仍需读实际文件；既不能认定已经包含，也不能认定必定缺失。

PR4367 对非 lazy 路径的说明主要基于当时 CUDA/mmap 路线，不能据此证明 Ascend 的每种 native 分配也提供同样保证。

### 判定公式

**结论：模型决定对象大小，但池基址和分配步长共同决定最终地址。**

```text
A = 实际 L1 align_bytes
B = 对象所属池的真实基址
L = 对象逻辑字节数
P = 向上取整到 A 的物理槽位大小
o = 对象在池内的字节偏移
p = 对象真实地址 = B + o
D = 当前 connector 使用的 disk_block_size
q = 最终提交的 memoryview 起点
```

当前标准 Lazy + TensorMemoryAllocator 保证 `B%A=0`、`o%A=0`，物理槽位按 A 取整。若 A=D=4096，则 `p%D` 必须为 0，与 L 具体是多少无关。[S7][S8]

举例：如果 B 的余数是 64，所有 o 都是 4096 的倍数，那么所有对象的 p 余数仍是 64。只对齐偏移、padding 长度都修不了这个基址错误。

## 5. Qwen 与 DS 的模型差异，什么时候才有因果关系？

**结论：模型大小和名字不是直接原因；实际 KV 布局可能暴露未对齐的切分路径。**

应采集实际 KV shapes、dtypes、object group、logical/physical size、TP 和传输模式。不能根据 DS 名字猜具体 MLA 维度，也不能把权重 `w8a8` 当作 KV dtype。

| 实际切分方式 | 模型变化是否可能改变对齐 |
|---|---|
| 按未取整 raw size 紧密排列，或对某个 group/subview 额外偏移 | 可能；L 改变后后续对象起点余数可变化 |
| 当前标准 Lazy，基址与槽位都按 D 对齐 | 不会仅因 L 变化就破坏对象地址对齐 |
| A 小于 D | 可能不满足 connector 要求；视物理长度还可能降级 buffered，而不是报地址错误 |
| 模型导致选择另一分配器、格式或传输路径 | 可能，但要先证明发生了路径切换 |
| 没有新 key，命中已存在文件 | 可能根本未进入地址检查，不能算 DIO 验收 |

你此前 Qwen 的成功结论应按当时配置保留；这次新回传明确关闭了 DIO，不能拿它作为 DS O_DIRECT 的反证。

## 6. PR305 之后仍可能失败的具体分支

**结论：可能，但必须确认真实分支。#305 不是所有 host 分配的统一替换。**

| 现场实际路径 | 静态对齐保证／风险 | #305 是否覆盖 |
|---|---|---|
| 当前标准 Lazy，A=D=4096 | 基址校验 + 槽位取整，应对齐 | 移除旧覆盖后恢复该路径 |
| 旧 Ascend lazy 覆盖仍加载 | 可能绕过主仓的对齐逻辑 | 覆盖范围内，但现场是否生效要核实 |
| #305 已生效，主仓 Lazy 缺少 #4367 | 普通 CPU 分配未必满足 D | #305 不自动补旧主仓逻辑 |
| 配置 A 小于 FS D | 只保证较小的 A | 不覆盖配置契约 |
| non-lazy、无 SHM/NUMA、普通 native ACL 分配 | 当前 Ascend 返回 ACL 原指针，代码没有额外补齐／检查 4096；实际余数未核实 | 不覆盖 |
| non-lazy 且启用 SHM | 走 SHM，不等于普通 ACL 分配；仍核真实基址和 D | 不覆盖，但不能先认定有问题 |
| 自定义 group/subview 或其他 allocator | 要核真实起点和 owner，不能套用标准 Lazy 不变量 | 不自动覆盖 |

non-lazy 的分支还依赖 `shm_name`；不能看到 `--no-l1-use-lazy` 就认定用了 `aclrtMallocHost`。[S9][S10]

## 7. 下一步：先抓 DS 真实失败，再做同模型单变量对照

**结论：最有效的下一轮是“真实 DS 请求 + 原始 error + 地址链”，不需要 GPU，也不必先全面更换模型。**

具体执行件见[给 NPU Agent 的精简定位指令](02_给NPUAgent_真实DS对象定位与回传.md)。

顺序为：

1. 先在原失败路径或对应隔离实例，抓 1—2 个真实失败任务，不改 buffer、不增加拷贝。
2. 给任务关联池基址 B、偏移 o、对象 p、view q、实际 A/D、L/P/提交长度和原始 error。
3. 用同一 DS、同版本、同分配器／传输模式，只切 DIO true/false 做对照；不要用 Qwen buffered 代替 DS buffered。
4. 若真实地址 guard 成立，按余数定位池基址、对象切分或中间包装层；若已经对齐但实际 write EFAULT，转入映射／有效范围／生命周期。
5. 仅修被证实的来源点，复测同 DS 请求。不要先重做全部旧实验矩阵。

地址定位可在独立小目录暂时不配 eviction，隔离清理；两组 DIO 对照保持同样设置。若保留 IsolatedLRU，必须确认预算高于本次数据水位，不能把 Qwen 的 8 GiB 盲套 DS。

## 8. 按证据选择最小修复

**结论：先配置或回补现成修复，再考虑改分配器；不要在 memoryview 层把指针直接挪到下一个对齐地址。**

| 真实证据 | 最小方案 | 风险与验收 |
|---|---|---|
| A 不满足 D，而基址／路径符合预期 | 按实际 D 设置 `--l1-align-bytes`，并核对新池基址 | 当前 A 已为4096、D也4096时，重复加参数并不能修复另一个错误；设置变化后用新目录，避免混用旧物理布局 |
| 旧 Ascend lazy override 仍生效 | 落实 #305 的等价删除，核实际主仓 Lazy | 新进程、真实最终地址、原 DS DIO 写入验收 |
| 实际主仓缺 #4367 | 只回补已有基址对齐修复，不升级整套依赖 | 保留 storage 所有权、pin/unpin 范围和最终基址校验 |
| B 齐、o 不齐，或 p 齐但 q 不齐 | 修具体对象切分、group/subview 或 wrapper 偏移 | 不能靠修改池基址掩盖，需校验内容完整且不越界 |
| non-lazy 普通 ACL 分配的 B 确实不齐 | 评估 Ascend `csrc/mem_alloc.cpp` 的分配／释放对 | 保留 ACL 原始指针；注册、映射和释放成对。不能只 round 返回值；该全局入口有其他调用者，不先扩大改动 |
| 所有真实参数已齐，实际 write EFAULT | 核实际分配来源、映射、有效范围和异步所有权；再决定普通内存+ACL注册等兼容路线 | 对齐不是页可访问性的充分条件，不能承诺加大对齐即可解决 |
| 真实 error 为 ENOSPC/EACCES/rename 等 | 按对应文件系统错误修复 | 不继续坚持地址假说 |

Ascend 分配器若选择超额 ACL 分配再返回对齐子区，必须记录并用原指针释放，正确维护注册表和 host↔device 映射；若改为 mmap+register，释放路径应相应 unregister+munmap，不能继续用 aclrtFreeHost。这些方案尚未因真实 DS 证据而选定，**未实施、未验证**。[S10]

明确不采用的捷径：

- 在 `_obj_to_memoryview` 里向上 round 原指针：会跳过 KV 开头，并可能越界。
- 直接 `bytes()` 后交给 DIO：没有保证地址对齐，还引入新的异步所有权问题。
- 只根据 task 失败率就重写所有分配器。
- 为验证而清空原缓存目录或删除历史数据。

## 9. 当前定稿与核对范围

**结论：配额分支已有通过回传，DS O_DIRECT 分支仍处于真实参数取证阶段。**

可定稿：

> 在回传的 A3 MainB、Qwen3-8B TP4、fs_native buffered、空 salt 8 GiB 配额条件下，16 个对象共 2.25 GiB 跨至 T60 保留，支持零配额清理定位；该结果不覆盖 DS 的 O_DIRECT。DS 地址未对齐目前只由合成样本验证了可能机制，真实业务根因仍待任务级参数和错误闭环。
