**对，你抓住了主要问题：之前把“底层提供设备内存共享能力”，和“TorchNPU 能按自己的方式完整使用它”，再和“LMCache-driven 已经适配好”，合并成了一个“支持 IPC”。**

但“底层简单适配”这个说法还可以更准确一点：**底层不一定只是做了简单适配，而是它提供的是另一层的接口和使用条件。上层还需要把这些接口组织成 Tensor 共享、缓存注册、异步同步等具体功能。**

这次查源码，已经找到了非常直接的证据：**LMCache-Ascend 的 `AscendIPCWrapper` 会调用 TorchNPU 的 `_share_npu_()` 和 `_new_shared_npu()`。** 所以它们之间的依赖不是推测，可以沿代码逐层看下来。:chatgpt-content-reference{index="0"}

## 一、先纠正“24 版本开始支持 IPC”这句话

目前我们讨论过的几个版本号，实际来自不同性质的资料：

| 版本号 | 可以核实的来源与含义 | 不能据此推出什么 |
|---|---|---|
| **HDK `24.1.RC1`** | 官方版本表列出它与 CANN `8.0.RC1` 的配套关系 | 这张表没有证明“910B 的所有 IPC 从这里首次支持” |
| **Driver `24.1.0`** | LMCache-Ascend README 的通用最低驱动要求；FAQ 还把它与 `HostRegisterError` 联系起来 | 不能当成 TorchNPU Tensor IPC 或 LMCache-driven MP 模式的完整支持门槛 |
| **HDK `25.3.RC1`** | 所引 TorchNPU IPC 技术说明中的多次共享句柄导入修复要求 | 不能解释成此前完全没有底层 IPC |

前两项分别可以在[官方版本配套表](https://www.hiascend.com/doc_center/source/zh/ModelZoo/pytorchframework/pies/pies_00003.html)和 [LMCache-Ascend README](https://github.com/LMCache/LMCache-Ascend/blob/main/README.md)中查看；第三项来自“昇腾CANN”发布的 IPC 技术说明。:chatgpt-content-reference{index="1"}

### 尤其要注意：HostRegister 不等于 HBM 跨进程共享

README 的 FAQ 建议遇到 `HostRegisterError` 时检查 `IPC_LOCK` 和驱动版本。这里很容易因为出现了“IPC”三个字母，就理解成“跨进程显存共享”。

实际上，Docker 文档对 `IPC_LOCK` 的说明是**锁定内存的权限**；它不是“NPU 设备内存 IPC 功能开关”。:chatgpt-content-reference{index="2"}

可以先记住：

```text
把 CPU 内存注册／固定，供设备搬运使用
                    ≠
让另一个进程访问本进程分配的 NPU HBM
                    ≠
把这块共享 HBM 恢复成可用的 PyTorch Tensor
                    ≠
让 LMCache 正确地保存、回填并同步 KV Cache
```

**所以，之前“24.x 支持 IPC”的说法不能直接沿用。我们需要先问：24.x 支持的是哪组接口、什么调用方式、什么产品和运行条件。前面的回答没有始终把这一点说清楚。**

## 二、把整个软件栈统一成这六层

下面的“层”指软件调用层，不是 CPU 缓存的 L1、L2。

| 软件层 | 它处理的对象 | 这一层需要做的适配 |
|---|---|---|
| **vLLM 与 LMCache 集成层** | 请求、Worker、模型各层的 KV Cache | 选择传输模式、注册缓存、发起保存和读取 |
| **LMCache 的设备适配层** | 共享句柄、缓存布局、传输任务、完成事件 | IPC wrapper、CacheContext、设备 Event 后端、搬运实现 |
| **TorchNPU 的 Python 层** | Tensor、Storage、序列化参数 | 给 PyTorch 增加 NPU Storage 方法，支持 Tensor 的跨进程拆解与重建 |
| **TorchNPU 的 C++ 层** | 实际分配块、偏移、映射、引用计数 | 将 Storage 共享请求转换成对应的 CANN 调用 |
| **CANN 运行时层** | 设备内存句柄、地址映射、事件 | 提供设备共享和同步 API，并调用底层实现 |
| **HDK Driver／Firmware／硬件** | 设备资源、映射和执行机制 | 在具体设备及运行条件下落实这些操作 |

这些边界能分别在 LMCache 的集成代码、设备接口，以及 TorchNPU 的 Python/C++ 实现中看到。:chatgpt-content-reference{index="3"}

一个最重要的认识是：

> **“适配”不是只发生一次。LMCache 适配 TorchNPU，TorchNPU 适配 CANN，CANN 再使用 HDK 提供的能力。每个连接处都有自己的版本和行为要求。**

下面沿实际代码来看。

**源码范围说明：** TorchNPU 以下使用公开的 **`v2.10.0` 标签**讲解，你安装的是 `2.10.0.post4`，不能声称每一行都与安装包相同。LMCache 则分别引用当前 `dev` 和 LMCache-Ascend `main` 中的实现，用来说明两种适配方式，**不把它们拼成你服务器上已经确认存在的一套代码**。

## 三、最上面两层：LMCache 到底在哪里适配？

### 1. vLLM 集成层：决定“什么时候注册缓存、使用哪条传输路径”

源码：

[LMCache：`vllm_multi_process_adapter.py`](https://github.com/LMCache/LMCache/blob/dev/lmcache/integration/vllm/vllm_multi_process_adapter.py)

在文件中搜索：

```text
register_kv_caches
_send_register_kv_caches_request
create_transfer_context
```

当前代码中，注册 KV Cache 时会根据传输模式创建 `transfer_ctx`，然后调用它的 `register()`。**这一层组织服务流程，不负责亲自实现底层 HBM 映射。**:chatgpt-content-reference{index="4"}

可以理解为：

```text
vLLM：这些 Tensor 是我的 KV Cache
        ↓
LMCache 集成层：根据模式选择相应的传输实现
        ↓
传输实现：决定如何让 Server 访问或接收这些数据
```

### 2. LMCache-Ascend：把原来的共享封装替换为昇腾实现

这次找到的一个很直观的适配位置是：

[LMCache-Ascend：`lmcache_ascend/__init__.py`](https://github.com/LMCache/LMCache-Ascend/blob/main/lmcache_ascend/__init__.py)

搜索 `_patch_multi_process`，里面有这条实际赋值：

```python
lm_mp_types.CudaIPCWrapper = AscendIPCWrapper
```

**它修改的是 Python 程序中的类引用：让使用这个引用的代码改用 Ascend 封装。不是修改 NPU 内核驱动。** 这就是一种运行时补丁适配方式。:chatgpt-content-reference{index="5"}

接着打开：

[LMCache-Ascend：`v1/multiprocess/custom_types.py`](https://github.com/LMCache/LMCache-Ascend/blob/main/lmcache_ascend/v1/multiprocess/custom_types.py)

搜索：

```text
class AscendIPCWrapper
def __init__
def to_tensor
```

它做的事情可以简化为：

```python
# 发送侧：请 TorchNPU 导出 Storage 的共享信息
shared_info = tensor.untyped_storage()._share_npu_()

# 接收侧：请 TorchNPU 从这些信息恢复 Storage
restored_storage = torch.UntypedStorage._new_shared_npu(...)

# 再把形状、步长、偏移装回 Tensor
restored_tensor.set_(restored_storage, offset, shape, stride)
```

以上是按源码改写的阅读示意，省略了参数及设备识别逻辑，不是可直接运行的代码。原实现还保存 dtype、shape、stride、storage offset，并处理设备标识与设备编号的对应关系。:chatgpt-content-reference{index="6"}

**这就是你问的“LMCache-driven 为什么和 TorchNPU 绑定”的具体连接处：这个实现没有自己完成底层内存共享，而是调用 TorchNPU 的共享能力。**

### 3. 新版设备接口，是另一种组织方式

前面我们讨论的：

```text
ipc_wrapper_cls
event_ipc_backend
create_cache_context
```

属于 LMCache 的 **`DeviceSpec` 设备后端接口**。源码在：

[LMCache：`platform/base/device_spec.py`](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/platform/base/device_spec.py)

基类中，wrapper 和 Event 后端默认没有实现；缓存上下文默认抛出 `NotImplementedError`。设备后端需要补上相应实现。:chatgpt-content-reference{index="7"}

**这两种风格不能混为一谈：**

```text
运行时补丁风格：
替换 CudaIPCWrapper 等现有引用

设备后端风格：
通过 DeviceSpec 显式注册 NPU 实现
```

这也说明：**仅凭某个开发版中没有 `DeviceSpec` 的一个属性，不能直接判断“没有做 Ascend 适配”。它可能用的是另一种补丁机制。** 后续核对你那两个 `0.1.dev…` 版本时，必须先识别实际代码结构。

## 四、TorchNPU 的 Python 层：把 PyTorch 对象接到 NPU 共享接口

### 1. `_share_npu_()` 这些方法是在哪里加上去的？

源码：

[TorchNPU：`torch_npu/utils/storage.py`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/utils/storage.py)

搜索 `_add_storage_methods`，可以看到它把 NPU 共享方法挂到 PyTorch Storage 上，例如：

```python
setattr(torch.UntypedStorage, "_share_npu_", _share_npu_)
setattr(torch.UntypedStorage, "_new_shared_npu", _new_shared_npu)
```

而这些 Python 函数继续转入 `torch_npu._C` 中的 C++ 实现。**这就是“让 PyTorch 的 Storage 认识 NPU IPC”的一个明确适配点。**:chatgpt-content-reference{index="8"}

### 2. 你写 `Queue.put(tensor)`，又是在哪里接进去的？

源码：

[TorchNPU：`torch_npu/multiprocessing/reductions.py`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/multiprocessing/reductions.py)

主要看三个函数：

| 函数 | 作用 |
|---|---|
| `_npu_reduce_tensor()` | 将 NPU Tensor 拆成共享信息和重建参数 |
| `rebuild_npu_tensor()` | 根据共享信息恢复 Storage，再恢复 Tensor |
| `_add_reductions_methods()` | 将 NPU 对应处理接入 PyTorch 的多进程序列化机制 |

发送侧调用 Storage 的 `_share_npu_()`；接收侧在需要新建共享 Storage 时调用 `_new_shared_npu()`。shape、stride、dtype 和 offset 等参数也需要一起保存。:chatgpt-content-reference{index="9"}

因此，两种入口可能在这里汇合：

```text
你的单元实验                         LMCache-Ascend 的封装
Queue.put(NPU Tensor)                AscendIPCWrapper(tensor)
        │                                    │
Tensor 的多进程序列化处理                     │
        │                                    │
        └──────────────┬─────────────────────┘
                       ↓
               Storage._share_npu_()
                       ↓
              TorchNPU 的 C++ 实现
```

**所以，Queue 本身不是显存共享的实现者；LMCache wrapper 也不一定经过 Queue。它们可以使用不同的消息传输方式，但复用相同的底层 Storage 共享入口。**:chatgpt-content-reference{index="10"}

## 五、TorchNPU 的 C++ 层：不是只把函数名换一下

### 1. Storage 共享的 C++ 实现

源码：

[TorchNPU：`torch_npu/csrc/ipc/StorageSharing.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/ipc/StorageSharing.cpp)

在这里，Python 方法与 C++ 函数对应为：

| Python 方法 | C++ 实现 |
|---|---|
| `_share_npu_` | `THNPStorage_shareNpu` |
| `_new_shared_npu` | `THNPStorage_newSharedNpu` |

发送侧会调用分配器的 `shareIpcHandle()`；接收侧会调用 `getIpcDevPtr()`，再处理 Storage 在整块分配中的偏移。这里还涉及引用计数和接收对象的释放处理。:chatgpt-content-reference{index="11"}

通俗一点：

> 底层共享的是一块设备内存；但一个 Tensor 可能只是这块内存中的一部分。TorchNPU 必须知道从哪里开始、占多少字节，以及其他进程什么时候不再使用它。

此外，TorchNPU 还用主机侧共享的引用计数管理生命周期。**所以，“这条链里出现了 CPU 共享内存”，也不代表 Tensor 的数据一定被复制到 CPU；共享计数和共享 HBM 数据是两个对象。**:chatgpt-content-reference{index="12"}

### 2. 一个关键发现：TorchNPU 内存 IPC 自己就有不同分支

源码：

[TorchNPU：`NPUCachingAllocator.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/core/npu/NPUCachingAllocator.cpp)

搜索这些符号：

```text
shareIpcHandle
SHAREABLE_NPU_MALLOC
SHAREABLE_NPU_EXPANDABLE_SEGMENT
fromShared
```

这份源码按**实际分配块的类型**走不同的共享路径：

| 分配路径 | 导出使用的接口 | 导入使用的接口 |
|---|---|---|
| 非 expandable segment 的分配块 | `AclrtIpcMemGetExportKey` | `AclrtIpcMemImportByKey` |
| expandable segment 分配块 | `AclrtMemExportToShareableHandle` | `AclrtMemImportFromShareableHandle`，之后还要映射 |

这些分支是代码中的实际判断，不是根据错误名称猜出来的。:chatgpt-content-reference{index="13"}

这正是为什么：

**“某一组底层 IPC 接口可用”，不等于“这个 TorchNPU 版本选择的另一组接口也可用”。**

而且还要看接口参数。比如当前 VMM 导出代码使用了 `ACL_RT_VMM_EXPORT_FLAG_DISABLE_PID_VALIDATION`。**同名 API 存在，与它支持调用方要求的全部标志和使用方式，也不是一回事。**:chatgpt-content-reference{index="14"}

这不是说该参数就是你们的根因，而是在解释：为什么“早期已经有 IPC API”仍不能代替当前调用链的兼容性检查。

## 六、CANN 和 HDK：底层接口在哪里接上？

### 1. TorchNPU 到 CANN 的边界非常明确

源码：

[TorchNPU：`core/npu/interface/AclInterface.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/core/npu/interface/AclInterface.cpp)

搜索：

```text
AclrtMemImportFromShareableHandle
```

这段封装的核心逻辑是：

```text
查找 CANN 动态库中的 aclrtMemImportFromShareableHandle
        ↓
找不到：报告接口不存在
        ↓
找得到：调用接口，返回其执行结果
```

可以直接看到 `TORCH_NPU_GET_FUNC`、函数存在性检查和后续调用。**这里是 TorchNPU 适配层，不是该设备内存共享功能的最终实现。**:chatgpt-content-reference{index="15"}

因此必须区分：

```text
TorchNPU 没有对应封装
        ≠
CANN 动态库没有这个符号
        ≠
符号存在，但这次调用失败
        ≠
硬件不具备这种能力
```

### 2. CANN 提供的是设备内存操作接口，不是 Tensor API

官方文档：

[CANN：`aclrtMemExportToShareableHandle`](https://www.hiascend.com/doc_center/source/en/canncommercial/850/API/appdevgapi/aclcppdevg_03_0118.html)

它描述的对象是**设备物理内存及共享句柄**，使用过程包括物理内存申请、导出、导入、地址映射和释放；页面也规定了进程白名单、生命周期和运行场景限制。它不负责替你保存 PyTorch Tensor 的 shape、stride 和 dtype。:chatgpt-content-reference{index="16"}

这就是“底层支持”和“TorchNPU 适配”的根本边界：

> **CANN 解决设备内存如何共享；TorchNPU 解决共享设备内存如何作为 PyTorch Storage／Tensor 使用。**

### 3. CANN 本身也有公开源码，但不能拿当前源码替代旧版驱动实现

[CANN Runtime 开源仓库](https://gitcode.com/cann/runtime)公开了运行时工程，目录中包括：

```text
src/acl       对外 ACL API
src/runtime   Runtime 实现
tests         测试
```

所以继续向下分析并不是只能看黑盒。:chatgpt-content-reference{index="17"}

但对于**你实际安装的 Driver `25.2.0`、Firmware `7.7.0.6.236`**，我们目前没有核对到与二进制完全对应的底层实现。因此，不能从上面几层的失败直接补写出“驱动里硬编码拒绝所有共享”“910B3 缺少跨进程 MMU 能力”等结论。

**公开接口、当前开源实现、实际安装二进制，仍然是三个需要对齐的对象。**

## 七、还有一条并行链：Event IPC 适配

内存共享解决：

> **另一个进程能不能访问这块数据？**

设备事件同步解决：

> **另一个进程什么时候可以访问，以及什么时候可以覆盖或复用它？**

TorchNPU 的 Event 链路可以在以下文件中看到：

| 文件 | 重点查找 |
|---|---|
| [`torch_npu/npu/streams.py`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/npu/streams.py) | `Event`、`interprocess`、`ipc_handle`、`from_ipc_handle` |
| [`NPUEvent.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/core/npu/NPUEvent.cpp) | Event 导出、从 handle 构造、等待和查询 |
| [`AclInterface.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/core/npu/interface/AclInterface.cpp) | `AclIpcGetEventHandle`、`AclIpcOpenEventHandle`、`IsSupportIpcEvent` |

公开实现确实沿着 Python Event → C++ NPUEvent → CANN 事件接口调用。:chatgpt-content-reference{index="18"}

### 代码里还能看到“接口存在”和“实际支持”不是同一回事

`IsSupportIpcEvent()` 不只是检查 Python 有没有一个方法。它还检查系统页大小、底层函数是否存在，并尝试创建带 IPC 标志的设备事件。:chatgpt-content-reference{index="19"}

更关键的是：

[TorchNPU：`NPUIPCTypes.cpp`](https://github.com/Ascend/pytorch/blob/v2.10.0/torch_npu/csrc/ipc/NPUIPCTypes.cpp)

这份源码中，Tensor 共享的同步处理有两种选择：

```text
可用的设备 IPC Event，并且资源条件满足
        → 使用 Event 同步

否则
        → 使用流同步
```

**这就从代码层面解释了：Tensor 内存共享测试通过，不一定意味着独立 Event IPC 能力也通过。**:chatgpt-content-reference{index="20"}

而当前 LMCache 的异步 `lmcache_driven` 设备接口要求单独的 Event 后端；文档明确指出，`engine_driven` 不要求这一项。因此，你的 **engine-driven 能启动**，不能替代这条并行链的验证。:chatgpt-content-reference{index="21"}

## 八、回到你的理解，应该怎样表述才准确？

你原来的理解是：

> 底层已经支持 IPC，所以 TorchNPU 和 LMCache-driven 应该也都支持。

现在可以改成：

> **底层可能已经提供某组设备内存共享接口；TorchNPU 需要按自己的分配器、元数据、生命周期和同步机制使用这些接口；LMCache 还需要把 TorchNPU 能力接入缓存注册、布局、搬运和事件后端。只有实际采用的各段实现与版本条件都满足，服务路径才成立。**

但还要避免另一种误解：

> 现在失败，是不是说明 TorchNPU 根本没有适配 IPC？

**也不是。我们已经在公开的 2.10 系列源码中看到了完整的共享入口、C++ 分配器分支和 Event 封装。当前要查的是“你安装的具体实现和底层版本能否配合工作”，以及“LMCache 补丁是否把需要的入口正确接上”，而不是简单判断“有没有写过 IPC 代码”。**:chatgpt-content-reference{index="22"}

后续报告里，建议始终用具体名称记录：

| 不再笼统写 | 改成 |
|---|---|
| IPC 支持／不支持 | **某组 CANN 设备内存共享接口**支持情况 |
| TorchNPU IPC 成功 | **某分配器路径的 Tensor 共享**成功 |
| IPC 全链路成功 | **内存共享、设备 Event、LMCache wrapper、KV 保存回填**分别通过 |
| 24.x 已支持 | 指明**具体版本、接口、参数和场景**的依据 |

**结论：你对“层级没有统一”的判断是对的。更准确地说，我们不仅要统一层级，还要统一同一层里的接口分支和使用条件。至于“HDK 24.1.RC1 是 IPC 首次支持版本”，目前核实到的是版本配套和项目通用要求，仍没有找到足以确认这句话的官方特性原文；不能把它继续当作已经证实的起点。**
