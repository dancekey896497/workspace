01 · 基础概念：KV Cache 与所谓 L1 / L2 / L3

这一章不出现任何 LMCache 代码。先把「缓存的是什么」「为什么要分层」这两件事说清楚，后面所有章节才有落脚点。

1.1先说 KV Cache 到底是什么东西

大模型推理分两个阶段，这两个阶段的硬件瓶颈完全不同，理解这一点是理解后面一切的前提。

为什么「缓存过」这件事能跨请求复用？

因为 Transformer 的 KV 只取决于从第 0 个 token 到当前位置的这段前缀。只要前缀一模一样，算出来的 KV 就逐比特一样（同样的模型、同样的精度、同样的并行切分）。

而真实业务里前缀重复率高得惊人：

  • 系统提示词（system prompt）：几千个 token，所有请求都一样。
  • Few-shot 示例、工具/函数定义、RAG 检索到的公共文档头。
  • 多轮对话：第 2 轮的前缀 = 第 1 轮的全部内容。
  • Agent 循环：同一份长上下文反复喂给模型几十次。
一句话记住 在 vLLM 里，同一个前缀被再次命中时，那部分 KV 不需要重算，直接复用（这叫 Prefix Caching / APC）。 但这个复用范围只限单实例内部、且这个 block 还没被踢出显存。LMCache 干的事，就是把这个复用范围从 「单实例显存内」扩大到「跨实例、跨进程、跨机器、断电也能留」。

1.2KV Cache 长什么样：分页、block、chunk

vLLM 的核心创新是 PagedAttention：把 KV Cache 切成固定大小的 block，像操作系统管理内存页一样管理显存。这带来的直接好处是：KV Cache 可以被寻址、被切片、被搬运——LMCache 才能把它拷出来。

新手最容易混的三个粒度 block_size（vLLM 显存分配单位，通常 16）≠ chunk_size（LMCache 缓存/哈希单位，常见 256）≠ page（vLLM v1 里也把 block 叫 page，是同一个东西的不同叫法）。

1.3L1 / L2 / L3 到底指什么

先破除一个误解：L1/L2/L3 不是 LMCache 源码里的类名，而是社区（LMCache 官方博客、文档、论文）用来描述「KV Cache 存储层级」的通俗说法，借用的是 CPU 缓存层级的隐喻。它们描述的是「KV Cache 此刻放在哪种介质上」。

1.4没有 LMCache 时会怎样

只用 vLLM 原生 Prefix Caching

  • KV 只能待在本实例显存里。
  • 显存不够时按 LRU 直接丢弃，丢了就得重算。
  • 重启进程 = 全部缓存清零。
  • 两台机器之间的公共前缀无法共享，各算一遍。
  • 长上下文场景显存被历史 KV 吃光，并发直线下降。

加上 LMCache 之后

  • 显存腾不出来时，把 KV 挪到 CPU 内存，显存立刻可用。
  • 进程重启后可从磁盘/远端复活缓存。
  • 多实例共享同一份 L3，公共前缀只算一次。
  • 长上下文不再必须靠堆显存。
  • 代价：显存↔内存↔磁盘的数据搬运开销，以及复杂度。
收益的本质 这是一道简单的不等式：
搬运这份 KV 的时间 < 重算这份 KV 的时间 → 用缓存划算。
例如 8K token 的 prefill 在 A100 上可能要 200ms，而 100MB 从 CPU 内存拷回显存只要 ~5ms。差了一个数量级，所以值得做。
