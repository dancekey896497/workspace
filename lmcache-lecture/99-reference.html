9.1先说明本讲义的可信度边界

请按这个标准使用本讲义
内容类型可信度说明
概念、架构、机制原理（L1/L2/L3、IPC/SHM/pickle、DMA、layerwise 思想）高这些是稳定的系统设计知识，不随版本变化
类名与方法名（LMCacheConnectorV1Impl、register_kv_caches、get_num_new_matched_tokens…）较高这些名字确实存在于对应仓库，但签名与细节随版本变化
目录结构（v1/distributed/l2_adapters/ 等）中较新加入的模块位置可能已调整
LMCache-Ascend 的内部实现细节待核实网络受限无法读源码，只依据 README/文档描述（见第 4 章开头）
性能数字（带宽、延迟量级）数量级只用于建立直觉，不是 benchmark 结果，务必自己实测
为什么无法核对源码：本次会话的网络访问被限制，只有 github.com 可解析； raw.githubusercontent.com、cdn.jsdelivr.net、docs.lmcache.ai、docs.vllm.ai、 deepwiki.com、hiascend.com、arxiv.org、huggingface.co、gitee.com 全部返回 「域名解析到非公网地址」而拒绝抓取。GitHub 的网页是客户端渲染，抓到的 HTML 里没有源码正文。 所以我保留了真实的文件路径与 API 名字（这些有把握），并在不确定处明确标注，没有编造具体代码行。

9.4API 名字分门别类

键与元数据

  • CacheEngineKey(model_name, world_size, worker_id, chunk_hash)
  • TokenDatabase.process_tokens(tokens, mask)
  • LMCacheEngineMetadata（模型名、层数、KV 形状、dtype、并行度）

引擎与存储

  • LMCacheEngine.store() / retrieve() / lookup()
  • StorageManager.reserve_put() / reserve_get() / get_blocking()
  • Allocator.allocate() → MemoryObj（.data_ptr / .tensor）
  • backend.submit_put_task() / contains() / get_blocking()

设备搬运

  • GPUConnector.from_gpu(...) / to_gpu(...)
  • CreateGPUConnector(config, metadata)
  • CUDA：cudaMemcpyAsync、torch.cuda.Stream/Event
  • NPU：aclrtMemcpyAsync、torch.npu.Stream/Event

vLLM 连接器接口

  • 调度侧：get_num_new_matched_tokens、update_state_after_alloc、build_connector_meta、request_finished
  • 执行侧：register_kv_caches、start_load_kv、wait_for_layer_load、save_kv_layer、wait_for_save、get_finished
  • register_connector(name, module, class)

CUDA IPC / 内存

  • cudaIpcGetMemHandle / cudaIpcOpenMemHandle / cudaIpcCloseMemHandle
  • cudaHostAlloc / cudaHostRegister（页锁定）
  • Storage._share_cuda_() / Storage._new_shared_cuda(...)
  • tensor.share_memory_()

CANN / 昇腾侧

  • aclrtMalloc / aclrtMemcpyAsync / aclrtStream / aclrtEvent
  • IPC 系列：导出 key / 导入 key / open / close / set-import-pid（以你版本文档为准）
  • torch_npu：torch.npu.Stream、torch.npu.Event、pin memory 支持
  • torch_npu 文档中的「内存共享（IPC）」章节

进程间通信

  • multiprocessing.shared_memory.SharedMemory(name=...)
  • multiprocessing.reduction（fd 传递 / file_descriptor 策略）
  • SCM_RIGHTS（UNIX 域套接字的 fd 传递）
  • /dev/shm（tmpfs）

序列化

  • pickle.dumps() / pickle.loads()
  • __reduce_ex__（对象自定义序列化协议）
  • torch.save() / torch.load()（自带 zip 容器）

9.6术语表

术语一句话解释
KV Cache每层 Transformer 缓存的 Key/Value 张量，Decode 阶段必须常驻显存
Prefill / Decode前者一次性算整个 prompt（算力瓶颈），后者逐 token 生成（带宽瓶颈）
PagedAttention / block / page把 KV 切成固定块管理显存，使 KV 可寻址、可搬运
chunk_sizeLMCache 的缓存与哈希粒度，要能被 block_size 整除
APC（自动前缀缓存）vLLM 内建的相同前缀复用能力，范围仅限单实例显存
L1 / L2 / L3社区对 KV 存储层级的叫法：显存+主机内存 / 本地盘 / 远端
pinned memory页锁定主机内存，可被 DMA / RDMA 直接访问
DMA不经过 CPU 的外设直接内存访问，拷贝大块数据的基本方式
CUDA IPC同机跨进程共享显存的机制，靠一个小句柄传递
SHM共享内存：同一物理页映射进多个进程，零拷贝
PicklePython 对象序列化协议，负责结构与元数据，必然复制
layerwise逐层搬运 KV 并与计算重叠，消除串行等待
KV ConnectorvLLM 中「把 KV 搬到外部/从外部搬回」的抽象接口
kv_role连接器角色：producer（只存）/ consumer（只取）/ both（双向）
EngineCorevLLM v1 的引擎核心进程，调度侧连接器跑在这里
NIXLNVIDIA 的传输抽象层，用于跨实例/跨机 KV 传输
HCCL / HCCS昇腾的集合通信库 / 多卡高速互联
PrivateUse1PyTorch 允许第三方注册新设备后端的机制，torch_npu 用它接入
ascendcl / aclrt*CANN 的 Runtime API，对标 CUDA Runtime
运行期 patchLMCache-Ascend 通过替换符号来适配 NPU 的手段

9.8建议的动手验证清单

  1. 跑通最小例子：单卡 + local_cpu only，确认同一个长 prompt 第二次请求 TTFT 明显下降。
  2. 确认命中粒度：把 chunk_size 改成 128 / 256 / 512，观察日志里的命中 token 数变化。
  3. 验证 pin memory 的收益：use_pin_memory: true/false 各跑一次，对比拷贝耗时。
  4. 验证 layerwise：开/关 enable_layerwise，对比 TTFT 与 GPU 利用率曲线。
  5. 加 L2：配置 local_disk，重启进程后看是否仍能命中。
  6. 加 L3：起一个 LMCache server，两个实例共享它，验证跨实例复用。
  7. 读源码：按 9.2 / 9.3 的两张表，把 start_load_kv → retrieve → to_gpu 这条链读一遍。
  8. 画自己的图：用第 7 章的七层结构，把你实际的机器拓扑（卡数、互联、网卡）标注上去。
