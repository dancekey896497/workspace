05 · CUDA IPC、SHM、Pickle 到底怎么运作

这三个词经常被混着说，其实它们解决的是三个不同的问题。先把问题分清，机制就自然清楚了。

5.2Pickle：把对象变成字节

它做了什么

Pickle 是一套「对象图 → 字节流」的协议。它不搬运任何显存，它只负责把「对象长什么样、里面有什么」写成一段可以被重建的指令序列。

Pickle 在 LMCache / vLLM 里的位置

  • LMCache 的远端传输：把 key、metadata、以及 KV 的字节打包发给 LMCache Server。数据面常走「自定义二进制头 + 裸字节」，控制面（键、元信息）走 pickle。
  • vLLM 的 ZMQ 通信：调度器与 worker 之间传消息（含 EngineCore 相关元数据）时会用到 pickle，配合共享内存传大数据。
  • 缓存到磁盘：写文件时 payload 的字节布局往往是「自己定义的格式」，但读取时要知道形状/dtype，这部分信息就是序列化出来的。
Pickle 的三个硬限制 ① 不安全：绝不要反序列化不可信来源（vLLM 甚至专门做过相关安全加固）。
② 慢：纯 Python 层的编码/解码，大数据量下 CPU 会成为瓶颈。所以高性能路径都会绕过它，直接传裸字节。
③ CUDA 张量不能直接 pickle 出进程：它会报错或隐式触发一次显存→内存拷贝。要跨进程共享显存，必须用 CUDA IPC。

5.3SHM：同一块物理内存，映射到两个进程

核心原理

操作系统的虚拟内存机制允许同一段物理页被映射进不同进程的地址空间。两个进程各自的虚拟地址不同，但读写的是同一块物理内存。这就是共享内存，零拷贝。

fd 传递：SHM 是怎么「告诉」另一个进程的

匿名共享内存没有名字，另一个进程要靠文件描述符传递找到它。这在 UNIX 域套接字上用 SCM_RIGHTS 实现，是 Python multiprocessing 与 PyTorch 张量共享的底层机制。

SHM 在 LMCache / vLLM 里的位置

  • vLLM 的进程间通信：调度器 ↔ worker 之间既要传控制消息（小），也要传大对象（如输出张量、采样结果）。大对象走 SHM，消息里只放「名字/句柄」。这就是很多实现里出现 ShmRingBuffer / 共享内存通信类的背景。
  • LMCache 多进程模式：引擎跑在独立进程时，worker 与引擎之间传 KV 需要跨越进程边界。若走 CPU 内存，SHM 是最省拷贝的方式。
  • 与 pinned memory 的区别（重要）：pinned 不等于 shared。pin 只影响「设备/网卡能否直接 DMA 访问」；shared 只影响「其他进程能否看到」。一块内存可以同时是 pinned 和 shared，也可以是其中之一。
记住这个区分 pinned 解决「谁能高效访问」（DMA/RNIC），shared 解决「谁能看到」（跨进程）。
LMCache 的 L1 缓冲通常是 pinned（为了显存↔内存快、为了能被 RDMA 网卡直接读）；当引擎与 worker 分进程时，才额外需要 shared。

5.4CUDA IPC：让另一个进程直接读写你的显存

它解决的独特问题

显存不能像主机内存那样被随便 mmap 到别的进程（设备内存的地址空间由 GPU 的页表管理，且受 IOMMU/隔离保护）。所以 CUDA 提供了一套专门的 API：导出句柄 → 传递句柄 → 导入句柄 → 拿到一个可用的设备指针。

PyTorch 把它包装成了什么

你平时不直接调 cudaIpc*，PyTorch 把它们包装成了 storage 层面的能力，并配合 torch.multiprocessing 自动完成句柄传递。

一个常被问的问题：LMCache 自己用 CUDA IPC 吗？ 在「LMCache 以库的形式嵌入 vLLM worker 进程」的默认模式下，KV 的搬运是同进程内的 DMA 拷贝（显存→pinned 内存），不需要 CUDA IPC。
CUDA IPC 真正重要的场合是：多个进程需要共享同一块显存缓冲区——例如多进程模式、跨进程共享权重、以及 vLLM 自己的多进程张量传递。 所以读 LMCache 代码时，看到 IPC 的地方往往在「进程边界」而不是「缓存逻辑」里。
