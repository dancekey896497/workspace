07 · IPC 从底层到上层：CUDA 与 torch-npu 逐层对照

你问的「torch-npu 的 IPC 在什么层级」——答案是：它是一个横跨「驱动 / Runtime / PyTorch」三层的机制，不是一个单独的 API。这一章把整条栈拆开，一层层对照。

7.1整条栈：7 层结构

关于 Ascend 侧 API 名称的说明 CANN 的 IPC 系列 API（aclrtIpcMemGetExportKey / aclrtIpcMemImportByKey / aclrtIpcMemOpen / aclrtIpcMemClose / aclrtIpcMemSetImportPid）是 CANN 提供的设备内存 IPC 接口， 与 CUDA 的 cudaIpc* 在设计意图上一一对应，但参数与语义细节不完全相同（例如多了 PID 约定）。 需在机器上核实具体签名请查你所用 CANN 版本的《应用开发指南》与 torch_npu 文档。

7.2PyTorch 是怎么把两套设备「统一」起来的

PyTorch 从 1.8 起引入了 PrivateUse1 机制：允许第三方把一套新的设备后端注册进 PyTorch，复用它的张量、调度器、缓存分配器等基础设施。torch_npu 就是通过这个机制接入的。

「层级」问题的标准答案 如果有人问你「torch-npu 的 IPC 在什么层级」，可以这样回答：
它不是一个单独的层，而是三层协作的结果：
  • L5（PyTorch 存储层）提供与 CUDA 同名的共享接口（_share_* / _new_shared_* / share_memory_），由 torch_npu 实现；
  • L4（CANN Runtime）是 IPC 的真正定义层，提供设备内存的导出/导入 API；
  • L3（昇腾驱动）决定可行性与权限（设备身份、PID 校验）。
越往下越「设备相关」，越往上越「跨平台统一」。
