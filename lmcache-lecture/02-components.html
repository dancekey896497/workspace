02 · LMCache 的组件组成

从外到内拆：最外面是「接进推理引擎的接口」，中间是「引擎本体」，里面是「存储与搬运」。

2.1仓库目录地图

先在脑子里建立「文件在哪」的地图，读源码时不会迷路。版本相关目录结构在不同版本间有调整，尤其是多进程模式（multiprocess/）与 L2 adapter（distributed/）是较新加入的。

2.2逐个组件：它们各自负责什么

① LMCacheEngine —— 门面 + 装配厂

你几乎不直接 new 它，而是通过 builder 拿实例（保证同一进程内同配置只建一个）。它的构造函数干了三件事：建分配器、建后端、建连接器，然后把它们串成一个 StorageManager。

记住这条装配线 Allocator（池子）→ Backends（池子上的分层）→ StorageManager（把两者绑一起）→ GPUConnector（池子与显存之间的搬运）→ TokenDatabase（池子里的东西叫什么名字）。 后面看数据流时，就是把数据沿这条线走一遍。
对外方法语义谁在调
store(tokens, mask, **kwargs)把一段 KV 按 chunk 存进缓存适配器在「算完之后」调
retrieve(tokens, mask, **kwargs)按键取出 KV 并写回显存适配器在「算之前」调
lookup(tokens, mask)只查前缀能命中多少（不搬数据）调度阶段，决定要不要省掉 prefill
clear() / close()清空所有层 / 释放资源测试与关停

② TokenDatabase —— 决定「什么算同一份缓存」

这是最容易出错、也最影响命中率的组件。它的工作只有两步：切、哈希。

③ StorageManager —— 分层的调度者

它持有「一块内存池」和「一串后端」，对上层只暴露两个动作：本来要写的东西，先申请一个内存对象（reserve），要读的东西，去各层找并填充内存对象。

④ MemoryAllocator —— 内存池与「借条」MemoryObj

LMCache 不会为每份 KV 都 malloc 一次。它在启动时一次性申请一大块（max_local_cpu_size），自己切分管理。这么做是为了避免频繁分配的开销，也为了能直接把这块内存注册给网卡做 RDMA。

⑤ 存储后端：LocalCPU / LocalDisk / Remote / NIXL

后端层级文件干什么关键细节
LocalCPUBackendL1 storage_backend/local_cpu_backend.py 在主机内存里保存 KV，用 key → MemoryObj 字典索引 满了按 LRU 淘汰；淘汰是「丢掉」，不是「下沉」（下沉由别的后端负责）
LocalDiskBackendL2 storage_backend/local_disk_backend.py 把 KV 写成磁盘文件，进程重启后还在 存在 local_disk 目录；要管文件布局、淘汰、以及「异步写」不阻塞推理
RemoteBackendL3 storage_backend/remote_backend.py 把 KV 发到独立的 LMCache Server 基于 ZMQ；remote_url 指定 host:port；可多级 URL 做「本地 server + 远端 server」
P2P / NixlStore跨实例 storage_backend/nixl_store.py 实例之间直接传 KV，不经过中心 server NIXL 是 NVIDIA 的传输抽象（RDMA/GPU Direct）；enable_p2p、lmcache.peer_init_url 控制
L2AdapterInterfaceL2/远端 distributed/l2_adapters/ 较新的可插拔抽象，把各种远端 KV 存储统一成 adapter 例如 RESP 协议 adapter（对接 Redis 类）、NIXL adapter、Mooncake adapter。版本相关
「L1 / L2 / L3」在代码里怎么落地 代码里没有 class L1。分层是通过配置项 + 注册后端顺序实现的： max_local_cpu_size 管 L1 容量，local_disk 决定有没有 L2，remote_url / enable_p2p 决定有没有 L3。 写入时靠 StorageManager 按顺序分发，读取时按顺序查找。

⑥ GPUConnector —— 显存与缓冲区之间的实际搬运

这是最「脏」也最讲性能的组件：vLLM 的 KV 在显存里是按层、按物理 block 散落的，还有 TP（张量并行）切分、MLA/非 MLA 结构差异、量化格式差异。连接器要负责把这些差异抹平。

连接器类名（节选）适用场景
VLLMPagedMemGPUConnectorV2vLLM v1 分页 KV、非 layerwise 的标准实现
VLLMPagedMemLayerwiseGPUConnector逐层搬运版本，配合 vLLM 层回调
VLLMPagedMemGPUConnector / VLLMPagedMemGPUConnectorV3不同版本/不同 KV 布局的变体
VLLMPagedMemNPUConnector 等昇腾 NPU 版本，由 LMCache-Ascend 提供（见第 4 章）
VLLMPagedMemCPUConnector / …CPUConnector纯 CPU 模式（无设备参与）
CreateGPUConnector(config, metadata)工厂函数，按配置与 metadata 选具体实现

⑦ 切面组件：Worker、统计、异步

LMCacheWorker（与调度器对话）

在「引擎进程」和「调度/控制进程」分离时，需要一个通道来交换「这个请求能命中多少」这类决策。它通过 ZMQ 在两端通信，让调度器在还没开始推理时就知道 LMCache 能帮上多少忙。

开关键：enable_async_loading。相关文件：v1/worker.py（版本相关）。

Observability（统计）

记录命中率、各层命中次数、拷贝耗时、内存占用等，供 Prometheus 抓取。调优 LMCache 时最先看的就是命中率与「搬运耗时 vs 重算耗时」。

相关目录：v1/observability/；开关：enable_metrics。

BlendEngine（在 CPU 上做模糊匹配）

不止精确前缀匹配：它能在 CPU 侧搜索「部分重叠」的历史 KV 并拼接复用。适合多轮对话、RAG 这种前缀结构不规整的场景。

相关文件：v1/blend_engine.py；开关：enable_blending。

Serializer / CacheEngineKey

把 key 和 KV 变成可跨进程序列化的字节。key 是 (model_name, world_size, worker_id, chunk_hash)；值是「元数据 + 裸张量字节」。

相关文件：v1/serial_utils.py（版本相关）、v1/cache_interface.py。
