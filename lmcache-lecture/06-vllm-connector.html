06 · vLLM 里跟 LMCache 相关的都有什么

你问的「LMCache-driver 和 engine-driver」在 vLLM 里其实对应两个角色：调度侧（scheduler/driver）和执行侧（worker/engine）。这一章把它们逐个点名，并给出真实代码路径。

6.1先纠正一个命名

vLLM 里没有叫 "LMCache driver" 或 "engine driver" 的类 这是社区口语化的说法。准确的说法是 vLLM 的 KV Connector 框架把连接器拆成两个角色：
  • Scheduler 侧（跑在 EngineCore 的调度进程里）—— 决定「这次请求能省多少、要搬多少」。有人叫它 driver 侧。
  • Worker 侧（跑在模型执行进程里）—— 真正执行搬运。
同一个连接器类内用 @supports_hma 之类的装饰器和角色判断来区分自己当前在哪个进程、该干什么。 另外「EngineCore」是 vLLM v1 的引擎核心进程；LMCache 的代码是挂进它的，不是引擎本身的一部分。

6.2vLLM 侧的文件清单

LMCache 侧对应的文件（配对看）
  • lmcache/integration/vllm/lmcache_connector.py —— 与 vLLM 的 lmcache_connector.py 对应（有些版本 LMCache 侧直接提供同名模块）。
  • lmcache/integration/vllm/vllm_v1_adapter.py —— 与 lmcache_integration/vllm_v1_adapter.py 对应，提供 LMCacheConnectorV1Impl。
  • 在不同 vLLM 版本上，LMCache 还提供过 lmcache_connector_v1_085.py 之类针对特定版本的实现——这本身就说明接口随 vLLM 版本在变。

6.3连接器接口：两套方法，两个进程

如果只让你读一个文件 读 register_kv_caches 和 start_load_kv 的实现。前者告诉你「显存里的 KV 长什么样」， 后者告诉你「数据怎么进去」。这两个方法串起来就是完整的搬运路径。

6.4LMCacheConnectorV1：角色分派与委托

这个类的职责非常薄：判断自己是调度侧还是执行侧，然后把调用转给 LMCacheConnectorV1Impl。真正的逻辑都在 Impl 里。

6.5vllm_v1_adapter：真正干活的地方

这个文件是整条链路的心脏。它做四件事：持有引擎实例、维护 per-request 状态、拼装 LoadSpec/SaveSpec、把 vLLM 的数据结构翻译成 LMCache 的调用。

上面是结构摘要，不是可复制粘贴的原文 vLLM 的 connector 接口在 0.8 → 0.9 → 0.10 → … 之间改过多次（参数名、是否返回 deferred、meta 的字段）。 我保留了真实存在的类名与方法名（LMCacheConnectorV1、LMCacheConnectorV1Impl、 register_kv_caches、get_num_new_matched_tokens、LoadSpec 等）， 但省略了参数细节。请以你安装版本的实际文件为准。

6.6kv_role：三种角色是什么意思

kv_role含义典型场景LMCache 下的行为
kv_producer 只负责把算好的 KV 送出去（保存） 分离式部署里的 prefill 实例 只走 save 路径
kv_consumer 只负责接收 KV（加载） 分离式部署里的 decode 实例 只走 load 路径
kv_both 既能存也能取（双向） LMCache 的典型配置：同一实例先缓存、后续请求复用 两条路径都开；命中即复用，算完即存
为什么 LMCache 用 kv_both LMCache 的定位不是「在实例之间搬 KV」（那是 NIXL / disaggregated prefill 的目标）， 而是「给本实例加一层缓存」。所以它要能存（第一次请求算完存起来）也能取（后续请求命中）。

6.8配置项清单

配置位置说明
kv_connectorKVTransferConfig固定填 "LMCacheConnectorV1"（由 LMCache 注册）
kv_roleKVTransferConfigkv_both / kv_producer / kv_consumer
kv_connector_extra_configKVTransferConfig透传给连接器的额外参数（如兼容性开关）
kv_connector_module_pathKVTransferConfig从任意模块路径加载连接器类（自定义连接器用）
--kv-transfer-configCLI以上配置的 JSON 入口
LMCACHE_CONFIG_FILE环境变量指向 LMCache 的 YAML 配置（chunk_size、分层、pinned 等）
LMCACHE_USE_EXPERIMENTAL环境变量启用新版（v1）适配路径
VLLM_USE_V1环境变量选择 v0/v1 引擎；LMCache 主要面向 v1 的 connector 框架
注册机制为什么重要 register_connector 让「连接器名字 → 实现类」的映射可以由第三方包注册。 这就是为什么 LMCache 不需要改 vLLM 源码：vLLM 只提供框架和抽象基类，LMCache 通过注册把自己插进去。 想写自己的连接器，照抄这个套路即可。

6.9版本差异与排错

常见版本差异

  • 连接器文件位置：早期在 vllm/distributed/kv_transfer/kv_connector/，后来加了 v1/ 子目录。
  • LMCache 侧提供过 lmcache_connector_v1_085.py 这类版本专用实现，说明接口变过。
  • 是否支持 register_kv_caches、返回值是否需要 deferred 对象，随版本不同。
  • v0 引擎用 lmcache/integration/vllm/vllm_adapter.py（旧路径），与 v1 完全不同。

排错清单

  1. 日志里有没有 LMCacheConnectorV1 的初始化记录？没有 = 配置没生效。
  2. 连接器有没有抛异常被降级？搜日志里的 connector 相关 warning。
  3. 命中数是不是 chunk_size 的整数倍？不是 = 哈希粒度不匹配。
  4. 开了 APC（enable_prefix_caching）吗？与 LMCache 的交互要留意。
  5. TP > 1 时，每个 rank 的 worker_id 不同，缓存天然按 rank 隔离——期望的命中率要按单 rank 算。
