# LMCache 适配 MemFabric：已有尝试调查

调查日期：2026-10-22。范围是公开一手文档、源码、PR/Issue 与提交索引。没有执行 Ascend 实机验证，没有修改业务代码或服务器。

## 结论

1. 本次未找到可直接采用的 **LMCache 原生 MemFabric 后端/传输插件**，但不能据此断言没有未公开分支或未被索引的尝试。
2. **已有非常相关的完整传输实现，而且不需要 MemCache**：MemFabric 官方仓库保存 Mooncake v0.3.9 的 BM/TRANS 适配补丁；Mooncake 主线于 2026-10-16 合入新的 TENT MemFabric TRANS 后端。
3. 因而应同时评估“直接给 LMCache 接 BM/TRANS”与“复用 Mooncake 的 MemFabric 实现”。后者可以省下对象目录等工作，但并非已验证的 LMCache+A3HCCS 一键组合。
4. 新 TENT 后端仍有 **device_sdma 的 GVA/Host 分配修复 PR #4834 未合入**。这恰好说明适配不能只关注传输函数，还要证明分配、注册、地址域、完成及释放。

## 已有实现一：官方 MemFabric 的 Mooncake BM/TRANS 补丁

来源：

- [UB Transport 文档](https://github.com/Ascend/memfabric_hybrid/blob/master/patches/mooncake/ub_transport.md)
- [Mooncake v0.3.9 补丁](https://github.com/Ascend/memfabric_hybrid/blob/master/patches/mooncake/tag_v0.3.9.patch)
- 旧链接：[openFuyao v0.3.7-dev UB Transport](https://gitcode.com/openFuyao/mooncake/blob/v0.3.7-dev/doc/zh/ub_transport.md)，本次未成功读取原文；上面官方仓库保留版本已读。

文档明确区分：池化能力经 `mooncake_store` 使用，P/D 传输经 `mooncake_transfer` 使用。构建参数是旧路线的 `USE_UB=ON`，接口协议为 `ub`，配置包括 `MF_STORE_URL`、`MF_DRAM_SIZE`、`MF_HBM_SIZE`、`MF_OP_TYPE=device_sdma/device_rdma`。

关键代码：

1. `RealClient::setup_internal` 在 `USE_UB` 下设置 `SMEM_BM`。
2. 初始化 BM，创建配置中的 DRAM/HBM 池并 join。
3. `MemFabricGetSegment()` 返回本 BM rank 的 Host 池地址与容量；`RealClient` 将该 segment 挂到 Mooncake 的对象分配与元数据体系。
4. 用户缓冲区注册转发到 `smem_bm_register_user_mem`；数据访问进入 BM copy。
5. 同一补丁另有 TRANS 路径用于点对点传输。

它对本项目的意义：`LMCache → Mooncake Store(ub) → MemFabric BM` 在结构上可以复用 Mooncake 的 key 目录、对象分配和管理，而不需要另接 MemCache。但补丁固定旧 Mooncake v0.3.9、使用旧 MemFabric ABI；当前 LMCache MP 原生 Mooncake 连接器调用新的 `setup_internal(ConfigDict)` 和 batch API，不能直接断言可编译兼容。旧补丁的 unregister 路径也存在 no-op，生命周期不能直接照抄。

建议：作为 BM 接入的移植参考与历史基线，不把旧补丁直接套入最新 Mooncake。不要将这里的 `USE_UB`、`protocol=ub`、`MF_OP_TYPE` 与下面新 TENT 路线混配。

## 已有实现二：Mooncake 主线 TENT MemFabric Transport

[PR #4682](https://github.com/kvcache-ai/Mooncake/pull/4682) 于 **2026-10-16 07:37:25 UTC 合入 main**。合入提交：`129c9614deecccd13d5f60e1d8bc4ba5b9a21e6b`。

[当前官方文档](https://github.com/kvcache-ai/Mooncake/blob/main/docs/source/design/transfer-engine/transport/memfabric_transport.md) 的调用链是：

```text
TENT TransferEngine
  → MemFabricTransport
  → MemFabricUnderApi（dlopen / dlsym）
  → libmf_smem.so 的 smem_trans_* API
```

这是真正使用 MemFabric 的实现，不是仅同名的 HIXL FabricMem。

启用条件：

- 源码构建 `USE_TENT=ON`、`USE_MEMFABRIC=ON`；文档建议默认在 Ascend Direct/HIXL 与 MemFabric 之间选择其一。
- 运行 `MC_USE_TENT=1`，`MC_TENT_CONF` 指向 JSON，其中 `transports.memfabric.enable=true`。
- `MF_PROTOCOL` 选择 `device_sdma`、`device_rdma` 等；`libmf_smem.so` 在动态库搜索路径中。
- Mooncake Store 的 `protocol` 仍为 `ascend`。不要猜成 `memfabric`。
- 文档列 CANN >=9.0.0；MemFabric 动态库必须匹配四参数 `smem_trans_batch_status_query(handle, batch_id, &result, flags)` ABI。

PR 作者报告的实机证据是两节点 Ascend、CANN 9.0.1、SGLang P/D 与 L3（结果项写 A5）；不是 LMCache，也不是 A3 HCCS。正文有 `device_xdma` 与当前 parser 支持值不一致之处，因此不能照搬 PR 里的协议拼写。当前源码的 parser 支持 `device_sdma/device_rdma/host_rdma/device_urma/device_uboe`。

本次 GitHub latest release 是 [v0.3.13.post1](https://github.com/kvcache-ai/Mooncake/releases/tag/v0.3.13.post1)，发布日期 2026-08-31，早于该合入。不能假设现有 wheel 已包含新后端。

### 已知未完成边界：SDMA 分配修复

[PR #4834](https://github.com/kvcache-ai/Mooncake/pull/4834)，标题 `Issue of Memfabric GVA allocation for NPU SDMA scenario`，创建于 2026-10-21，检索时 **open、未合入**。head：`8b174525ae79c4a897d236d6113ec1f76b9c4c33`。

其补丁针对 `device_sdma` 将 Store Host 分配改为 `smem_mem_alloc`，绕过普通 `aclrtMallocHost`/hugepage mmap；跟踪所有权并用 `smem_mem_free` 释放；对本地 SDMA 读写 buffer 改变注册行为；新增 `MF_STORE_PROTOCOL` 以区分 Store 和独立 TE/P/D 协议。

这说明当前主线的普通 Host allocator 不应被当作 SDMA GVA 池的已验证实现。PR 的测试说明为空，不能宣称新补丁已完成硬件验证，也不能把尚未合入的 `MF_STORE_PROTOCOL` 当作主线正式参数。

### LMCache 侧如何复用、还缺什么

已有 [MooncakeStore L2 adapter](https://github.com/LMCache/LMCache/blob/v0.5.6/lmcache/v1/distributed/l2_adapters/mooncake_store_l2_adapter.py) 将 setup 配置转发到 Mooncake，具备组合基础。

但该 factory 只在 `protocol=rdma` 时启用 L1 预注册；[原生 connector](https://github.com/LMCache/LMCache/blob/v0.5.6/csrc/storage_backends/mooncake/connector.cpp) 的 `ensure_registered()` 遇到无效的 `l1_registration` 直接返回。Ascend/MemFabric 的 LMCache L1 内存分配、地址域、注册和工作线程上下文因此仍需实测并可能改代码。不能只改环境变量就宣布 LMCache 适配完成。

另有 [LMCache MP Mooncake TE 传输实现](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/distributed/transfer_channel/impl/mooncake_te_impl.py)：通过 `MC_TE_PROTOCOL`（默认 tcp）初始化 TransferEngine，并注册整个 L1 区域。这是 `LMCache P2P → Mooncake TE/TENT → MemFabric TRANS` 的另一个组合候选，可借用现有 P2P 控制面，仍无本次可查到的 LMCache+MemFabric+A3HCCS 联调证据。

## 相邻实现：适合复用的代码

### SGLang 本地 Host↔NPU 路径

[SGLang PR #38826](https://github.com/sgl-project/sglang/pull/38826) 于 2026-09-10 合入，增加 `SGLANG_HICACHE_HOST_MEM_BACKEND=memfabric`，将 HiCache Host 分配改为 MemFabric 映射内存，并使用 `offload.kv_exchange_copy`。

它明确处理：普通 `torch.pin_memory` 缓冲区只能被 SDMA 访问，不能直接被其 AIV sparse-copy kernel 解引用。涉及 `pool_host/common.py` 的分配器、容量管理与异步 staging 生命周期，`pool_host/mla.py` 的 Host VA→DVA 与稀疏传输。

价值：可参考本机 CPU/NPU 内存适配；它不是跨实例共享池，也不是 LMCache 插件。

### vLLM-Ascend TRANS 包装及原语诊断

- [memfabric_transfer_engine.py](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/distributed/kv_transfer/utils/memfabric_transfer_engine.py)
- [test_memfabric_pd_read.py](https://github.com/vllm-project/vllm-ascend/blob/main/tools/test_memfabric_pd_read.py)

后一个脚本不启动推理服务：Prefill 进程分配确定性 NPU 数据，Decode 拉取并比较；默认目的内存是 MemFabric offload Host buffer，也可用 NPU buffer 做对照。其说明面向两节点，改为单机双进程时仍要核对设备与端点标识，不能直接视为已有单机验收。

## 对本项目方案判断的影响

- 要求 LMCache 直接承担缓存语义、完全不引入其他对象 Store：优先研究直接 BM L2 或直接 TRANS P2P；借鉴上述实现的 allocator/注册/完成契约。
- 可以引入 Mooncake 但不能引入 MemCache：已有 BM 旧补丁和 TRANS 新主线，可以减少从零开发量，但需分别处理旧版本兼容或新 SDMA 缺口。
- 已确认用户有机内 HCCS、缺跨机线缆/交换机：可以先做真实机内多进程/多 NPU 原语与 LMCache 适配验证；这些结果不能外推跨主机 GVA、网络初始化、拓扑、故障与性能。
- 本报告的所有硬件结论均为 `NOT_VERIFIED`；引用 PR 作者测试时已标注原配置边界。
