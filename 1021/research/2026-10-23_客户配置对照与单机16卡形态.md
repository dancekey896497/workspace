# 参考客户配置：Qwen3-8B 单机 16 卡形态

日期：2026-10-23。本文补充[隔离 A3 终端实施指南](2026-10-23_隔离A3终端实施指南.md)，落实“能沿用的配置尽量沿用，按单机资源调整形态”。

**目标：Qwen3-8B，单机 1P1D，P TP8 / D TP8，两侧 PP1、DP1，使用独立 LMCache service，后续接入 MemFabric BM。** 首次连通仍按主指南 TP1+TP1；本文的 TP8+TP8 是基础验证通过后的形态对照。以下没有 A3 实机执行证据，状态均为 `NOT_VERIFIED`。

## 1. 这份客户资料原本是什么形态

已阅读原件，保留原始目录不改动：

- [客户说明](<../1. 原始客户资料/客户原始部署资料_纯净版_20261023/README.md>)。
- [start_p1.sh](<../1. 原始客户资料/客户原始部署资料_纯净版_20261023/start_p1.sh>)、[start_p2.sh](<../1. 原始客户资料/客户原始部署资料_纯净版_20261023/start_p2.sh>)。
- [start_d.sh](<../1. 原始客户资料/客户原始部署资料_纯净版_20261023/start_d.sh>)。
- [GLM 量化配置](<../1. 原始客户资料/客户原始部署资料_纯净版_20261023/GLM-5.1_best_practice.yaml>)。

`p1/p2` 是 **一个 P 实例的 node-rank 0/1**，脚本写的是 TP16、PP2、两节点；不是两个独立的 P 服务。按标准 TP×PP 计算，这个 P 实例就需要 32 个 worker。D 的 Connector 声明 DP4×TP4，实际启动大小还取决于 `$3`、`$7` 入参。因此原形态无法原样装进单机 16 个逻辑设备。

P1/P2 的 master 地址字符串也不一致。原件保留作来源；本次使用本机配置，不推测原客户网络中两地址是否映射同一节点。

## 2. 单机资源怎样安排

下表以 S0 确认有 **16 个可用逻辑 device** 为前提；数字仅是示例，实际按拓扑分组。A3 的物理卡/chip/device 计数不要混用。

| 阶段 | A / 未来 P | B / 未来 D | 缓存服务和池 |
| --- | --- | --- | --- |
| 首次功能验证 | TP1，1 个空闲 device | TP1，另 1 个空闲 device | 一个 LMCache service；余下设备可用于 BM 独立验证 |
| 客户形态对照 | TP8，示例 `0,1,2,3,4,5,6,7` | TP8，示例 `8,9,10,11,12,13,14,15` | 一个 LMCache service，可见两侧设备 |
| 最终 1P1D | 同上，由协调入口发起 prefill | 同上，等待并恢复 P 的 KV | adapter 提供 BM 存取，协调层保证 KV ready 后再交给 D |

P/D 各加载一份完整模型，由各自 TP 组切分；不是把一份模型的前半层给 P、后半层给 D。PP 固定 1，也不保留 `41,37` 的 GLM 分层。先使用对称 TP，减少首版需要处理的 KV 分片重排。

TP8+TP8 是为了接近客户的多卡运行方式，并不宣称是 Qwen3-8B 的最佳吞吐配置。BM 池服务不等于额外加载一份模型，但其 rank 仍有 device 绑定、runtime 和可能的临时 HBM 开销。16 个设备都用于引擎后，需要验证 BM 与引擎共用设备是否可行；若有冲突，先用 TP4+TP4、保留空闲设备验证池，不擅自认定必须有第 17 张卡。

## 3. 哪些保持一致，哪些必须调整

### 3.1 保留或对齐

| 项目 | 客户原值 | 本次选择 |
| --- | --- | --- |
| 参考镜像 | `quay.io/ascend/vllm-ascend:v0.23.0-a3` | 优先复用这套已可用环境，记录实际版本，不自动换新镜像 |
| 启动方式 | `vllm serve` | 保留 |
| 模型 seed | `1024` | 保留；与 `PYTHONHASHSEED=0` 是两件事 |
| API 监听 | `0.0.0.0` | 保留；本机请求仍用 `127.0.0.1` |
| 显存预算 | `0.92` | 保留；启动前核实空闲 HBM |
| 进程后端 | P 为 `mp` | 两侧均为 `mp`；这是 vLLM worker 后端，与 LMCache MP 是不同配置 |
| OMP | `OMP_PROC_BIND=false`、`OMP_NUM_THREADS=1` | 保留 |
| NPU allocator | `expandable_segments:True` | 保留 |
| 通信/初始化 | `HCCL_OP_EXPANSION_MODE=AIV`、`ACL_OP_INIT_MODE=1`、`ASCEND_A3_ENABLE=1` | 沿用当前配套环境中的设置；不能以 export 成功证明优化生效 |
| HCCL buffer | P `400`、D `256` | 按角色保留 |
| P 执行模式 | eager | 保留 |
| P batch / seq 上限 | `16384` / `64` | TP8 对照阶段保留 |
| D batch / seq 上限 | `164` / `32` | TP8 对照阶段保留；这是借用的对照值，不是 Qwen 的最佳值 |
| D task queue | `TASK_QUEUE_ENABLE=1` | 保留 |
| P FlashComm1 | `VLLM_ASCEND_ENABLE_FLASHCOMM1=1` | TP8 对照保留；TP1 连通阶段不额外启用 |

官方 v0.23.0 文档仍描述 FlashComm1 环境变量兼容方式；后续版本可能转移到 `--additional-config`，因此只在盘点出的具体版本上核对，不能靠一份脚本覆盖所有版本。[配置说明](https://docs.vllm.ai/projects/ascend/en/v0.23.0/user_guide/configuration/additional_config.html)。

镜像标签来自客户原件，不等于我们已经检查过远端镜像内容。CANN、驱动、torch/torch_npu 和 hcomm 仍按 S0 的真实配套确定，不能把 LMCache 文档的最低版本当作整套 v0.23.0 环境的依赖锁定。

### 3.2 因模型、机器或接入方式改变

| 项目 | 原值 | 本次调整和原因 |
| --- | --- | --- |
| 模型 | GLM-5.1-W8A8C8-MTP | 标准 Qwen3-8B BF16；若实际提供的是量化权重，需重新核对，不混用此命令 |
| TP / PP / DP | P TP16 PP2；D 声明 DP4 TP4 | P TP8 PP1 DP1；D TP8 PP1 DP1，合计 16 device |
| 多节点参数 | `nnodes=2`、两种 node-rank、跨节点 master IP | 普通单节点启动；去掉原跨节点地址/rank，两个实例的 master 端口分开 |
| 分层 | `VLLM_PP_LAYER_PARTITION=41,37` | 删除；Qwen3-8B 不是这套层数，也不用 PP2 |
| 上下文 | `202752` | 首次 4096；TP8 对照 32768 |
| 量化 | `--quantization ascend`、W8A8C8 YAML | 标准 BF16 权重不传；原 YAML 属于 GLM 的量化材料，不是通用 vLLM 配置 |
| MTP | `deepseek_mtp`、3 个 speculative token | 删除；标准 Qwen3-8B 不带这份 GLM/DeepSeek MTP 配套 |
| EP / shared expert | EP、`multistream_overlap_shared_expert` | 删除；本次是 dense 模型 |
| DSA / sparse C8 / index | `enable_dsa_cp`、SFA/LI C8、`index_topk_freq` 等 | 删除；不属于本次普通 Qwen3 attention 路径 |
| 模型解析器 | `glm47`、`glm45` | 删除；本次使用普通 completions 验证，不复用 GLM parser |
| KV Connector | Mooncake producer/consumer，端口 30000/30200，engine_id、拓扑描述 | 改成 `LMCacheMPConnector` 连独立 service；旧 Connector 的专属字段全部移除 |
| P prefix caching | 开启 | 首轮关闭本地 prefix cache，用于证明外部 KV 复用 |

标准 Qwen3-8B 官方配置包含 36 层、32 attention heads、8 KV heads，`max_position_embeddings=40960`，`rope_scaling=null`。因此 32768 在该配置范围内，TP8 也满足注意力头的基本整除条件；这只说明形状合理，仍需验证实际软件栈。[模型配置](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)。

### 3.3 分阶段恢复的优化项

- **D 图模式和异步调度**：客户为 `FULL_DECODE_ONLY` + `--async-scheduling`。先用 eager 验证外部 KV；通过后依次恢复图模式、异步调度，各确认一次 KV 恢复。最终是否保留取决于所锁定版本与 MP Connector 的实际兼容性。
- **recompute scheduler**：客户 P=false、D=true，和其 PD 请求流有关。不能直接认为更换 Connector 后语义仍相同；首轮不强制该配置，完整 MP 1P1D 协调确定后再核对。
- **Fused MC2、MLAPO 等模型/执行路径优化**：保留原值作为对照记录，本次不把这些 GLM 路径设置加入 Qwen BF16 必选项。若需要对齐性能，先确认具体 Qwen 路径确实使用它们。
- **`fuse_muls_add`**：当前文档将其列在编译配置内，默认 true。eager 阶段不额外添加旧脚本顶层字段；恢复图模式后按实际版本配置位置核对。

以上是明确的阶段差异，不把“原脚本里有这个参数”当成“新模型和新 Connector 下必需”。

## 4. TP8+TP8 对照的原始命令

**执行条件：主指南 S0/S1/S2 已通过，确认 16 个逻辑设备可用、两组设备内部通信可用、安装版本匹配。** 先停止自己原来的 TP1 实验；本轮另用 `run02`。若 TP1 或 BM 基础步骤仍失败，停在对应阶段修复，不同时引入 TP8。

这组命令目前验证的是“采用 P/D 资源参数的两个完整引擎共享 LMCache”，还没有 MemFabric adapter 和 PD 请求协调入口。A/B 暂用 `kv_both`，不能凭修改 `kv_role` 就宣称完成 1P1D。

### 4.1 每个终端的共同设置

在相同专用容器/环境中执行：

```bash
export MF_LAB="$HOME/memfabric_lab"
export MF_RUN="$MF_LAB/run02"
export MODEL=/data/models/Qwen3-8B
mkdir -p "$MF_RUN"
export PYTHONHASHSEED=0
export OMP_PROC_BIND=false
export OMP_NUM_THREADS=1
export PYTORCH_NPU_ALLOC_CONF=expandable_segments:True
export HCCL_OP_EXPANSION_MODE=AIV
export ACL_OP_INIT_MODE=1
export ASCEND_A3_ENABLE=1
export LD_LIBRARY_PATH="${LD_LIBRARY_PATH:+${LD_LIBRARY_PATH}:}/usr/local/lib"
unset VLLM_PP_LAYER_PARTITION
unset VLLM_ASCEND_ENABLE_FUSED_MC2 VLLM_ASCEND_ENABLE_MLAPO VLLM_ASCEND_ENABLE_FLASHCOMM1
set -o pipefail
```

这里的 `unset` 仅清除本终端可能从客户旧脚本继承的覆盖值，不改变其他服务，也不保证对应软件默认值为 false。P 的 FlashComm1 会在 P 终端明确设置。

查看本机网卡：

```bash
ip -br -4 addr
```

P/D 终端使用同一块有效主机网卡。下面的 `eth0` 和地址都是示例，先替换成上一条输出中的真实值；不依赖隔离网络存在默认路由：

```bash
export MF_NIC=eth0
export MF_IP=192.168.0.10
export HCCL_IF_IP="$MF_IP"
export GLOO_SOCKET_IFNAME="$MF_NIC"
export TP_SOCKET_IFNAME="$MF_NIC"
export HCCL_SOCKET_IFNAME="$MF_NIC"
```

这些设置选择主机控制通信网卡，不等于把 KV 数据面指定为 TCP/RDMA/HCCS。MemFabric 数据面仍需其独立验证。

### 4.2 终端 L：LMCache service

```bash
unset ASCEND_RT_VISIBLE_DEVICES
lmcache server \
  --host 127.0.0.1 --port 5555 \
  --http-host 127.0.0.1 --http-port 8080 \
  --chunk-size 128 \
  --l1-size-gb 4 \
  --eviction-policy LRU \
  --supported-transfer-mode lmcache_driven \
  2>&1 | tee "$MF_RUN/lmcache.log"
```

4 GiB 是这次少量固定前缀实验的初始 L1 预算，不承诺覆盖 64 个满 32K 请求。容器自身必须映射两组设备；修改可见性变量不能补出缺少的设备映射。

### 4.3 终端 A：未来 P 的 TP8 引擎

```bash
export ASCEND_RT_VISIBLE_DEVICES=0,1,2,3,4,5,6,7
export HCCL_BUFFSIZE=400
export VLLM_ASCEND_ENABLE_FLASHCOMM1=1
vllm serve "$MODEL" \
  --host 0.0.0.0 --port 8001 \
  --served-model-name mf-test \
  --dtype bfloat16 \
  --seed 1024 \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 1 \
  --data-parallel-size 1 \
  --distributed-executor-backend mp \
  --master-port 7060 \
  --max-model-len 32768 \
  --max-num-batched-tokens 16384 \
  --max-num-seqs 64 \
  --gpu-memory-utilization 0.92 \
  --block-size 128 \
  --enable-chunked-prefill \
  --no-enable-prefix-caching \
  --enforce-eager \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":5555,"lmcache.mp.mp_transfer_mode":"lmcache_driven"}}' \
  2>&1 | tee "$MF_RUN/engine-a-tp8.log"
```

### 4.4 终端 B：未来 D 的 TP8 引擎

```bash
export ASCEND_RT_VISIBLE_DEVICES=8,9,10,11,12,13,14,15
export HCCL_BUFFSIZE=256
export TASK_QUEUE_ENABLE=1
vllm serve "$MODEL" \
  --host 0.0.0.0 --port 8002 \
  --served-model-name mf-test \
  --dtype bfloat16 \
  --seed 1024 \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 1 \
  --data-parallel-size 1 \
  --distributed-executor-backend mp \
  --master-port 7061 \
  --max-model-len 32768 \
  --max-num-batched-tokens 164 \
  --max-num-seqs 32 \
  --gpu-memory-utilization 0.92 \
  --block-size 128 \
  --enable-chunked-prefill \
  --no-enable-prefix-caching \
  --enforce-eager \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":5555,"lmcache.mp.mp_transfer_mode":"lmcache_driven"}}' \
  2>&1 | tee "$MF_RUN/engine-b-tp8.log"
```

此时 B 仍是完整引擎，缓存 miss 时会正常 prefill。保留 D 的 `164` 是参数对照；不把它的冷请求耗时当作完整 PD 的 Decode 性能。

两组各有 8 个 worker，每个 worker 都要确认 connector 初始化成功，不能只看 rank 0 或 HTTP 存活。端口 5555、8080、8001、8002、7060、7061 均应先检查占用；`7060/7061` 是两个引擎的 master 端口，不是 MemFabric 数据端口。

### 4.5 请求与验收

按主指南 6.3/6.4 的相同请求文件先请求 A，再请求 B，沿用 `mf-test` 模型名和 8001/8002 端口。本轮继续只发一个固定前缀请求，不直接用 `max-num-seqs=64/32` 发满并发；这些参数是调度上限，不是实际请求并发。

```bash
grep -nEi 'Stored|Retrieved|external.*(hit|token)|Creating transfer context' "$MF_RUN/lmcache.log" "$MF_RUN/engine-a-tp8.log" "$MF_RUN/engine-b-tp8.log" | tail -n 50
```

成功条件仍是 A store 完成、B external retrieve 且成功生成。参数、rank 数和 TP 分片都必须记录；该阶段通过只证明 TP8 的共享服务基线，不能证明 BM 命中或单请求 P→D 交接。

图模式恢复时，先仅将 B 的 `--enforce-eager` 替换为 `--compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'`，验证同一前缀的外部 KV 恢复；通过后再单独增加 `--async-scheduling`。若目标版本明确不支持该组合，就保留 eager 并记录差异，不为匹配参数而升级整套环境。

## 5. 后续 MemFabric 适配保持什么不变

固定模型、dtype、seed、P/D 设备组、TP/PP/DP、请求内容和已验证的执行模式。在 LMCache service 一侧加载我们实现的 BM 后端，再完成“store 完成 → 定向驱逐 L1 → BM load → NPU KV 恢复”。不要同时替换 Connector、调整 TP、打开图模式，再据一次成功/失败判断 MemFabric。

完整 1P1D 的协调入口仍需实现或确认兼容路径。客户原件没有提供适用于 LMCache MP 的代理；Mooncake 的 `use_ascend_direct`、engine_id、prefill/decode 拓扑 JSON 不是独立 KV 池的配置，不能原样保留。

## 6. 与原资料的证据边界

原脚本只提供其参数和启动形态，本文没有据此声称原 GLM 服务已在当前 A3 机器验通。新版命令做了来源对照与静态检查，没有执行模型、NPU 通信、LMCache 或 MemFabric。

模型范围与官方部署入口参考：[Qwen3-Dense v0.23.0 文档](https://docs.vllm.ai/projects/ascend/en/v0.23.0/tutorials/models/Qwen3-Dense.html)。此页面会随维护更新示例镜像；本次使用客户已有的 v0.23.0 基线，不据网页中的更新标签自动升级。
