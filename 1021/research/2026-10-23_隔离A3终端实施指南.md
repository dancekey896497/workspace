# 隔离 A3：LMCache–MemFabric 终端实施指南

日期：2026-10-23。适用条件：一台约 16 卡的 A3，机内 HCCS 可用，缺跨服务器互联物料；实施机不能被本机访问，可以拉 GitHub，可以单向导入文件，只能回传少量文字。

**工作方式：本地准备代码和明确命令 → 服务器执行一小步 → 回传结果和第一处错误 → 本地修正后交付下一版。** 不依赖远程桌面、SSH 回连、网页操作或服务器推送 GitHub。

**当前状态：已经 fork 并克隆 LMCache-Ascend，本地分支为 `feature/memfabric`，还未发布到 GitHub，也还没有 MemFabric adapter 实现。本文是实施指导；以下 A3 实机步骤均为 `NOT_VERIFIED`。**

## 1. 先明确这次要验证什么

目标数据流：

```text
vLLM-Ascend A ─┐
              ├─ LMCacheMPConnector → 独立 lmcache server → 新增 MemFabric 后端
vLLM-Ascend B ─┘                           L1 CPU 内存          BM DRAM 池
```

先证明两个引擎能使用独立缓存服务，再证明缓存确实存到 MemFabric、能从 MemFabric 恢复，最后接完整 P/D 请求流程。

| 步骤 | 要解决的问题 | 当前能否执行 |
| --- | --- | --- |
| S0 环境盘点 | 实际设备、拓扑、版本、模型、依赖是否具备 | 可以，第一轮只做这个 |
| S1 原生推理 | 不接缓存服务时，选定模型能否运行 | 环境和模型就绪后可以 |
| S2 MP 基线 | 两个引擎能否共享一个 LMCache service | 配套版本就绪后可以 |
| S3 BM 单 rank | MemFabric 能否分配 DRAM、SDMA 写入读回 | 配套和 Python 包就绪后可以 |
| S4 BM 双 rank | 能否访问另一设备绑定进程贡献的 DRAM | 需要我们交付小型 SDMA 验证程序 |
| S5 后端对象读写 | adapter 的 store / lookup / load 是否正确 | 需要实现 adapter |
| S6 KV 池恢复 | L1 miss 后能否从 BM 恢复到推理 NPU | 需要 adapter 和定向 L1 驱逐验证入口 |
| S7 真正 1P1D | 一个请求的 P 结果能否交给 D 连续生成 | 需要匹配 MP 路线的协调/代理方案 |

**两个 `vllm serve` 接同一个 server 是共享缓存实验，还不是完整 1P1D。** 1P1D 还要完成请求转发、P 写入完成通知、D 等待与恢复等协调。P 和 D 各自通常都需要加载模型权重；16 个可见设备是否能分成 TP8+TP8，要根据模型和 HBM 余量决定。

当前主线维护 MP 接入。旧 `examples/disagg_prefill/hccs` 使用 `LMCacheAscendConnectorV1Dynamic` 和 `hixl`，属于另一条进程内路线；不要将它的配置、旧 LMCache 依赖或 proxy 直接拼进本指南的 MP 实验。[主线说明](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/README.md)、[MP 说明](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/docs/mp_mode/README.md)。

## 2. 隔离环境的操作约定

- 以下命令在 **A3 的 Linux Bash** 中执行，不是在本机 Windows PowerShell 中执行。
- 优先进入现有、专门用于本实验的容器或 Python 环境。先复用已能推理的环境，发现不匹配再处理；不要直接升级驱动、CANN 或正在使用的业务环境。
- 同一轮的 server、引擎和请求终端使用同一个容器、Python 环境、模型目录。跨容器共享设备 IPC、`/dev/shm` 和网络不是第一轮任务。
- 服务前台运行，每个长驻进程占一个终端，保留日志。使用自己的终端 `Ctrl+C` 停止，不使用 `killall python` 或批量清理其他人的任务。
- 每轮一个目录，例如 `run01`、`run02`。失败后保留这一轮日志；每次只修复一个原因，不同时换模型、版本、协议和卡号。
- 回传文字即可，不要求上传完整日志、模型、容器或源代码目录。

每个终端先设置同一组目录：

```bash
export MF_LAB="$HOME/memfabric_lab"
export MF_RUN="$MF_LAB/run01"
mkdir -p "$MF_RUN"
export PYTHONHASHSEED=0
set -o pipefail
```

`pipefail` 使接了 `tee` 的失败命令仍然返回失败状态。一个阶段失败就停在该阶段，不连续粘贴后续所有命令。

如果 `npu-smi` 某个子命令不支持，回传命令和错误即可，不安装另一版工具替换它。

### 3.3 模型和端口

本轮固定使用 **Qwen3-8B**，将下面的路径改成服务器上的真实模型目录，不依赖服务器访问 Hugging Face 下载模型。先用 TP1、4096 上下文、单请求并发跑通原生服务；共享缓存阶段再用两块空闲设备各启动一个相同的 TP1 实例。两个实例各自加载一份模型权重，设备是否有足够空闲 HBM 以 S0 盘点和实际启动为准。

```bash
export MODEL=/data/models/Qwen3-8B
test -f "$MODEL/config.json"
python3 -c 'import json,os; p=os.path.join(os.environ["MODEL"],"config.json"); c=json.load(open(p)); print({k:c.get(k) for k in ["architectures","model_type","torch_dtype","dtype","num_hidden_layers","num_attention_heads","num_key_value_heads"]})'
ss -ltnp | grep -E ':(5555|8080|8001|8002|8570|8572)\b'
```

`ss` 过滤没有输出通常表示这些 TCP 端口未监听；`grep` 此时返回 1，不是服务错误。如果有占用，记录进程/端口，改用空闲端口并同步修改所有相关命令，不停止别人的服务。

### 3.4 S0 的判断

当前查阅的主线要求 CANN ≥ 8.5、驱动 ≥ 25.5、PyTorch ≥ 2.8、vLLM / vLLM-Ascend ≥ 0.23；这是文档中的配套范围，**不是建议把现有机器全部升级到这些版本，也不能保证任意更高版本组合都兼容**。源码 `pyproject.toml` 还约束 Python `>=3.10,<3.13`。

MemFabric DRAM 池另有驱动、固件和 A3 L1 互联配套要求；官方 README 提到 HDK 25.5.0 起、推荐 25.5.1，以及 A3 DRAM 池化对应的 L1 配套。普通 HCCS 通信已通，仍不能替代这项确认。[MemFabric 配套说明](https://github.com/Ascend/memfabric_hybrid/blob/master/README.md#软件硬件配套说明)。

**第一轮到这里回传。** 若机器已有兼容 MP 环境，可继续 S1/S2；若缺环境，则依据这次盘点准备固定版本的材料，不在现场反复尝试最新版。无法确认的固件/L1 版本写“未知”，先由机器维护方核实，不在本实验中直接更新。

## 4. 代码和依赖怎样送进去

### 4.1 GitHub 能解决源码传递，不能自动解决所有依赖

| 材料 | 建议路径 | 需要注意 |
| --- | --- | --- |
| 我们的适配代码 | GitHub fork 的指定提交 | 每轮给出完整 commit 和改动说明 |
| LMCache 核心 | 官方仓库的匹配提交 | 首次选定后固定，不每轮追 `dev` 最新 |
| `hcomm` | 能访问 GitCode 则拉取；否则导入源码包 | LMCache-Ascend 的子模块指向 GitCode；版本须匹配 CANN |
| MemFabric 和缺少的 Python 依赖 | 对应 Linux/CPU 架构/Python ABI 的 wheel | Windows wheel 不能拿到 Linux A3 使用 |
| CANN、驱动、镜像、模型 | 复用目标环境；缺少时单向导入匹配材料 | 不承诺 GitHub 能提供这些材料 |

当前本机仓库位置：`LMCache-Ascend/`；上游 `LMCache/LMCache-Ascend`，fork 为 `Dancekey/LMCache-Ascend`。本地基线提交：`c5e29f15902437883dba530c22705a48ff7ce0fb`。

目标机可先拉源码用于阅读，不触发安装：

```bash
mkdir -p "$MF_LAB/src"
cd "$MF_LAB/src"
git clone https://github.com/Dancekey/LMCache-Ascend.git
git -C LMCache-Ascend remote add upstream https://github.com/LMCache/LMCache-Ascend.git
git -C LMCache-Ascend switch --detach c5e29f15902437883dba530c22705a48ff7ce0fb
git -C LMCache-Ascend rev-parse HEAD
git -C LMCache-Ascend submodule status
```

仅对新的目录执行 `clone` / `remote add`。已经存在时，先查看 `git status --short --branch` 与 `git remote -v`，不覆盖现有改动。暂时不加 `--recurse-submodules`，避免误把 GitCode 不通当成 GitHub 克隆失败。

**现在不能执行 `git clone -b feature/memfabric ...`：该分支还只有本地版本。** 首版实现交付时会明确给出已发布分支、固定提交和启动入口。

### 4.2 需要安装时怎么做

这一节在 S0 配套确认、离线依赖准备好、进入专用实验环境之后执行。已有可用安装先复用，不重装。LMCache-Ascend 安装会构建原生扩展并应用集成补丁，不要把它当成只改自己源码目录的纯 Python 操作。

有 GitCode 访问能力时，在选定 CANN 对应 `hcomm` 版本后再初始化、切换子模块。只有 GitHub 能访问时，将匹配的 `hcomm` 完整源码作为单向文件材料导入 `third_party/hcomm/`；材料说明必须记录版本、提交及其子依赖是否齐全。不要临时换一个名字相似的镜像仓库。

S0 回传后，本地开发端会给出匹配的 LMCache 核心提交。需要新取核心源码时执行下面的模板；`CORE_COMMIT` 必须换成这次选定的真实提交，不能留下占位文字：

```bash
cd "$MF_LAB/src"
git clone --branch dev https://github.com/LMCache/LMCache.git
export CORE_COMMIT=本轮选定的核心完整提交号
git -C LMCache switch --detach "$CORE_COMMIT"
git -C LMCache rev-parse HEAD
```

匹配的源码以及全部构建和运行依赖都就绪后，安装命令保持直接：

```bash
python3 -m pip install --no-index --no-deps --no-build-isolation -v -e "$MF_LAB/src/LMCache" 2>&1 | tee "$MF_RUN/install-lmcache.log"
```

上一步成功后：

```bash
python3 -m pip install --no-index --no-deps --no-build-isolation -v -e "$MF_LAB/src/LMCache-Ascend" 2>&1 | tee "$MF_RUN/install-ascend.log"
python3 -m pip check
python3 -c 'import lmcache, lmcache_ascend; print(lmcache.__file__); print(lmcache_ascend.__file__)'
```

这些开关禁止 pip 自行联网补依赖或替换现有依赖；**不负责补齐依赖，也不能禁止构建脚本自己访问网络**。若提示缺包、缺源码或编译失败，回传第一处错误，准备缺少的确切物料后再安装，不删掉开关盲目升级。

MemFabric 缺失时使用实际交付的单个 wheel 路径，例如先设置 `MF_WHEEL` 为真实文件，再执行：

```bash
python3 -m pip install --no-index --no-deps "$MF_WHEEL"
python3 -c 'import memfabric_hybrid as mf; from memfabric_hybrid import bm; print(mf.__file__); print("BmConfig", hasattr(bm,"BmConfig")); print("create2", hasattr(bm,"create2")); print("SDMA", hasattr(bm.BmDataOpType,"SDMA"))'
```

导入成功仅说明 Python/native 库基本可加载，不代表 DRAM 池或 HCCS 已经可用。[官方离线安装说明](https://github.com/Ascend/memfabric_hybrid/blob/master/doc/installation.md)。

## 5. S1：先跑一个不接 LMCache 的 vLLM

前提：S0 已选好空闲设备；下例的 `0` 只是示例，必须换成目标环境确认的编号。模型必须能在所选单卡上装下。

终端 A：设置第 2 节目录和已有环境，再执行：

```bash
  --block-size 128 \
  --enforce-eager \
  --no-enable-prefix-caching \

```

终端 B：

```bash
curl --fail-with-body --max-time 10 http://127.0.0.1:8001/health
curl --fail-with-body --max-time 120 http://127.0.0.1:8001/v1/completions \
  -H 'Content-Type: application/json' \
```

成功：health 为 HTTP 200（可能无正文），请求返回 `choices`、`usage`，没有引擎错误。旧 curl 若不支持 `--fail-with-body`，仅将其改成 `--fail`。

## 6. S2：独立 LMCache server + 两个引擎

这里验证现有 MP 基线，**暂时不启用 MemFabric**。官方接入使用 `LMCacheMPConnector`，NPU 默认选择 `lmcache_driven`。[启动与验证依据](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/docs/mp_mode/lmcache_driven.md)。

### 6.1 终端 L：启动缓存服务

server 所在环境必须能看见后续两个引擎所用的 NPU，不要只给它暴露其中一张。清除的是本终端的 runtime 掩码；容器本身若只映射了一张设备，需要换到正确的实验容器。

```bash
unset ASCEND_RT_VISIBLE_DEVICES
lmcache server \
  --host 127.0.0.1 --port 5555 \
  --http-host 127.0.0.1 --http-port 8080 \
  --chunk-size 128 \
  --l1-size-gb 4 \
  --eviction-policy LRU \
  --supported-transfer-mode lmcache_driven \
  2>&1 | tee "$MF_RUN/s2-lmcache.log"
```

这里的 4 GiB 是初始 **CPU L1 缓存预算**，不是给 Qwen3-8B 模型的 HBM；先确认主机内存有余量。本轮从短请求、单并发开始，后续容量按实际 KV 大小调整。

成功标志：ZMQ 服务监听 5555，HTTP 服务监听 8080。可以在请求终端执行以下命令检查 HTTP 服务；LMCache 的路径是 `/healthcheck`，vLLM 的路径才是 `/health`：

```bash
curl --fail-with-body --max-time 10 http://127.0.0.1:8080/healthcheck
```

若 `--http-host` 等参数不存在，说明安装版本不同，停下回传 `--help`，不猜另一套参数。

### 6.2 终端 A：启动第一个引擎

```bash
export MODEL=/data/models/Qwen3-8B
export ASCEND_RT_VISIBLE_DEVICES=0
vllm serve "$MODEL" \
  --served-model-name mf-test \
  --host 127.0.0.1 --port 8001 \
  --tensor-parallel-size 1 \
  --max-model-len 4096 \
  --max-num-seqs 1 \
  --gpu-memory-utilization 0.7 \
  --block-size 128 \
  --enforce-eager \
  --no-enable-prefix-caching \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":5555,"lmcache.mp.mp_transfer_mode":"lmcache_driven"}}' \
  2>&1 | tee "$MF_RUN/s2-engine-a.log"
```

预期 worker 日志包含 `device_type=npu, mode=lmcache_driven`。只看到模型 HTTP 服务启动还不够，需要确认 connector 建立成功。

### 6.3 请求终端：准备固定长前缀并先请求 A

下面的一行 Python 只生成固定请求 JSON，不负责启动或管理服务。比手工输入上千 token 更容易复现。

```bash
python3 -c 'import json; print(json.dumps({"model":"mf-test","prompt":"The cache stores reusable attention keys and values. "*160+"Explain why this saves computation.","max_tokens":32,"temperature":0}))' > "$MF_RUN/request.json"
curl --fail-with-body --max-time 180 http://127.0.0.1:8001/v1/completions \
  -H 'Content-Type: application/json' \
  --data-binary @"$MF_RUN/request.json" \
  -o "$MF_RUN/response-a.json" -w 'HTTP=%{http_code} total=%{time_total}s\n'
cat "$MF_RUN/response-a.json"
```

确认 `usage.prompt_tokens` 明显超过 128，且没有超过 4096 的上下文限制。然后看 server 和引擎日志中的存储完成信息；存储没完成前不发 B 的验证请求。

### 6.4 终端 B：启动第二个引擎

复制 **6.2 的整条命令**，仅改三处：

1. `ASCEND_RT_VISIBLE_DEVICES` 改成第二个空闲设备的编号；
2. `--port 8001` 改成 `--port 8002`；
3. 日志文件改成 `s2-engine-b.log`。

两个引擎的模型路径字符串、模型名字、TP、dtype/KV 格式和 chunk/block 配置保持一致。缓存 key 使用的模型名取自模型路径，仅让 `--served-model-name` 相同还不够。它们连接同一个 `127.0.0.1:5555`；worker 的实例标识由 MP 实现生成，不需要手工让它们使用相同 ID。

请求终端先检查 B 的 `/health`，再使用完全相同的请求文件：

```bash
curl --fail-with-body --max-time 10 http://127.0.0.1:8002/health
curl --fail-with-body --max-time 180 http://127.0.0.1:8002/v1/completions \
  -H 'Content-Type: application/json' \
  --data-binary @"$MF_RUN/request.json" \
  -o "$MF_RUN/response-b.json" -w 'HTTP=%{http_code} total=%{time_total}s\n'
cat "$MF_RUN/response-b.json"
grep -nEi 'Stored|Retrieved|external.*(hit|token)|Creating transfer context' "$MF_RUN/s2-lmcache.log" "$MF_RUN/s2-engine-a.log" "$MF_RUN/s2-engine-b.log" | tail -n 40
```

S2 通过需要：A 的 store 完成、B 存在实际 external retrieve/token 命中、B 成功返回。具体日志文字随版本有变化；没有查到字符串时回传对应日志片段，不能直接认定成功或失败。两份响应本身、请求变快、服务能启动，都不足以证明 KV 复用。

这里命中的可以是 server 的 L1，**不代表 MemFabric 已接入，也不证明 HCCS 路径**。这一步用来排除 vLLM ↔ LMCache service 的基础问题。

停止时先停 A/B，等请求结束，再停 server。如果 server 崩溃或需要重启，A/B 一起重启，避免沿用失效 IPC 状态。不要在服务运行中清理 `/dev/shm`。

## 7. S3：单独验证 MemFabric 单 rank SDMA

先停止本轮推理和缓存进程，降低资源竞争。此步骤不运行 vLLM。

准备官方样例源码；已有 checkout 则复用，不重复克隆：

```bash
cd "$MF_LAB/src"
git clone https://github.com/Ascend/memfabric_hybrid.git
git -C memfabric_hybrid rev-parse HEAD
```

样例源码必须和已安装的 MemFabric API 配套。`BmConfig`、`create2` 或 `SDMA` 不存在时先处理版本，不能只升级 wheel 试运气。本文核查的样例为 `03_optimization/03_device_sdma`；world size 为 1，DRAM 为 4 GiB，默认 device 为 0。

在专用 BM 终端清除 runtime 掩码，再按 `npu-smi info -m` 和容器设备映射确定 BM 使用的 device 编号。不要照搬推理进程经过掩码重排后的局部编号。

```bash
unset ASCEND_RT_VISIBLE_DEVICES
export BM_DEVICE=0
cp "$MF_LAB/src/memfabric_hybrid/examples/memory_pool/03_optimization/03_device_sdma/03_device_sdma.py" "$MF_RUN/bm_single_sdma.py"
sed -i "s/^DEVICE_ID = 0$/DEVICE_ID = ${BM_DEVICE}/" "$MF_RUN/bm_single_sdma.py"
grep -nE 'LOCAL_DRAM_SIZE|WORLD_SIZE|DEVICE_ID|data_op_type' "$MF_RUN/bm_single_sdma.py"
```

检查输出确实是预期设备、`WORLD_SIZE = 1` 和 `BmDataOpType.SDMA`；若替换没有生效，先停止检查，不运行。此副本仅用于本轮测试，不修改官方源码。需要超过 4 GiB 的可用主机内存及额外临时缓冲余量，NPU 也不能被占满；端口 8570 必须空闲。

```bash
python3 -u "$MF_RUN/bm_single_sdma.py" 2>&1 | tee "$MF_RUN/s3-bm-single.log"
```

预期结尾包含 `BM destroy SUCCESS` 和 `03_device_sdma ok`，没有 traceback / assert 失败。[原始样例](https://github.com/Ascend/memfabric_hybrid/blob/master/examples/memory_pool/03_optimization/03_device_sdma/03_device_sdma.py)。

这是官方性能样例的初步 smoke：它复用源/目标 buffer，不是我们最终的全对象正确性验收；单 rank 更不能证明跨设备或跨机 HCCS。不要把它输出的吞吐直接当作 KV 池收益。

## 8. S4–S7：我们后续需要交付什么

这些步骤尚没有本项目可运行入口，下面是开发与验收顺序，不是已有命令。不会要求你在服务器上手写 backend 或修改大量源码；实现和小型验证程序在本地准备，服务器只运行交付的固定版本。

### S4：两 rank 的 SDMA 测试

交付一个小程序，明确接收 rank、world size、device、store 地址和容量。你开两个终端，分别运行一条 `python3 ...` 命令。rank 0/1 各绑定一块已确认的 HCCS 设备，测试远端 rank 贡献的 DRAM，双向逐块检查不同数据模式，并覆盖 NPU HBM ↔ 池 DRAM 的目标路径。

必须显式限定 SDMA，保存所选协议及失败返回值；不能启用混合协议 fallback 后仅凭“成功”认定走了 HCCS。控制面使用本机 TCP rendezvous 是正常的，不等于数据走 TCP。若要进一步声称字节确实经过指定 HCCS 链路，还要结合该机支持的链路计数或 profiling；只有协议配置和拓扑时，报告为“双 rank SDMA 功能通过，具体链路流量未确认”。

**不能直接拿官方 `01_single_node_multi_device_dram.py` 当 HCCS 证明：已查到的版本默认 `DEVICE_RDMA`。** [官方多 rank 源码](https://github.com/Ascend/memfabric_hybrid/blob/master/examples/memory_pool/02_scale_out/01_single_node_multi_device_dram/01_single_node_multi_device_dram.py)。

### S5：实现 MemFabric L2 adapter

优先在 LMCache-Ascend 侧新增 backend，复用 LMCache 的 external L2 plugin 接口。首版使用单 service、固定池容量、固定成员，处理对象 key → rank/offset/length、写入完成后发布可读、读锁保护、回收和关闭时的缓冲生命周期。

先用无模型的小型验证入口运行 store → lookup/lock → load → unlock，检验数据一致、缺失 key、容量满和读取期间不能复用槽位。测试使用真实 MemFabric，不能用 mock 成功替代实机结果。[L2 插件接口](https://github.com/LMCache/LMCache/blob/dev/docs/design/v1/distributed/l2_adapters/plugin.md)。

### S6：接回 LMCache service，排除只命中 L1

沿用 S2 的 `lmcache server` / `vllm serve` 操作方式，只增加已实现后端所需的配置。交付时提供完整 JSON/文件，不能用一个目前不存在的 `--enable-memfabric` 开关代替实现。

验收顺序：

1. A 请求并完成 BM store，记录 key、owner rank、写入字节与完成状态。
2. 通过这一版本支持的定向入口驱逐目标 L1 对象，保留 BM 副本；没有入口则由我们增加仅用于实验的小入口。
3. B 请求同前缀，记录 **L1 miss → BM L2 hit → 真实读取字节 → NPU KV 恢复 → 请求成功**。
4. 再请求一个不在池中的前缀，确认 miss 后正常重算。

不能用“重启整个 server”来制造 L1 miss，因为首版池和对象目录都是易失状态，重启可能把 BM 副本或索引一起销毁。速度变化只作辅助证据。

### S7：最后接真正 1P1D

Qwen3-8B 先用 TP1+TP1；本轮不需要为了用满 16 卡而增大 TP。需要交付适合 MP + BM 的完整启动组：P、D、service/pool、请求协调入口，并证明同一请求的 P KV 在 D 中使用。通过后，有更大模型或并发目标时再单独评估设备分配。

旧 HIXL 1P1D 可作为单独的通信对照，但它不经过我们要做的 BM KV 池，不算适配验收。若要运行该对照，另用它匹配的环境和完整配置，不与当前 MP 环境混装。

单机可验证适配、对象生命周期、指定设备对上的机内通信与 NPU KV 恢复；跨服务器互联、跨机性能和超节点扩展性继续标为 `NOT_VERIFIED`。

## 9. 每轮代码更新与回退

每次交付至少说明：仓库和固定 commit、改了什么、是否需要重编译、执行哪一条命令、成功标志、失败回传哪些行。你不需要在隔离机器解决 merge conflict。

**以下模板仅在 `feature/memfabric` 已发布后使用**，`TEST_COMMIT` 换成本轮给出的真实提交。先停自己的实验服务：

```bash
cd "$MF_LAB/src/LMCache-Ascend"

```

记录当前提交为上一版；工作区无本地修改后再执行：


## 10. 出错只回传这一小段

失败后先记录阶段、完整启动命令、软件提交、设备和端口。看**第一处导致退出的错误**；末尾的 worker exited / timeout 常是连带结果。

下面以引擎 A 为例；其他阶段换成对应日志文件：

```bash
grep -n -m 1 -E 'Traceback|ERROR|Error|Exception|AssertionError|failed' "$MF_RUN/s2-engine-a.log"
tail -n 60 "$MF_RUN/s2-engine-a.log"
```

如果首错在第 200 行附近，另回传其前后约 60 行：

```bash
sed -n '180,240p' "$MF_RUN/s2-engine-a.log"
```

编译失败回传第一次编译错误附近，不只回传最后的 `Failed building wheel`。只隐藏令牌、内部地址或敏感路径，保留错误码、模块名、函数名及版本。模型输出过长时保留 `usage`、错误字段和少量输出即可。
