核查日期：2026-10-23。仅核查 MP 基线与离线依赖边界，没有安装或实机执行。未修改 LMCache-Ascend。

本地 LMCache-Ascend HEAD：`c5e29f15902437883dba530c22705a48ff7ce0fb`。LMCache 上游通过官方 `dev` 原始源码核查，服务器执行时必须另记实际 commit；不要把移动分支名当作版本锁定。

## 可确认的结论

- `lmcache server` 是带 ZMQ 请求服务与 HTTP 管理端点的入口。请求默认 5555，HTTP 默认 127.0.0.1:8080。
- `--host`、`--port`、`--http-host`、`--http-port` 都是真实参数。ZMQ 服务的 `--host` 填裸主机地址；连接器的 `lmcache.mp.host` 可明确填 `tcp://127.0.0.1`。
- `--supported-transfer-mode lmcache_driven` 是当前默认值；显式填写可减少版本默认值歧义。NPU 的该路径由 server 导入 engine 的 NPU IPC handle。
- 两个 TP1 engine 连接同一服务，不需要手填不同的 LMCache worker `instance_id`；当前源码为每个 worker 自动生成 UUID 派生的 int64 身份。server 的 `--instance-id` 是服务身份，不能当成两个 engine 的配置项。
- 两个 engine 使用同一个请求 host/port，但 vLLM HTTP 端口、可见设备不同。第一轮放在同一个容器/同一运行环境，减少 IPC namespace 差异。
- **LMCache server 必须能看到两个 engine 使用的实际 NPU**。NPU IPC wrapper 用设备 UUID 找回本进程中的设备索引，不能只给 server 暴露其中一张卡。
- **两 engine 使用完全相同的模型路径字符串**。当前 connector 的 cache model name 来自 `model_config.model`，不是 `--served-model-name`；仅把 API 模型名设为相同，不能保证共享同一缓存 key。模型文件、dtype、TP、block size、KV 格式也应一致。
- T2 只是两个完整推理实例共享 LMCache L1，不是 P/D 分离。不需要旧 P/D proxy、producer/consumer 配对、HCCL P2P YAML 或手工管理远端 KV 地址。

源码证据：

- [LMCache MP server 配置与 CLI](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/multiprocess/config.py)：`MPServerConfig`、`HTTPFrontendConfig`、`add_mp_server_args`、HTTP 参数注册。
- [LMCache worker adapter](https://github.com/LMCache/LMCache/blob/dev/lmcache/integration/vllm/vllm_multi_process_adapter.py)：`instance_id = uuid.uuid4().int & ((1 << 63) - 1)`；连接同一 server 不会因此共享 worker 身份。
- [LMCacheMPConnector](https://github.com/LMCache/LMCache/blob/dev/lmcache/integration/vllm/lmcache_mp_connector.py)：`get_dcp_decorated_model_name` 取 `vllm_config.model_config.model`。
- [NPU IPC wrapper](https://github.com/LMCache/LMCache/blob/dev/lmcache/v1/platform/devices/npu/ipc_wrapper.py)：`device_uuid`、`_get_device_index_from_uuid`、`_new_shared_npu`。
- [MP HTTP API/入口说明](https://github.com/LMCache/LMCache/blob/dev/docs/source/mp/index.rst)：`GET /healthcheck`；不要误用旧示例中的 `/health`。

## 可用于主指南的三终端基线

前提：原生 vLLM 已在相同模型和环境通过；选择两张空闲且已确认运行时编号的 NPU；以下以编号 0、1 作示例。模型选择普通 dense GQA/MHA Qwen3，TP1 能装下。L1 8 GiB、上下文 4096 等是本次小实验建议值，不是上游统一要求。

终端一：服务看见两个 engine 的 NPU。

```bash
export PYTHONHASHSEED=0
export ASCEND_RT_VISIBLE_DEVICES=0,1
lmcache server \
  --host 127.0.0.1 --port 5555 \
  --http-host 127.0.0.1 --http-port 8080 \
  --chunk-size 128 --l1-size-gb 8 --eviction-policy LRU \
  --supported-transfer-mode lmcache_driven
```

先确认两个监听端口空闲，并等待 server 启动后再启动 engine。可以读取 `http://127.0.0.1:8080/healthcheck`；HTTP liveness 不是 KV 存取通过证明。

终端二：实例 A。

```bash
export PYTHONHASHSEED=0
export ASCEND_RT_VISIBLE_DEVICES=0
export MODEL_PATH=/实际已存在的同一个模型目录
vllm serve "$MODEL_PATH" \
  --served-model-name qwen3 --tensor-parallel-size 1 \
  --max-model-len 4096 --max-num-batched-tokens 1024 \
  --max-num-seqs 1 --gpu-memory-utilization 0.7 \
  --enforce-eager --no-enable-prefix-caching \
  --port 8900 \
  --kv-transfer-config '{"kv_connector":"LMCacheMPConnector","kv_role":"kv_both","kv_connector_extra_config":{"lmcache.mp.host":"tcp://127.0.0.1","lmcache.mp.port":5555,"lmcache.mp.mp_transfer_mode":"lmcache_driven"}}'
```

终端三：实例 B 使用完全相同命令与模型路径，只把 `ASCEND_RT_VISIBLE_DEVICES` 改为 `1`，HTTP `--port` 改为 `8901`。不需要自定义 instance id，不要把两个 engine 的 `kv_role` 改成 producer/consumer。

这套命令的有效性仍以目标机实际 `lmcache server --help`、`vllm serve --help` 和已安装版本为准。先在 server、A、B 三侧都确认 `device_type=npu, mode=lmcache_driven`，再做 A cold→B warm 的相同长 prompt 测试；prompt 应覆盖多个完整 chunk。B 首次请求即命中外部缓存、server 有对应 Stored/Retrieved 记录才是共享 L1 的核心证据，两个 HTTP 服务存活不够。

源文档：[本地对应版本 README](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/README.md)、[lmcache_driven 部署说明](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/docs/mp_mode/lmcache_driven.md)。其中普通 Qwen3 示例 chunk 为 128；DeepSeek-V4 的 4096、TP8、EP、模型解析器和编译参数不能复制到本轮 TP1 基线。

## 隐含版本和设备依赖

1. 本地 README 匹配表是 LMCache-Ascend main ↔ LMCache dev，vLLM/vLLM-Ascend >=0.23；也列出成对 v0.5.6。不能把 main 的新命令与旧 in-process 0.4.5 混装。当前 in-process 维护分支为 `dsv4_support_045`，不是本次基线。
2. 当前本地 main 已写入 `lmcache_driven` 支持混合 Mamba 模型，与昨天版本存在变化。本轮选 Qwen3 普通 attention，避免把这类快速变化支持矩阵带入首次验证。
3. server 与 engine 的 `--chunk-size` / block 几何必须兼容。当前 dev 可以协商更大的 chunk，但不能把这个新行为外推旧 tag。以启动日志最终 chunk 和 block size 为准。
4. `lmcache_driven` 不要求照抄 `engine_driven` 的 `--shm-name --no-l1-use-lazy`；两条模式各有数据路径，不能随意拼接。
5. 安装前记录 CANN 的真实版本文件与路径，不能只看 `/usr/local/Ascend` 目录名。`setup.py` 从 `${ASCEND_HOME_PATH}/${arch}-linux/ascend_toolkit_install.info` 的 `version=` 读取；也会调用 `npu-smi` 查 SOC，并依赖 CANN 内对应 platform_config。

## 仅 GitHub 网络时会遇到的具体阻碍

### hcomm 子模块不在 GitHub

本地 [.gitmodules](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/.gitmodules) 明确指向 `https://gitcode.com/cann/hcomm.git`。当前 gitlink 为 `4ca1db912ce02a5f5075849a3fa3faaf731bdd60`。

因此 `git clone --recurse-submodules https://github.com/LMCache/LMCache-Ascend.git` 的递归步骤会访问 GitCode。只有 GitHub 可达时，它不能独立完成。文档要求 hcomm 与 CANN 版本匹配，不能为了下载方便随意换成第三方 GitHub 镜像或另一个 commit。

本地 [setup.py](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/setup.py) 始终向 CMake 提供 `HCOMM_SRC_PATH`；[csrc/CMakeLists.txt](https://github.com/LMCache/LMCache-Ascend/blob/c5e29f15902437883dba530c22705a48ff7ce0fb/csrc/CMakeLists.txt) 因此构建 HCCL agent。CANN >=8.5 还构建 HIXL。即使本轮只测本机 MP，也不能假设缺少 hcomm 无影响。

最小处理：先盘点既有镜像/目录中是否已有匹配且完整的 hcomm 源码或已编译好的 LMCache-Ascend；缺失时通过获准的材料传递方式提供对应源码包，记录版本。若远端没有任何传入非 GitHub 依赖的通道，本步骤属于明确依赖缺失，暂停安装即可，不应通过禁用构建掩盖。

### GitHub 可拉源码不等于 pip、镜像和模型可取

- LMCache 的 [pyproject.toml](https://github.com/LMCache/LMCache/blob/dev/pyproject.toml) 需要 setuptools、setuptools_scm、ninja、grpcio/grpcio-tools 等构建依赖；当前隔离构建还声明 torch 2.13.0。README 用 `--no-build-isolation` 是为了使用现有环境，不代表依赖自动消失。
- 当前 [requirements/common.txt](https://github.com/LMCache/LMCache/blob/dev/requirements/common.txt) 含 `transformers>=5.4`、`grpcio>=1.78.0` 等要求。普通 `pip install -e . --no-build-isolation` 仍解析运行依赖，可能访问 PyPI或升级底座。
- LMCache-Ascend 的 CMake 需要 Python headers、pybind11、编译器、CANN/torch_npu headers 和库以及 libnuma。`--no-build-isolation` 下这些都需要预先存在。
- 上游示例镜像来自 quay.io，模型来自本地目录或模型仓库；不能以 GitHub 可达推定它们可下载。

已有完整匹配依赖时，可使用如下形式避免安装阶段联网和隐式升级（这不是缺依赖的解决方案）：

```bash
python -m pip install --no-index --no-deps --no-build-isolation -e /实际源码目录
```

若缺依赖，应先输出缺项与现有版本，准备匹配 Python/CPU 架构/CANN/torch 的 wheel 或源码材料，再继续。不要把一条未限定版本的 `pip install -r ...` 放进首次验证脚本自动执行。
